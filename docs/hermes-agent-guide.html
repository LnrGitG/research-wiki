1. Диагностика: «что-то сломалось»

Перед любой крупной операцией — сначала проверка, потом действия.

hermes doctor && hermes status          # здоровье сетапа и компонентов
hermes logs -f agent                    # живой хвост (errors/gateway/gui тоже)
hermes logs --session <id> --since 1h   # по конкретной сессии
hermes logs --level WARNING -n 100      # только предупреждения и выше
hermes insights --days 7                # токены, стоимость, паттерны инструментов
hermes prompt-size --json               # бюджет системного промпта: skills+memory+tools
Минимальный диагностический сценарий 
hermes doctor
hermes status
hermes logs --level WARNING -n 50
hermes tools list
hermes prompt-size
hermes cron doctor

Известная тяжесть нашего сетапа: kanban-toolset занимает ~23.5 KB схемы (≈5 900 токенов) при 0 строк в kanban.db — крупнейший единичный потребитель статического контекста после системного промпта. hermes tools → снять галочку kanban, либо hermes config set.

2. Сессии и история

hermes sessions list                    # последние, с моделью и источником
hermes sessions export <id> --format md # выгрузка в JSONL/Markdown/QMD
hermes sessions optimize                # слить FTS5-сегменты + VACUUM (диск, без потери)
hermes sessions repair                  # починить state.db / роутинг

В сессии: /resume, /sessions, /undo [N], /rollback [N] (чекпоинты ФС), /compress и /compress here [N] (сжать историю), /status.

Повтор прошлой задачи. Через session_search по query + sort=newest, затем сверка артефактов с файлами на диске: сводки ассистента — это самоотчёты, а не факты. Это правило уже спасало: отчёт «сделано» расходился с содержимым каталога.

3. Cron — наши джобы

У нас 8 джобов. Семь запинены на glm-5.3-flash / ollama-cloud, чтобы дрейф модели не приводил к «молчаливому пропуску».

hermes cron list                        # состав и статус
hermes cron doctor                      # health-check джобов
hermes cron runs <job_id>               # история попыток
hermes cron incidents                   # сбои с ack: --ack <id>
hermes cron run <job_id>                # запустить на следующем тике
hermes cron status                      # жив ли планировщик

Режим --no-agent — важный приём: если вся работа делается скриптом (загрузка данных), LLM не нужен, и джоб переводится в режим «скрипт сам себе джоб». Так устроен KEP short-term indicators monthly refresh: пустой stdout = ничего не отправляется, тишина при отсутствии нового выпуска. Это снимает риск дрейфа модели и не тратит токены.

hermes cron create "0 9 5,7 * *" --name "KEP refresh" \
  --script kep_refresh.sh --no-agent --deliver origin

Скрипт cron ищет в ~/.hermes/scripts/; рабочая версия — research-wiki/scripts/. Обёртка в ~/.hermes/scripts/ вызывает репозиторный скрипт одной строкой, чтобы логика жила в git.

Правило идемпотентности. Джоб, который пишет в БД, обязан уметь запускаться дважды без последствий. Ошибка, уже стоившая данных: метка релиза формировалась по-разному при разных путях запуска, поэтому проверка «уже загружено» не срабатывала и данные задвоились. Метка должна зависеть только от имени файла-источника.

4. Навыки и гейт записи

У нас включён skills.write_approval=true: любая мутация skill_manage (staged) ждёт подтверждения — и от агента, и от куратора.

hermes skills list                      # установленные
hermes skills search <запрос>           # поиск по реестрам
hermes skills inspect <имя>             # карточка навыка
hermes skills install <откуда>          # установка (действие пользователя, не гейтится)
hermes skills diff <id>                 # что изменено в staged
hermes skills audit                     # проверка безопасности
hermes skills update                    # обновить установленные

В сессии: /skills pending — очередь staged-мутаций, /skills approve <id>, /skills reject <id>. Файлы очереди: ~/.hermes/pending/skills/*.json.

Важно: в CLI подкоманды skills pending нет — очередь смотрится из сессии через /skills pending. Это разные вещи, и их легко перепутать.

Правило: bundled/hub-скиллы куратор не трогает никогда. Отключить гейт — hermes config set skills.write_approval false.

5. Бандлы — навыки под одну команду

Бандл загружает несколько навыков одним слэш-вызовом. Полезно, когда для задачи нужен устойчивый набор: сбор данных + эконометрика + отчётность.

hermes bundles list                     # установленные бандлы
hermes bundles show <имя>               # состав бандла
hermes bundles create <имя>             # создать
hermes bundles delete <имя>             # удалить
hermes bundles reload                   # пересканировать каталог бандлов

В сессии /<имя-бандла> подгружает все его навыки сразу.

6. Память

Встроенная MEMORY.md / USER.md активна всегда; внешние провайдеры — опция (honcho, mem0, hindsight, openviking и др.).

hermes memory status                    # конфигурация провайдера
hermes memory setup                     # интерактивный выбор провайдера
hermes memory off                       # только встроенная память
hermes memory reset                     # стереть встроенную память (осторожно!)

В сессии: /memory pending|approve|reject — ревью отложенных записей; /journey — таймлайн навыков и памятей.

Бюджет памяти жёсткий: встроенная память ограничена по символам (у нас MEMORY.md и USER.md по 5 000 символов, заполнены почти под потолок). Когда места не хватает, правильный ход — не добавлять, а консолидировать: заменить устаревшую запись новой в одном вызове.

Хранить в памятиНе хранить
Кто пользователь, устойчивые факты среды, постоянные конвенции, предпочтения стиля API-ключи, пароли, токены, разовые данные, прогресс задач, большие датасеты

Процедуры и приёмы — не в память, а в навыки: они подгружаются по релевантности, а не в каждый вызов.

7. Модели, провайдеры, fallback

hermes model                            # пикер модель+провайдер (постоянный дефолт)
hermes fallback list | add | remove     # цепочка при rate-limit/overload
hermes auth status                      # пул кредов, приоритеты
hermes auth login | logout              # вход/выход провайдера

В сессии /model [name] [--global] меняет модель только текущей сессии; постоянный дефолт — через hermes model.

Наш расклад: fallback — claude-sonnet-4 / openrouter; делегаты — glm-5.3-flash; Astra Pro годится только для коротких синтезов, но не для tool-call. Ключи — в .env или в секретах Hermes, никогда в конфигах проекта и не в чате.

8. Инструменты и политика привилегий

hermes tools                            # интерактивный UI включения/выключения
hermes tools list                       # статус всех инструментов и toolsets
hermes tools enable <имя>               # включить toolset или MCP-инструмент
hermes tools disable <имя>              # выключить
hermes tools --summary                  # краткая сводка

MCP-инструменты адресуются как server:tool (например, github:create_issue).

Каждый toolset — это статический контекст в каждом вызове. Поэтому выключение ненужных наборов (вроде kanban при пустой БД) даёт прямую экономию токенов и снижает риск, что модель «зацепится» за лишний инструмент.

Ограничение прав. Опасные операции проходят через подтверждение (hermes approvals, режим --yolo обходит его — использовать осознанно). Правило нашей работы: перед разрушительной операцией создавать точку возврата (git-тег, дамп в бакет) и сообщать путь восстановления.

9. Curator — контроль качества навыков

Curator — фоновая задача на вспомогательной модели: периодически просматривает созданные агентом навыки, чистит устаревшие, объединяет дубли, архивирует неактуальные. Bundled- и hub-навыки не трогает никогда; удаления безвозвратного не бывает — только архив.

hermes curator status                   # статус и статистика навыков
hermes curator usage                    # телеметрия использования всех навыков
hermes curator run --dry-run            # предпросмотр прогона, без изменений
hermes curator run --consolidate        # прогон с LLM-слиянием
hermes curator pause | resume           # приостановить/возобновить
hermes curator list-archived            # что в архиве
hermes curator restore <имя>            # вернуть из архива
hermes curator rollback                 # откат последнего прогона
hermes curator ledger                   # журнал операций

Наш конфиг: curator.consolidate=true (LLM-слияние), skills.write_approval=true — все мутации навыков идут через staged-очередь и одобрение. Это значит, что куратор не может изменить навык молча.

10. Делегирование: субагенты и профили

Отдельных «субагент-команд» в Hermes нет — делегирование устроено иначе.

Два разных механизма — не путать
МеханизмЧто этоКоманда
Делегирование (subagent)Изолированный контекст на одну задачу: возвращает только итог, промежуточный шум не попадает в родителяинструмент delegate_task в сессии
ПрофилиОтдельные «личности» агента со своими навыками, памятью и cronhermes profile create <имя>
 
hermes profile list                     # все профили
hermes profile create <имя>             # новый профиль
hermes profile use <имя>                # сделать дефолтным
hermes profile show <имя>               # детали
hermes profile export | import          # перенос профиля
hermes profile describe <имя>           # описание для kanban-оркестратора

Профили — независимые острова. У каждого свои skills/, plugins/, cron/, memories/. Не переносите навыки между профилями без явного указания — это отдельная сессия пользователя.

Когда делегировать. Детей стоит запускать для reasoning-ёмких подзадач, работы, которая зальёт контекст промежуточными данными, и независимых параллельных веток. Не стоит — для механических шагов без рассуждения (там хватит скрипта).

Наш опыт. Делегаты не могут задавать вопросы и не видят историю чата — контекст надо передавать целиком. Их итог — самоотчёт, а не факт: заявленное «файл записан» или «опубликовано» проверяется отдельно (существование файла, HTTP-код, хеш). У нас так уже ловилось расхождение отчёта с реальностью.

11. Бэкап, обновление, откат

hermes backup -q -l pre-update          # быстрый снапшот критических файлов
hermes backup -k 5                      # zip ~/.hermes с ретеншном 5 копий
hermes backup -o /path/backups          # в конкретный каталог
hermes update --check && hermes update  # проверка, затем обновление (--plan для плана)
hermes checkpoints status               # чекпоинты ФС
hermes checkpoints prune                # чистка старых чекпоинтов

Откат правок ФС — /rollback [N] в сессии. Для данных — восстановление из дампа: у нас точки возврата кладутся и локально, и в бакет wiki-research/rollback/.

Правило обратимости. Перед удалением или перезаписью — точка возврата (git-тег, ветка-бэкап, дамп) и сообщение пути восстановления. Откат должен быть точечным: не задевать соседнюю работу.

12. Отправка и платформы (без LLM)

hermes send -t telegram "текст"          # в канал без агента/токенов
hermes gateway status                    # жив ли gateway
hermes gateway restart                   # перезапуск (только снаружи сессии!)
hermes pairing list                      # пары-коды доступа

Target-форматы: platform, platform:chat_id, platform:#channel, platform:chat_id:thread_id.

Перезапуск gateway изнутри сессии запрещён. Команда убьёт саму сессию: SIGTERM распространяется на дочерние процессы. Запускать только из отдельной оболочки снаружи. Плюс guard режет символ & в командах терминала — сложные цепочки собирать через скрипт-файл.

13. Инварианты нашего сетапа

  • Секреты — только в .env; настройки — config.yaml через hermes config set, руками конфиг не править.
  • Telegram-токен = один слушатель: два gateway на один токен конфликтуют.
  • /model действует на текущую сессию; постоянный дефолт — через hermes model.
  • Навыки hub/bundled куратором не трогаются; мутации — только через гейт write_approval.
  • Перед разрушительной операцией — точка возврата и путь восстановления.
  • Итог делегата — самоотчёт: проверять результат, а не доверять формулировке.
  • Джоб, пишущий в БД, обязан быть идемпотентным.
  • Тяжёлые данные — на YC, не в git: GitHub не место для гигабайтов.

15. Работа на слабом VPS

У нас VPS во Франкфурте с ~1 ГБ ОЗУ. Главное правило: не запускать тяжёлую локальную модель на том же хосте, где живёт агент.

ДействиеЗачем
Swap 2–4 ГБСнижает риск OOM. Без него сбор данных падал по памяти.
Один активный агентЭкономия ОЗУ и CPU.
SQLite/DuckDB вместо больших CSV в памятиЭкономия ОЗУ.
Ограничить логи и кэшДиск быстро заполняется: df -h перед крупным батчем.
Тяжёлые расчёты — на мощной ВМТак переносилась гармонизация: OOM на VPS → ВМ в YC.
Проверять место перед операциейVACUUM и git gc на полном диске падают с невнятной ошибкой.

География тоже ресурс. С этого VPS недоступны российские источники (ЕМИСС, Росреестр) — обход через маршрутизацию по доменам. Обратная ситуация на датацентр-IP в РФ: там блокируются Telegram и зарубежные LLM-провайдеры. Это не сбой, а свойство окружения — учитывать при планировании сбора.

Итоговые лучшие практики

  • Сначала проверка, потом действие — doctor перед крупной операцией.
  • Точка возврата перед разрушительным — и путь восстановления в ответе.
  • Скрипт вместо LLM там, где работа детерминирована — дешевле и надёжнее.
  • Идемпотентность для всего, что пишет в БД — повторный запуск не должен ломать.
  • Итог делегата — самоотчёт, его нужно проверять.
  • Компактная память — консолидировать, а не накапливать.
  • Всё воспроизводимо — код, данные, логи и версии рядом с результатом.

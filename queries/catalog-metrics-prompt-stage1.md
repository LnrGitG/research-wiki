# Промт-спека: каталог экономических показателей (этап 1)

Роль исполнителя: профессиональный дата-инженер и дата-аналитик. Задача —
спроектировать и наполнить каталог экономических показателей для
PostgreSQL research_wiki (ВМ YC), опираясь на практики FRED/DBnomics/
World Bank Metadata Editor/OECD. Промт для делегатов с разными ролями.
Структура: цель → слои модели → поля каталога → этапы 0–7 → роли агентов
→ приёмка → контрольные рубежи владельца → экономика моделей.

---

## ПАРОЛЬНАЯ ЧАСТЬ (копируется в задачу делегату дословно)

Ты — дата-инженер и дата-аналитик хранилища экономических временных
рядов (PostgreSQL 16 + pgvector, БД research_wiki). Задача этапа —
{подставить этап}. Работаешь read-only, если в задаче не указано иное.

Контекст хранилища: существующая схема core.metric (metric_id,
metric_code, name_ru, description, unit_id, frequency_id, metric_type,
index_base, is_derived, formula_text, status, tags) и core.observation_v2
(obs_id, metric_id, region_id, frequency_id, period_start/end, value,
assessment_type, observation_status, source_id, release_id, quality_flags,
sub_dimension, notes). Справочники core.unit, core.region, core.source.
Полный объём: ~2 400 метрик, 692 месячных, 1 108 квартальных, 640 годовых.

Бенчмарки практик (используй как требования, не копируй): FRED —
машиночитаемые фацеты (гео/источник/частота/сезонность/лицензия/релизы)
с честными счётчиками; ловушка FRED: два ряда с одним названием
(уровень vs темп роста) — поэтому обязательны поля measure (level/
growth_rate/index) и unit normalization. DBnomics — 3 идентификатора +
dimension map, декодирующий код ряда в фильтр, а не строковая хирургия;
сохранение исходных кодов провайдера. World Bank Metadata Editor —
связи рядов: is_part_of / has_disaggregation / derived_from. Практики
слойed-модели: entity (стабильный ключ + ISO-коды + история переименований)
/ series (источник, частота, методология, правила нормировки) /
observation (series_key, entity_key, ts, value, quality flags, load meta).

Правила жёсткие:
- Ничего не удалять и не переписывать в core; все предложения — в
  proposal-слой (таблицы derived.catalog_proposal) с run_id.
- Каждый вывод — с проверяемым артефактом (SQL-вывод, CSV, отчёт).
- Останов и вопрос владельцу при: конфликте методологий, неясности
  принадлежности, разрушительной операции, превышении лимита.
- Формат ответа: JSON по схеме из задачи; незавершённый ответ = сбой.
- Проверяемость: количество записей сверяется с БД; пропуски не скрывать.

Выполни задачу этапа и верни JSON: {stage_status, artifacts[], metrics{},
open_questions[], next_stage_recommendation}.

## ЭТАПЫ (каждый — отдельный run_id, коммит, контрольная точка)

### Этап 0. Точка возврата (без модели)
pg_dump -Fc research_wiki → бакет wiki-research, backups/catalog/<run_id>/;
проверка восстановления в тестовую БД; manifest (пути, хеши, commit).
Приёмка: путь точки возврата сообщён владельцу.

### Этап 1. Инвентаризация (детерминированная, SQL/Python)
Полный каталог сущ. рядов: метрика × частота × разрезы × единица ×
периоды × источник × качество (пропуски, плейсхолдеры, дубли, конфликты
уровень/темп, накопление vs период). Статусы-кандидаты: основной /
дополнительный / архив / карантин / заменённый. Дубликаты точные — по
хешу рядов значений; семантические — флагом на LLM-этап. Связи: вывод
кандидатов is_part_of (общий префикс/источник), derived_from (formula_text),
replaces (статус). Артефакты: CSV/JSON каталога, manifest, отчёт сверок.
Приёмка: каждый показатель имеет запись или явную причину отсутствия;
count сверен с БД.

### Этап 1.5. Консолидация дублей БЕЗ потери знания (принцип владельца, 21.09)
Дубли — это одно явление в разных источниках (например, ИКВ из КЭП
Росстата и из ЕМИСС). Удаление запрещено. Вместо удаления:
- каноническая метрика (основной источник) + поле provenance: массив
  source_ids всех рядов, дублирующих явление;
- таблица derived.metric_crosswalk: metric_id дубля → canonical_id,
  связь (exact/semantic/manual), дата консолидации, run_id;
- исходные метрики НЕ удаляются: статус replaced_by + наблюдения
  остаются; выборка «по явлению» идёт через канонический id, история
  источника сохраняется;
- сверка значений дублей на пересечении периодов: расхождения >5% —
флаг conflicts_with (не молча выбрать один).
Приёмка: каждый дубль разрешим в канон через crosswalk; ни одна строка
observation не удалена (счётчик строк БД неизменен); знание «в каких
ещё источниках есть показатель» сохранено в provenance.
Урок (этап 1, 21.09): хеш-сверка валидна только при глубине n≥12 — на
1–2 точках ложные совпадения массовые (192 псевдодубля vm* vs vmns*
«ввод мощностей»/«новое строительство» — разные явления, значения
пока совпали). Псевдодубли фиксируются в crosswalk с link_type=
'pseudo_short_window', не консолидируются.

### Этап 2. Эталонная модель каталога (дизайн, мало модели)
Схема v1 на основе бенчмарков: фацеты (geo, source, frequency,
seasonality, measure, unit_canonical, domain, license, release), связи
(is_part_of, has_disaggregation, derived_from, replaces, conflicts_with),
качество (gaps, placeholder_pct, revision_lag), применяемость (к какой
исследовательской задаче: nowcasting СМР/ИКВ, трансмиссия ДКП, hedonic,
финансовое здоровье застройщиков). unit_canonical — справочник нормировки
(тыс руб → млрд, уровень → yoy, квартал → средне-месячная). DDL proposal-
слоя. Приёмка: DDL применён в тестовой БД, ERD-описание в протоколе.

### Этап 3. Семантическая разметка (модель, evidence-обязателен)
Evidence-пакет на метрику: шапка источника + методология + 5 крайних
значений. Правила → модель gpt-oss:120b (Medium) с JSON Schema ответа.
Кэш по хешу evidence+prompt+schema+model. Эскалация: неоднозначные →
вручную (дорогие модели только вручную). 10% случайной выборки уверенных
— на контроль. Приёмка: доля unknown < порога пилота; критические поля
(частота/единица/measure) верны на проверочной выборке.

### Этап 4. Наполнение и сшивка связей (код + контроль)
Автосшивка связей по правилам + подтверждение модели для спорных;
построение доменного дерева (строительство/жильё/ДКП/макро/регионы/
фирмы); фацетные счётчики. Проверки: уникальность id, ссылки целостны,
циклы в derived_from отсутствуют. Приёмка: граф связей без циклов,
счётчики фацетов сходятся с каталогом.

### Этап 5. Контроль качества и ревизия (роль контролёра)
Независимый ревизор (модель без доступа к ответам разметчика) на случайной
выборке 10% + все целевые ряды. Сверка с первоисточниками (паспорта
метрик). Отчёт: ошибки по классам, систематичность, карантин семейств.
Приёмка: критических ошибок 0 на выборке; спорные — в карантин.

### Этап 6. Применение (после явного утверждения владельца)
Diff-отчёт, git-тег, before-image; транзакционное переключение витрины;
идемпотентность; откат по run_id. Приёмка: чтение изменённых записей,
сверка счётчиков, второй прогон идемпотентен.

### Этап 7. Витрина и регламент обновления
Каталог-карточки (определение, источник/ячейка, версии, качество,
трансформации, применимость), API-фацеты, регламент: новые наблюдения при
той же методологии — без ИИ; изменение шапки/методологии — только
затронутое семейство; релизный контроль.

проверяет до доклада.

## Экономика
Кэш по хешу evidence+prompt+schema+model; контрольные точки после каждого
семейства; журнал расходов; остановка при 401/403. Upper-bound бюджет
утверждается владельцем до этапа 3. Повторы ограниченные; после сбоя —
продолжение с чекпоинта, не всего корпуса.

1. Хеш-сверка рядов значений находит ≥90% точных дублей без модели.

   правилами на ≥80% метрик; остальное — LLM с evidence.

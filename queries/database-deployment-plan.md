# Постановка на развёртывание единой БД в YC и миграцию

Реализация [[queries/database-architecture]] после закрытия всех восьми вопросов
и построения [[queries/regions-reference]].

## Назначение

Развернуть целевую базу на YC-ВМ, перенести шесть существующих SQLite-баз в
PostgreSQL, обеспечить работу 27 скриптов-потребителей без падений, демонтировать
GCS.

## Критическое ограничение канала

**SSH с зарубежного VDS на YC-ВМ недоступен** — проверено 16.09: порт 22
открыт из России (СПб, 35 мс), но блокируется для Германии и США. Значит прямой
перенос «VDS → YC по SSH» невозможен.

Обходной путь: **обмен через S3-бакет `agent-vm-exchange`**. Проверено
17.09.2026 полностью: с VDS работают и чтение (`list-objects`, `get-object`),
и запись (`put-object` — etag совпал при обратном чтении), и `head-object`.
Канал VDS ↔ YC через S3 действует, дополнительных мер не требуется.

Схема доставки: SQLite-базы → (S3 PUT с VDS) → бакет → (S3 GET на YC-ВМ) →
PostgreSQL. Промежуточные дампы могут не понадобиться, если миграция читает
SQLite напрямую из бакета.

## Фазы

### Ф0. Подготовка канала — ВЫПОЛНЕНО 17.09.2026

**Вход:** доступ к VDS и YC CLI.
**Действия:** проверены PUT и GET тестового объекта в `agent-vm-exchange`.
**Результат:** чтение, запись, head — все работают; etag совпал при обратном
чтении. Обмен VDS ↔ YC через S3 подтверждён.
**Критерий успеха:** достигнут.

### Ф1. Развёртывание ВМ

**Вход:** подтверждённый канал.
**Действия:**
```
yc compute instance create \
  --name research-db \
  --zone ru-central1-b \
  --network-interface subnet-id=e2lihlksrvl26ukhrcef,security-group-ids=enpeaib2jcgjfab3hg63,nat-ip-version=ipv4 \
  --create-boot-disk image-id=fd8nj6iro13qffg31not,size=60,type=network-ssd \
  --cores 4 --core-fraction 20 --memory 8 \
  --metadata-from-file ssh-keys=<ключ> \
  --service-account-id ajeevb50ninggg9d8cnu
```
без `--preemptible` (постоянная).

**Выход:** ВМ в статусе RUNNING, SSH доступен из РФ.
**Проверка:** SSH-вход, `nproc`=4, `free -m`≈8 ГБ, `df -h` / =60 ГБ SSD.
**Критерий успеха:** ресурсы соответствуют, SSH работает.

### Ф2. PostgreSQL и справочники

**Вход:** работающая ВМ.
**Действия:** установить PostgreSQL 15+, применить DDL из §2 архитектуры
(18 таблиц, схемы `core`/`meta`/`derived`/`marts`), загрузить справочники
(`unit`, `frequency`, `source`, `region` — 102 записи из
`data/regions_canonical.csv`).
**Выход:** пустая БД с полной схемой и справочниками.
**Проверка:** DDL применён без ошибок; `SELECT count(*) FROM core.region` = 102;
проверка иерархии — сумма детей ЮФО включает 4 новых территории; агрегаты
сходятся с `aggregate_of`.
**Критерий успеха:** схема и справочники загружены, иерархия корректна.

### Ф3. Миграция данных

**Вход:** БД со схемой, SQLite-файлы в бакете.
**Действия:** для каждой из шести баз — скрипт `migrate_<db>.py`: чтение SQLite →
маппинг через `region_aliases.csv` и `source_metric_mapping` → staging →
валидация качества → core. Порядок: `developers_ifrs` (512 стр., обкатка) →
`rosreestr_deals` → `cbr_lending` → `regions_panel` → `fns_tochno_sectors` →
`rosstat_construction`.

Особые случаи, требующие обработки при миграции:
- вариант «с АО» и «без АО» — разные коды (`arkhangelsk_nao` / `arkhangelsk`),
  агрегаты помечены `with_ao_included`;
- `row_label` → колонка `sub_dimension` (подразрез);
- 387 строк `row_label_stacked` в Росреестре — расщепить на три колонки;
- `Не продано (продажи открыты)` и подобные — в `sub_dimension`, не в регион.

**Выход:** данные в `core.observation`.
**Проверка на каждой базе:** `COUNT(*)` core == COUNT SQLite (минус
`rejected` с обоснованием); сверка суммы `value` по ключу; выборочный
аналитический запрос возвращает те же цифры.
**Критерий успеха:** все шесть баз перенесены, расхождений нет.

### Ф4. Совместимость скриптов

**Вход:** данные в PostgreSQL.
**Действия:** модуль `db_compat.py` (прокси `sqlite3.connect` → `psycopg`);
представления-двойники с именами старых таблиц; переключение 27 скриптов.
**Выход:** скрипты читают PostgreSQL.
**Проверка:** запуск всех 27 скриптов; критерий приёмки 3 архитектуры.
**Критерий успеха:** ни один скрипт не упал.

### Ф5. Демонтаж GCS

**Вход:** скрипты на PostgreSQL.
**Действия:** перенести 3.5 ГБ из GCS в YC Object Storage; заменить
gcsfuse-монтирование `raw/` (rclone mount к S3 YC); удалить `gcs_sync.py`
и ссылки на `gs://`.
**Выход:** нет зависимостей от GCS.
**Проверка:** `grep -rE 'gs://|gsutil|gcsfuse'` по коду и конфигам — пусто;
`raw/` доступен через новый механизм.
**Критерий успеха:** критерий приёмки 4 архитектуры.

### Ф6. Бэкапы с фактической проверкой

**Вход:** работающая база.
**Действия:** ночной `pg_dump` в S3-бакет YC; восстановление во временную базу
с diff счётчиков.
**Выход:** автоматические бэкапы + подтверждённое восстановление.
**Проверка:** критерий приёмки 5 архитектуры — восстановление проверено
фактически, а не заявлено.
**Критерий успеха:** восстановление прошло, счётчики совпали.

## Критерии приёмки (из архитектуры)

1. Аналитический режим: оценки двух и более источников за период видны с датами.
2. Исследовательский режим: срез «на дату T», длинный ряд без разрывов.
3. Ни один из 27 скриптов не падает.
4. Каталог = физическая реальность.
5. Восстановление из бэкапа проверено фактически.

## Риски

- ~~S3 PUT с VDS недоступен~~ → снято: проверено 17.09, запись работает.
- **Расхождение COUNT** при миграции широких таблиц (ЦБ, ДОМ.РФ) → staging
  позволит переобработать без повторной загрузки.
- **Память при разборе**: pandas на Росстате пиково ~2 ГБ; 8 ГБ RAM даёт запас.
- **Постоянная ВМ вместо прерываемой** — рост расхода с ~330 до ~4 300 ₽/мес,
  согласовано владельцем.

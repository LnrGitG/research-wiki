# Концепция хранения среза ФНС в v2 (агрегаты по регионам, без разреза по организациям)

**Дата:** 2026-09-21. **Статус:** на утверждение.
**Контекст:** ВМ не имеет микроданных по организациям (bo.nalog по ИНН — отдельный
трек); ФНС публикует готовые агрегаты «в разрезе субъектов РФ» quarterly.

## 1. Источник и формат

- Страницы форм: nalog.gov.ru/…/forms/ (1-НОМ, 1-НДС, 4-НОМ, 5-НИО и др.).
- Файлы прямые xlsx: `<форма><дата>.xlsx` (РФ) и `<форма><дата>reg.xlsx`
  (разрез субъектов) — доступны с VPS без капчи (проверено).
- Reg-файл 1-НОМ: 89 листов = строки формы (1010=ВСЕГО, 1015=в т.ч. …,
  1513); внутри листа: РФ → ФО → 85 субъектов; колонки = показатели
  (начислено, поступило, по видам налогов: прибыль, НДФЛ, …).
- Квартальная частота: снапшоты 01.01/01.04/01.07/01.10 (кроме НДФЛ —
  приостановлено распоряжением Правительства №1074-р до 01.04.2027).
- v1-таблицы (fns_1nom_okved_f_quarterly и др.) — старые снапшоты
  2018–2025, сшивка по (форма, строка, показатель, регион).

## 2. Концепция: одна метрика = (форма × строка формы × показатель)

Не разносить листы по отдельным метрикам (89 листов × 20 колонок = тысячи
метрик — шум, который мы убрали при перезагрузке). Вместо этого:

- **v2.metric — по одному на (форма, показатель)**: fns_1nom_receipts_total,
  fns_1nom_profit_tax, fns_1nom_ndfl, fns_1nds_accrued, fns_4nom_…
  Целевое ядро: **6–10 метрик** (поступления всего, прибыль, НДФЛ, НДС,
  имущественные), не всё дерево формы.
- **Строка формы (уровень детализации) → native_key** в staging: парсер
  «тупой и быстрый» складывает ВСЁ (лист × строка × колонка × регион), а
  селекция листов — в YAML-карточке (selective) — как с ЕМИСС 34118.
- **Разрез ОКВЭД**: строки 1015+ — в staging, в ядро только раздел F
  (строительство, F41/F42/F43) — это тот же принцип, что 1-НОМ по ОКВЭД в v1
  (G53_okved_F). Стройка-специфика: поступления по разделу F — прямой
  финансовый индикатор СМР.

## 3. Идентификация региона и иерархии

- РФ-строка — агрегат по отфильтрованным ФО (не суммировать с субъектами).
- ФО-строки: в v2 хранить (region_id ФО — уже есть в v2.region) — для
  пространственных панелей.
- Субъекты: резолвер по v2.region (алиасы: «Республика Саха (Якутия)»,
  «г. Москва» и т.д.) — карта уже отработана на ЦБ/ДОМ.РФ.
- **Квартальная дата**: снапшот-дата (01.01.2026) → date = квартал
  (2026-01-01), freq_id=3 (v2-конвенция «кварт»), значение — нарастающим
  итогом с начала года (как в ЦБ-Т-серии). Метки saar не делаем.

## 4. Staging-схема

```
v2_stage.fns_rows (
  run_id, snapshot_date, form_code, sheet_code,   -- '1-НОМ', '1010'
  region_raw, level_code,                         -- RF/FO/subject
  col_code, col_name,                             -- '5', 'налог на прибыль…'
  value_num, native_code)
```
- Универсальная: одна на все формы (1-НОМ, 1-НДС, 4-НОМ…).
- Верификация: РФ = Σ ФО (снапшот за квартал) — уже проверенная схема
  (ЕМИСС 34118: РФ-агрегат = сумма субъектов).
- Селекция в ядро: через metric_dataset_map + YAML-карточку (allowlist).

## 5. Приёмка

1. Снапшот 01.01.2026 (1-НОМ): РФ по 1010 = Σ 8 ФО ±0.1%.
2. Сшивка с v1 (fns_1nom_okved_f_quarterly, Белгород 01.01.2025 —
   4 997 506 vs 3 997 506 — пересчёт при переносе).
3. Пропуски: у ФНС встречаются скрытые значения (звёздочки/прочерки) —
   null, не 0.
4. Freshness: квартальные, лаг ~2.5 мес (публикация 16.03 за 01.01).
5. v2 totals: +6–10 метрик, ~20–35 тыс. obs (8 ФО+85 рег × 6 метрик × 30
   кварталов) — Г2 (<500К) остаётся в бюджете.

## 6. Не-цели

- Не грузить все 89 листов в ядро (только staging).
- Не тянуть разрез ОКВЭД по всем видам деятельности — только раздел F.
- Не делать nowcasting-метки (saar/szn) — только факты.
- Микроданные bo.nalog (ИНН-панель) — отдельный трек developer health.

# Схема БД для решений по ключевой ставке (dkp) — дизайн-заметка

Дата: 2026-09-23. Статус: **предложение** (DDL в `scripts/cbr_decision_ddl.sql`,
в БД не применён). БД: research_wiki (PostgreSQL 16.15 + pgvector 0.6.0, ВМ YC
research-db, доступ scripts/db_tunnel.py, порт 15432 с VPS).

## Постановка

Хранить решения Банка России по ключевой ставке (значение, изменение,
решение СД, заявление Председателя, резюме, среднесрочный прогноз 4 раза в
год) так, чтобы:

- анализировать **эффективность ДКП** (прогноз vs факт, трансмиссия,
  предсказуемость траектории);
- при подготовке очередного решения иметь **весь исторический ряд
  предпосылок и аргументов** Банка России с поиском по смыслу.

## Что уже есть в БД (проверено запросами 2026-09-23)

- `core.release` (81 строка), `core.document` (пустая — структура готова:
  doc_code, title_ru, doc_type, url, sha256), `core.file_registry` (sha256),
  `core.note` (пустая, polymorphic FK на metric/region/hypothesis/doc/obs);
- `v2.observation` с `run_id` + `is_current` (ревизионно-осведомлённые
  наблюдения), `v2.load_run/load_check` (file_sha256, parser_version),
  `v2.series_revision` (автодетект ревизий), `v2.source` cbr = id 2;
- `v2.metric` metric_code `key_rate` = metric_id 37, наблюдений 0 — пустой
  слот под дневную ключевую ставку;
- `core.hypothesis` (пустая), `core.paper_card` (314), pgvector 0.6.0 +
  Yandex-эмбеддинги 256-dim (scripts/build_yandex_embeddings.py);
- роль wiki: CREATE и на БД, и на core.

## Дизайн: 8 таблиц в схеме dkp

1. **dkp.meeting** — календарь: 8 плановых заседаний в год, из них 4
   опорных (`is_pillar`), внеочередные (`decision_kind='unscheduled'`).
   Уникальность (date, kind). Источник ленты: cbr.ru/dkp/mp_dec/.
2. **dkp.decision** — решение: rate_prev/rate_new numeric(6,2),
   сгенерированный столбец delta_bp, action cut/hold/hike, headline_ru
   (формулировка), signal_note (сопроводительный сигнал), FK на
   core.document (пресс-релиз как документ). Политика единого голоса —
   ровно одно решение на заседание (UNIQUE meeting_id).
3. **dkp.rate_level** — решётка операционных ставок **ступенями**:
   (rate_code, effective_from, effective_to). Коды: ключевая, ПВР/СПВР,
   аукционы/фикс РЕПО, ИКР, НКР, ломбардные, депозитные, СКС. Вьюха
   разворачивает в дневной ряд (`gap-fill` за минуты). Уровень, введённый
   решением, связан FK с decision — виден эффект каждого решения.
4. **dkp.argument** — атомарные аргументы из пресс-релизов/конференций/
   резюме обсуждения: block (рубрикатор v1: inflation_now, inflation_expect,
   demand, labour, wages, fx, credit, budget_rule, fiscal, external, oil,
   transmission, signal, rationale, dissent…), direction hawkish/neutral/
   dovish, text_raw, source_span, **embedding vector(256)** (Yandex, как в
   вики-стеке) с HNSW-индексом, classifier_version ('manual' | 'llm:<model>').
   Это ядро «ряда предпосылок»: каждое новое решение можно сверять со всеми
   прошлыми по смысловому поиску, а не только по рубрикам.
5. **dkp.statement** — заявления Председателя (пресс-конференции привязаны
   к meeting_id, прочие — свободные), body + embedding.
6. **dkp.minutes** — Резюме обсуждения (с 02.2024): источник для разброса
   мнений СД; аргументы сторон попадают в dkp.argument.
7. **dkp.forecast** — среднесрочный прогноз к опорным заседаниям: длинный
   формат (meeting_id, scenario, series_code, horizon_year, low/high/point,
   unit_code, run_id). Словарь series_code v1: inflation_dec, inflation_avg,
   key_rate_avg, gdp_yoy, gdp_q4q4, cons_hh, gross_capital (ВНОК), M2,
   требования банков, ипотека, платёжный баланс, нефть для
   налогообложения. Диапазон «6,0–7,0» → low/high; точка «4,0» → point.
8. **dkp.forecast_realized** — фактические значения тех же серий по годам
   **со срезами as_of** (ревизии Росстата/ЦБ хранятся все, не затираются).

## Почему так (ключевые решения)

- **Ступенчатое хранение ставок** (rate_level), а не дневные строки: нет
  6 тыс. дублированных значений, даты ввода уровней связаны с решениями,
  дневной ряд достраивается вьюхой. Слот v2.metric key_rate (id 37)
  остаётся под дневную производную — заполняется из rate_level.
- **Аргументы — отдельная сущность, а не тексты**: только атомарный разбор
  даёт (а) тональные ряды hawkish/dovish по блокам, (б) смену повестки
  между раундами, (в) семантический поиск прецедентов («когда ЦБ в
  последний раз аргументировал паузу слабым рублём»). Текстовые тела
  документов остаются в core.document; dkp хранит разборы.
- **Прогноз в длинном формате** с run_id: любое изменение таблицы — это
  новый load_run со sha256 файла; прошлые раунды никогда не перезаписываются.
- **Ревизии факта через as_of**: ошибка прогноза считается против
  актуального среза, а история ошибок — против исторических (важно для
  честных RMSFE, как в NBP №87: p_C(y*|y) = p_S(y|y*)·p_E(y*)/p_C(y)).

## Сценарии использования агентом

1. **Контекст очередного решения** (v_decision_context): последние уровни
   ставок + последний среднесрочный прогноз + аргументы последних
   раундов + семантический поиск по embedding прецедентов.
2. **Эффективность ДКП**: v_forecast_error → hit_range и err_point по
   сериям и раундам; накопление фактов для core.hypothesis (H1
   «экспертные поправки к модельному прогнозу»: систематический дрейф
   точечных прогнозов от модельных расчётов).
3. **Трансмиссия**: rate_level (дневная решётка) join v2.observation
   (кредитование, депозиты, инфляция, спрос) — IRF-стиль сравнения.
4. **Предсказуемость**: err_point по key_rate_avg против рыночных
   ожиданий (когда появится источник — ОФЗ/РУОНИА).

## Загрузка (пайплайн)

- Каждая загрузка = v2.load_run (sha256 файла-источника, parser_version) →
  v2.load_check → строки dkp.forecast/decision. Пресс-релиз регистрируется
  в core.file_registry + core.document (doc_code = 'cbr_press_release_YYYYMMDD').
- Дедупликация по sha256 в file_registry. Статус: 'raw'|'parsed'|'verified'.
- Расписание: после каждого решения (8/год) и после каждой публикации
  среднесрочного прогноза (4/год); внеочередные — вручную.

## Открытые вопросы

- Официальный CSV/эксель-источник истории ключевой ставки (cbr.ru/hd_base)
  против ручной сборки из ленты решений — проверить экспорт hd_base.
- Разметка аргументов: ручная для исторического ряда (2013–2024, ~120
  решений) или LLM с последующей выборочной проверкой (classifier_version
  фиксирует метод) — предложить гибрид: LLM-черновик + ручная проверка
  решений с разворотом тренда.
- Эмбеддинги: Yandex 256-dim (уже в стеке) или локальная модель —
  пока Yandex для единообразия с вики-стеком.

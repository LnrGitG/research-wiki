# Обзор контекста Hermes-2 и дальнейшие шаги (30.10.2026)

## Что фактически работает на WSL Hermes-2

- Hermes Agent v0.19.0, профиль один — `dbops`; шлюз, обратный тоннель Metabase
  (`13000 → localhost:3000`) и peer-тоннель живут как systemd --user юниты,
  все `active running`.
- Две инсталляции Metabase: прод на `localhost:3000` (v0.64.3.5, `/api/health`
  = 200), dev на `localhost:3001`.
- MCP-серверы в профиле `dbops`: `research-db`, `metabase-dev`,
  `metabase-prod` (21 инструмент).
- Диск ноутбука свободен (948 ГБ), память 9,9 ГБ, занято 4,8.

## Незакрытые линии в контексте Hermes-2

1. **msync — git-синхронизация контента.** Remote Sync в OSS недоступен
   (`/api/ee/remote-sync` → 404), поэтому написан свой движок
   `~/metabase-sync/msync.py` (export / import / status / apply / validate,
   идентичность по uid, карта uid→id в `state/<host>.json`). Проверен на dev:
   создание с нуля, конфликты по `updated_at`, `--prune`, `validate`.
   Рабочий репозиторий `~/metabase-content-work` на ветке
   `feature/metric-freshness-dashboard`, в нём пока только демо-коллекция
   `agent-demo` (6 объектов). Origin — **локальный bare-репозиторий**
   `~/metabase-content.git`, не GitHub, поэтому CI-гейт из README не работает.
2. **Права.** Коллекционная изоляция не действует, пока `All Users` имеет write
   на root; scoped-ключ упирается в отсутствие админ-прав. Это решение
   владельца, не техническое.
3. **Подписанные определения.** 17 кодов получили `status=official`,
   `approved_by=owner`; применено на проде (77 строк `catalog.metric_definition`,
   из них 49 текущих). `verified_at` пуст до фазы сверки с первоисточником.

## Найденный дефект данных (важнее остального)

`data.observation` содержит настоящие дубли: один регион-месяц записан двумя
релизами с одинаковым значением. Пример — `cbr_izhk_debt_m`: 15 288 строк на
7 728 точек (ровно вдвое), значения в парах идентичны (`altai_rep`,
2019-03: 3880 и 3880). Затронуты `cbr_izhk_count_m`, `_ddu_volume_m`,
`_debt_m`, `_rate_m`, `_volume_m`, `_term_m`.

Следствия:
- **средние** (ставка, задолженность на регион, ИФО-медиана) не искажены;
- **суммы** удвоены — в семантическом слое это метрики «Выдачи ИЖК по регионам»
  и «Реализация квартир по регионам»; проверено на Алтае: 743,0 млн руб. на
  дублях против 371,5 млн руб. на дедуплицированных данных;
- национальные значения верны (на уровне страны одна строка: задолженность
  сентябрь 2026 = 21 881 863 млн руб.).

Попытка дедуплицировать широкую витрину через `DISTINCT ON` уронила ВМ в
`DiskFull`: сортировка 7,8 млн широких строк не помещается в 1,4 ГБ свободных.
Витрина откачена к исходному определению, диск в норме (85 %).

Решение, которое работает: узкая дедуплицирующая вью
`derived.v_bi_dedup` (7 колонок вместо 29 400 — только ключ, значение, релиз).
Создана, грант `metabase_ro` выдан, время отклика 0,6–0,7 с на индикатор,
потому что фильтр по `metric_code` применяется до сортировки.

## Предлагаемые шаги

1. **Перевести 17 метрик на `derived.v_bi_dedup`** (schema sync Metabase,
   смена `source-table`, повторная сверка чисел). Региональные суммы при этом
   уменьшатся ровно вдвое — это и есть признак исправления.
2. **Убрать причину, а не следствие:** разобраться, почему два релиза пишут
   одни и те же точки (второй писатель у `cbr_izhk_*`), и либо дедуплицировать
   на инжесте, либо удалить дубли из `data.observation` после дампа.
3. **Экспортировать семантический слой в msync-репозиторий** (17 метрик,
   3 сегмента, дашборд 7), собрать PR и перевести origin на GitHub, иначе
   CI-гейт из README не существует.
4. **Решить про права:** сузить `All Users` на root (нужно слово владельца) —
   без этого коллекционная изоляция фиктивна.
5. **Диск ВМ:** 1,4 ГБ свободно при квоте 10 ГБ. Материализованные вью и
   тяжёлые сортировки недоступны, пока квота не расширена.

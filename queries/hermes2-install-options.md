# Способы установки Hermes на ВМ YC: копирование папки против клонирования

Записка 19.09.2026. Разбор двух предложенных вариантов — скопировать папку
`hermes-agent` с VPS либо клонировать дистрибутив с официального GitHub и
начать настройку. Все утверждения проверены командами на VPS и на ВМ YC.

## Главное препятствие, общее для обоих вариантов

**Стандартная однострочная установка с ВМ YC не работает.** Проверено:

```
$ curl -fsSL https://hermes-agent.nousresearch.com/install.sh
HTTP/2 403
server: Vercel
x-vercel-mitigated: deny
```

Отказ приходит по-разному в зависимости от заголовков, но `x-vercel-mitigated: deny`
не оставляет сомнений: адрес заблокирован для датацентровых адресов YC. Это
тот же класс ограничения, что и блокировка Telegram. Значит, привычная команда
`curl ... | bash` на этой машине неприменима, и оба варианта нужно строить в
обход.

**Что при этом доступно с ВМ YC:**

| Ресурс | Результат |
|---|---|
| `github.com` | 200 OK |
| Клон `NousResearch/hermes-agent` | **успешно, 284 МБ** |
| `raw.githubusercontent.com` | 200 OK, `scripts/install.sh` читается |
| `astral.sh/uv/install.sh` | 200 OK, 71 308 байт |
| `nodejs.org/dist/index.json` | 200 OK |
| `files.pythonhosted.org` (пакет) | 200 OK, 99 109 байт |
| `hermes-agent.nousresearch.com` | **403 — заблокирован** |

Вывод: **GitHub доступен, официальный домен установщика — нет.** Из этого
следует всё остальное.

## Вариант 1: копирование папки — не работает, и это проверяемый факт

На первый взгляд копирование выглядит проще. Фактически оно ломается по
четырём причинам, каждая из которых достаточна.

**Первая: виртуальное окружение не портируется.** Каталог `venv` — 2,7 ГБ, и
в нём 85 исполняемых файлов с **жёстко прописанным путём** `/home/lnr`:

```
$ head -1 venv/bin/pip
#!/home/lnr/.hermes/hermes-agent/venv/bin/python3
$ grep -rl '/home/lnr' venv/bin/ | wc -l
85
```

Виртуальное окружение Python содержит абсолютные пути к своему интерпретатору
в заголовках скриптов. Пользователя `lnr` на ВМ **нет** — там `ubuntu`. То
есть после копирования эти 85 файлов указывают в никуда. Пришлось бы
пересоздавать окружение, а это ровно та работа, которую копирование
якобы экономит.

**Вторая: интерпретатор живёт вне копируемой папки.** `pyvenv.cfg` указывает
на `~/.local/share/uv/python/cpython-3.11-linux-x86_64-gnu/bin` — Python,
управляемый `uv`, отдельно от системного. На ВМ системный Python 3.12.3,
дистрибутив Ubuntu, и он не подходит: в `pyproject.toml` записано
`requires-python = ">=3.11,<3.14"`, но само окружение собрано под 3.11.
Копирование папки агента этот интерпретатор не приносит — он лежит в
`~/.local/share/uv`, то есть в стороне.

**Третья: папка `hermes-agent` — это не весь Hermes.** Рядом, вне её:

- `~/.hermes/config.yaml` (5 980 б) — профили, curator, модель;
- `~/.hermes/SOUL.md` (4 322 б);
- `~/.hermes/.env` (25 922 б) — все ключи доступа;
- `~/.hermes/skills/` (104 МБ) — 130 навыков;
- `~/.hermes/profiles/` (143 МБ) — профили `personal` и `legal`;
- `~/.local/bin/hermes` — обёртка, запускающая venv;
- `~/.local/share/uv/` (98 МБ) — сам интерпретатор.

Копирование одной папки даёт **код без окружения, без конфигурации и без
интерпретатора** — неработоспособный набор файлов.

**Четвёртая: секреты поехали бы копированием вслепую.** В `.env` лежат
S3-ключ YC, ключ GCP, ключ Gemini, токен Telegram, пароль `datalens_ro`,
пароль sudo. Копировать их на новую машину нужно осознанно и по списку, а не
в составе каталога. Отдельно: у профилей `personal` и `legal` своя история в
`state.db` — на рабочий профиль она не нужна.

**Единственное, в чём копирование выигрывает:** обход блокировки 403.
Локальная передача по SSH не касается внешних доменов. Но и у этого выигрыша
есть более простой ответ — см. вариант 2.

## Вариант 2: клонирование — работает, но не через однострочник

Проверено прямо на ВМ: `git clone --depth 1 https://github.com/NousResearch/hermes-agent.git`
проходит успешно, 284 МБ, и **внутри клона есть `scripts/install.sh`** — тот
самый установщик, что отдаётся по заблокированному домену.

Отсюда рабочий порядок:

```
git clone --depth 1 https://github.com/NousResearch/hermes-agent.git ~/.hermes/hermes-agent
cd ~/.hermes/hermes-agent
./scripts/install.sh
```

Это **официальный путь, а не обходной**: `scripts/install.sh` и есть источник
того, что публикуется на домене. Установщик сам скачает `uv` с `astral.sh`
(доступен, 200), сам поставит нужный Python (в границах `>=3.11,<3.14`) и
`nodejs` с `nodejs.org` (доступен). Системный Node на ВМ отсутствует — в
`apt` только 18.19.1, но установщик ставит свою сборку, так что это не
препятствие.

**Проверенные требования на ВМ выполнены:**

| Требование | Состояние на ВМ |
|---|---|
| `git` | 2.43.0 — есть |
| Python | 3.12.3 системный, установщик поставит нужный |
| `sudo` без пароля у `ubuntu` | **есть** |
| Свободное место | 48 ГБ (код 202 МБ без `.git` и `venv`) |
| GitHub | доступен |

**Важное преимущество, которого лишён вариант 1:** клон — это git-репозиторий,
значит `hermes update` работает штатно. При копировании папки без `.git`
обновление придётся делать тем же копированием, каждый раз вручную.

**На что обратить внимание при запуске:**

- Установщик интерактивен (мастер настройки). Флаги для неинтерактивного
  режима: `--skip-setup` (пропустить мастер), `--no-skills` (не сеять
  встроенные навыки — нам нужен свой набор), `--dir PATH` (каталог
  установки), `--hermes-home PATH`.
- `--ensure` позволяет дозаложить зависимости, не пересобирая всё.
- Установщик отказывается работать с существующим каталогом, который не
  является git-репозиторием: «Directory exists but is not a git repository.
  Remove it or choose a different directory with --dir». Это подтверждает, что
  смешивать два варианта — копировать поверх клона — нельзя.
- На VPS в ядре агента **нет локальных правок** (`git status` чист по всем
  файлам, изменённых 0). Значит, клон даёт ровно тот же код, что работает
  сейчас, и расхождения между машинами не будет. На ветке `main`, коммит
  `205645ee424163c7b6cfc032c331c3557797497b`. Есть один autostash от
  `hermes update` от 13.09 — на новую машину его переносить не нужно.
- Версию агента на ВМ следует зафиксировать той же, что на VPS: две разные
  версии сломают `hermes peer`, которым машины будут связаны.

## Что переносить осознанно — это третий вариант, и он рабочий

Ни один из двух предложенных вариантов не даёт готовой к работе машины сам по
себе: копирование приносит лишнее и ломает окружение, клонирование даёт
голый агент. Верный путь — **клонирование плюс выборочный перенос
конфигурации**, где переносится не «всё», а по списку.

**Переносить:**

| Что | Откуда | Зачем |
|---|---|---|
| `AGENTS.md` (симлинк) | клон `hermes-shared` | общий слой: пути, инварианты, доступы |
| ключи в `.env` | VPS, по списку | S3, GCP, Gemini, провайдеры моделей |
| выбранные навыки | VPS, под профиль | только нужные `monitor`/`analyst` |
| `SOUL.md` | VPS | стиль и роль агента |

**Не переносить:**

- `state.db` разговорного профиля (592 МБ) — история VPS остаётся на VPS;
- профили `personal` и `legal` — личный контур, ему на рабочей ВМ не место;
- токен Telegram — на ВМ он бесполезен, домен заблокирован;
- `state-snapshots` (469 МБ) — снапшоты VPS.

**Ключевое правило по секретам.** Токен Telegram на ВМ **не переносить вовсе**:
он там неработоспособен (домен под блокировкой), а его наличие на лишней
машине — только риск. Ключи к данным (S3, GCP) и к моделям (Gemini,
провайдеры) переносить нужно — без них профили не соберут данные и не
задумаются.

## Стоимость передачи, если понадобится копировать

Канал VPS → ВМ замерен: 50 МБ по `scp` за 3,4 секунды, то есть около
**15 МБ/с**. Передача 200 МБ кода заняла бы около 15 секунд. Скорость не
является ограничением — ограничением является несовместимость `venv`.

## Где устанавливать

Отдельный вопрос, который за вами: **ВМ `hermes2` не существует.** В каталоге
YC одна машина — `research-db` (`epd1a9b94f8pskro2uh9`, 4×20% vCPU, 8 ГБ,
48 ГБ свободно), Hermes на ней не установлен. Два пути:

1. **Ставить на `research-db`.** Данные и агент в одном контуре, тоннель к
   PostgreSQL не нужен, платить за вторую машину не надо. Минус — 20%
   гарантированной доли vCPU: для cron-сбора и фоновых прогонов хватит, для
   интерактивной аналитики будет вяло.
2. **Создать отдельную `hermes2`.** Чище разделение, но плюс машина в счёте,
   плюс сетевые переходы между агентом и БД.

Моя рекомендация — **начать с `research-db`**: запас по памяти восьмикратный,
база данных занимает лишь 12 КБ каталога, а тоннель к ней уже работает. Если
вычислительная доля окажется узким местом, отдельную ВМ всегда можно поднять
позже, перенеся готовую конфигурацию.

## Итог

**Вариант 1 (копирование папки) — не рекомендую.** Он не переносит
виртуальное окружение (85 скриптов с путём `/home/lnr`, отсутствующий
пользователь), не переносит интерпретатор, не переносит конфигурацию, лежащую
вне папки, и тащит секреты вслепую. Даёт нерабочий набор файлов и требует
пересборки окружения — то есть выполняет ту работу, которую обещал сэкономить.

**Вариант 2 (клонирование) — рекомендую, с одной поправкой.** Не
`curl ... | bash` (домен отдаёт 403 с адресов YC), а клон с GitHub и запуск
`./scripts/install.sh` из клона. Добавить к нему осознанный перенос
конфигурации по списку выше. Это даёт работающий агент с рабочим
`hermes update`, точной версией и без лишнего.

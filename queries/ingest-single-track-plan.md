# Проект «Единый приёмный контур» (открыт 05.10.2026)

## Проблема

Приём данных идёт в два параллельных контура со старой и новой логикой:

- **Новый (канон):** `catalog.*` (справочники: source, metric, release, unit,
  region, frequency, topic, metric_alias, metric_topic, source_endpoint,
  metric_region_scope) + `data.observation` (канон-хранилище, 239 партиций).
  Образец правильного пути — `load_cbr_key_rate.py`: регистрирует метрику в
  каталог, создаёт релиз, пишет наблюдения, ведёт alias/topic.
- **Старый (дубль-контур):** `v2.*` — собственные копии справочников
  (v2.metric 150 метрик, v2.source 10, v2.dataset, v2.load_run, v2.load_check)
  плюс своя observation (428 112 строк). Семь loader'ов пишут туда и только
  туда: ingest_observation, parse_domrf_pi, parse_wordstat, parse_sberindex,
  parse_cbr_vfs, pipeline6, pipeline7 + пять dkp/load-скриптов.

Цена двойного контура: (а) 89 метрик из v2.metric отсутствуют в catalog.metric
СЕРЕЗНЫЕ из них — sber* (162 000 наблюдений) и domrf_* (203 934 наблюдений)
в v2.observation, в каноне их НОЛЬ — живые данные недоступны из канона;
(б) два журнала загрузок (v2.load_run и ops.ingest_rows_written=0);
(в) loader-знания разъезжаются.

## Целевая архитектура

Один приёмный контур: загрузчики пишут ТОЛЬКО в catalog + data (+ ops-журнал).
Лендинг-площадки (staging.* сырьё с парсеров) сохраняются как вход парсеров,
но их чистит 2А. Старые схемы v2/v2_stage/public остаются как есть (заморожены),
пока 2А/миграции их не почистят.

## Этапы

- [ ] **0. Инвентаризация расхождений справочников.** Сверить v2.metric (150)
      vs catalog.metric — 89 отсутствующих: какие из них живые (их наблюдения
      в v2.observation свежие) vs мёртвые (не нужны). Результат: список
      на регистрацию. Аналогично v2.source (10) vs catalog.source (11).
- [ ] **1. Регистрация недостающих метрик в catalog.** Перенос 89 (после
      отсева) в catalog.metric с привязкой source/frequency/unit/domain и
      tags. Здесь же релиз-выкладка их 365 934 наблюдений из v2.observation
      в data.observation (единый релиз «перенос v2 на дату»).
- [ ] **2. Общий модуль приёма.** scripts/ingest_common.py: функции
      ensure_metric, ensure_source, new_release, log_ingest_run (с ЧЕСТНЫМ
      подсчётом строк — починить нулевой rows_written ops-журнала).
- [ ] **3. Перевод loader'ов.** По одному: parse_sberindex, parse_domrf_pi,
      parse_wordstat, parse_cbr_vfs, pipeline6, pipeline7, ingest_observation,
      dkp/load-скрипты. Каждый: writes catalog+data, приёмка прогона
      (число строк против журнала), точка возврата git на каждый шаг.
      Порядок — от наименее живого к самому живому (интерактивно-используемые
      последними).
- [ ] **4. Приёмка миграции v2.observation → data.observation** (365 934
      sber/domrf строк; методика stepG-приёмки: ключи, счётчики, выборка
      значений, RI).
- [ ] **5. Заморозка v2-контpypa.** v2.observation → read-only (REVОKE
      INSERT/UPDATE/DELETE для роли wiki); v2_metric/load_run остаются
      историческими; представления-совместимости, если кто-то читает.
- [ ] **6. Передача площадок 2А.** После перевода loader'ов площадки
      domrf_indicators/fns_rows теряют смысл как вход (данные сырые идут в
      лендинг) — 2А чистит их по политике 90 суток.
- [ ] **7. Сводный доклад** в репозиторий (queries/ingest-single-track.md)
      с числами до/после.

## Инварианты

- Каждый шаг обратим (git + дамп перед записью в БД больше 100 тыс. строк).
- Параллельной записи нет: loader пишет либо в старый либо в новый контур,
  не в оба (без дублирования).
- Приёмка каждого переноса по методике migration_stepG (счётчики, ключи,
  выборки) — до сообщения об успехе.
- Секреты и доступ не расширяются.

# Проект «Единый приёмный контур» (открыт 05.10.2026, стратегия БАКЕТ)

> Ревизия 2 (05.10.2026, вечер): по предложению владельца стратегия изменена со
> «построчного переноса из v2» на «повторную пакетную загрузку из исходников».
> Основание: сырьё целиком лежит в бакете — rclone lsf yc-s3:wiki-research/raw/
> (1 526 файлов, 2,1 ГБ) и в sandbox_datasets ВМ (1,1 ГБ). Вместо выуживания
> наблюдений из старого контура loaders запускаются сырьём заново, но по
> новому пути (catalog + data + честный журнал); v2-данные остаются эталоном
> сверки, а не источником.

## Проблема

Приём данных идёт в два параллельных контура:

- **Новый (канон):** `catalog.*` + `data.observation` (239 партиций).
  Образец пути — `load_cbr_key_rate.py` (регистрирует метрику, создаёт релиз,
  пишет наблюдения, ведёт alias/topic).
- **Старый (дубль):** `v2.*` — свои справочники (v2.metric 150, v2.source 10)
  и своя observation (428 112 строк). Семь loader'ов + пять dkp/load-скриптов
  пишут только туда. 89 метрик v2.metric без канона, среди них живые:
  sber* (162 000 наблюдений) и domrf_* (203 934) — в каноне их ноль.

## Целевая архитектура

Один приёмный контур: loaders пишут только в catalog+data (+ops). staging.*
остаются лендингом сырых выгрузок; чистку площадок делает 2А (pg_staging_groom.py,
политика 90 суток). Старые схемы v2/v2_stage заморожены после перевода loaders
и отдаются 2А.

- Каждый шаг обратим (git; дамп перед записью >100 тыс. строк).

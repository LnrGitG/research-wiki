# JupyterLab на ВМ YC как песочница для ручной разведки данных

Записка 19.09.2026. Оценка решения развернуть JupyterLab на ВМ `research-db`
для ручной разведки данных. Все утверждения проверены запуском на самой ВМ.

## Проверено на практике, а не предположено

JupyterLab **установлен и запущен** на ВМ во время оценки:

```
$ uv pip install --python venv/bin/python3 jupyterlab
jupyterlab 4.6.3

$ jupyter lab --no-browser --port=8888 --ip=127.0.0.1 --ServerApp.token=probe123
LISTEN 127.0.0.1:8888
$ curl "http://127.0.0.1:8888/api/status?token=probe123"
{"connections": 0, "kernels": 0, "last_activity": "2026-09-19T14:15:58.722040Z"}   # HTTP 200
```

Потребление: **86 МБ RSS**, 13% CPU в простое, на диске 25 МБ. Без токена
сервер отдаёт 403 — аутентификация работает.

## Ресурсы: хватает с запасом

| Параметр | Значение | Комментарий |
|---|---|---|
| ОЗУ | 7 941 МБ, занято 944, **доступно 6 996** | песочница возьмёт ~500 МБ с данными |
| Диск | 58 ГБ, **свободно 45 ГБ** | библиотеки анализа ~1 ГБ |
| vCPU | 4 ядра по 20% | **но burst работает** — см. ниже |

**Про 20% vCPU — важное уточнение.** Проверил не по спецификации, а замером:
четыре потока по 6 секунд отработали за **6,2 секунды** (при жёстком
ограничении в 20% заняли бы около 24). Счётчики троттлинга нулевые:

```
nr_periods 0   nr_throttled 0   throttled_usec 0
```

То есть это burstable-конфигурация: гарантированная доля 20%, но фактически
ядро отдаётся целиком, пока не исчерпан кредит. Для интерактивной разведки —
загрузок, сводных таблиц, построения графиков — этого достаточно.

## Данные уже под рукой — это главный довод «за»

Вся аналитика лежит на той же машине, где будет крутиться песочница:

- **PostgreSQL `research_wiki` — 3,5 ГБ.** Схемы: `core`, `derived`,
  `meta`, `pipeline`, `staging`. Доступ по `localhost:5432`, пароль в
  `~/.pgpass`, тоннель не нужен.
- **26 CSV-файлов** в `research-wiki-private/data` (7,7 МБ).
- 314 карточек статей, 35 метрик ETL, ряды наблюдений.

Это тот же контур, ради которого Hermes2 ставился на эту ВМ: данные и
вычисления рядом, без сетевых переходов.

## Единственная реальная проблема — доступ

**Наружу порт 8888 закрыт.** Группа безопасности `ssh-access-sg` разрешает
входящие только на 22 и 5432. Публиковать Jupyter напрямую нельзя, да и не
нужно: он не рассчитан на открытый доступ.

**Решение — SSH-туннель, и он уже отработан.** На ВМ это не новшество:
два тоннеля работают постоянно — `pg-tunnel` (15432 к БД) и `hermes2-tunnel`
(18642 к `api_server`). Третий, для Jupyter, ложится в ту же схему:

```
# с ноутбука или телефона:
ssh -i ключ -N -L 8888:127.0.0.1:8888 ubuntu@89.169.168.214
# затем в браузере: http://localhost:8888/?token=<токен>
```

**С телефона** это делается штатными клиентами — Termius, Termux, JuiceSSH
умеют перенаправление портов `-L`. Схема: туннель в клиенте, браузер на
`localhost:8888`.

**Не нужно** открывать порт в группе безопасности и не нужно ставить
nginx/caddy с TLS: трафик идёт внутри SSH-шифрования, поверхность атаки не
растёт.

## Что придётся доставить

JupyterLab встал, но аналитических библиотек в окружении нет — только
`psycopg` (поставлен для доступа к БД). Нужны:

```
uv pip install --python ~/.hermes/hermes-agent/venv/bin/python3 \
  pandas numpy matplotlib seaborn scipy statsmodels duckdb polars plotly
```

Это **25 пакетов**, разрешение зависимостей заняло 650 мс, на диске около
1 ГБ. `pypi.org` и `files.pythonhosted.org` с ВМ доступны, `uv` работает.

## Развилка, которую стоит решить сознательно

**Ставить в окружение Hermes или отдельное?** Два варианта с разными
компромиссами.

**Один venv (проще, но смешивает роли).** Jupyter и агент делят окружение.
Плюс: одна установка, один набор библиотек. Минус: обновление Hermes через
`hermes update` пересобирает venv и может снести доставленные пакеты —
песочница сломается молча, как это уже случилось с `psycopg`.

**Отдельный venv для песочницы (чище).** `~/.venvs/sandbox` со своим
JupyterLab и библиотеками. Плюс: `hermes update` до него не дотягивается,
роли разделены, версии можно двигать независимо. Минус: библиотеки в двух
копиях (~1 ГБ диска, а его 45 ГБ свободно).

**Моя рекомендация — отдельный venv.** 1 ГБ диска — ничто против риска,
что обновление агента тихо снесёт рабочую песочницу. К тому же окружение
Hermes обслуживается `uv` как проект, и посторонние пакеты в нём — это
изменение того, что агент считает своим.

## Оценка альтернатив, которые я рассмотрел

**Hermes dashboard (`hermes dashboard`).** У агента есть веб-панель для
управления конфигурацией, ключами и сессиями. Она **не заменяет**
JupyterLab: это пульт для агента, а не среда для анализа данных. Но её стоит
держать в уме как дополнение — запускается на том же хосте.

**code-server (VS Code в браузере).** Раньше был на VPS, удалён при
освобождении памяти. На ВМ доступен (`update.code.visualstudio.com` — 200).
Даёт редактор и терминал, но для табличной разведки Jupyter удобнее: ячейки,
вывод на экран, графики рядом с кодом.

**DuckDB без Jupyter.** Для чисто SQL-разведки хватило бы `duckdb` в
командной строке — 10 МБ вместо 1 ГБ. Если ручная работа в основном
табличная, а не графическая, это может оказаться достаточным. Оставляю как
запасной вариант.

## Чего это решение не даёт

**Многопользовательского режима.** JupyterLab поднимется для одного
пользователя через туннель. Если нужен доступ вдвоём — это уже JupyterHub,
отдельный слой сложности, который сейчас не нужен.

**Замены профилю `monitor`.** Песочница — для ручной работы человека.
Автоматический сбор остаётся за агентом. Это разные инструменты, и
совмещать их не следует.

## Вердикт

**Решение оправдано.** Ресурсы есть с восьмикратным запасом по памяти,
данные лежат на той же машине, доступ решается тоннелем по уже работающей
схеме, а цена вопроса — около 1 ГБ диска и полчаса настройки.

Установку я уже провёл в ходе оценки — JupyterLab 4.6.3 работает на ВМ.
Осталось решить две вещи: ставить библиотеки в отдельный venv или в
окружение агента (рекомендую отдельный) и завести ли systemd-юнит, чтобы
песочница поднималась автоматически, или запускать вручную по мере
надобности.

**Замечание о ручном режиме.** Раз песочница для ручной работы, юнит с
автозапуском может быть избыточен: сервер будет держать 86 МБ постоянно.
Разумнее запускать по требованию — `systemctl --user start jupyter` перед
сессией разведки и гасить после.

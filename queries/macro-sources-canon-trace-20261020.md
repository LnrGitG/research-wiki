## 3. Трасса загрузки: шесть стадий, один контракт

Разрыв воспроизводится не в парсерах, а в отсутствии единого контракта: у 15 живых
рядов — 4 разных способа попадания в базу (cron → канон, скрипт руками → CSV,
ручная выгрузка → `data/*.xlsx`, «в реестре есть, скрипта нет»). Предлагаю один
контракт для всех, включая новые макро-ряды.

1. **Обнаружение (discovery).** Запись в `catalog.source_endpoint`: `url`, `kind`
   (`api`/`file_feed`/`html_table`/`opendata_index`), `poll_cron`, `parser_script`,
   `parser_args`, `is_active`. Опрос — **по календарю публикаций**, а не «раз в сутки
   на всякий случай»: ключевая ставка — день заседания СД (публикация 13:30 мск),
   аукционы ОФЗ — объявление во вторник, публикация результатов в среду, ИПЦ Росстата —
   третья среда месяца, КЭП — конец месяца за предыдущий, макропрос — 4 волны в год,
   inFOM — еженедельно. Точные даты держит календарь публикаций, не cron-строка.
2. **Снимок сырья (snapshot).** Скачанный файл кладётся в `raw/<источник>/<YYYY-MM-DD>/`
   неизменным; SHA-256 пишется в `catalog.release.content_hash` и в `ops.release_seen`.
   Совпадение хэша = «нового выпуска нет» → прогон завершается без записи.
3. **Разбор (parse).** Снимок разбора (JSON: что извлечено, откуда, с какими
   предупреждениями) кладётся рядом с сырьём. Разбор без снимка не принимается:
   иначе расхождение значений нечем объяснить.
4. **Запись в канон.** Напрямую в `catalog.release` → `data.observation`, без
   промежуточного SQLite (правило владельца 16.10.2026). Метка релиза — по снапшоту
   (`cbr_mo_survey_2026-10`), не по накопленной выборке. `sub_dimension` заполняется
   осмысленным значением (`'итого'`), не NULL — иначе `ux_observation` не отсекает дубль.
5. **Приёмка (verify).** Сверка канона со снимком разбора **по (период, регион,
   подразрез)**: совпало / расхождения / лишние / пропущенные. Плюс контроль
   идемпотентности повторным прогоном: 0 новых строк.
6. **Свежесть и журнал.** `ops.ingest_run` (status, rows_written, exit_code,
   output_tail), `ops.quality_result`, статус в `derived.v_metric_context`.
   Ежедневный `db_freshness_daily.py` сводит снимок; допуски — пер-частота.

Расписание по источникам, которые сейчас вне контура (предлагаемое):

- `minfin_budget` — месячно, 20-е число, `minfin.gov.ru/ru/statistics/fedbud/execute/`
  (проверено: HTTP 200 с VPS). Ряд накопительный с начала года → месячный поток первой
  разностью внутри года, метка накопления пишется в `sub_dimension`.
- `minfin_ofz_auctions` — вторник (объявление) и среда (результаты), частота E,
  `frequency_code='E'`, `period_start = period_end = дата аукциона`.
- `moex_intraday` — в дни заседаний и аукционов, окно −30…+120 мин, частота I.
- `nbki_pdn` / `bki_okb` / `riarating` — месячно по дате публикации пресс-релиза
  (`nbki.ru`, `bki-okb.ru`, `riarating.ru` — все три отдают 200 с VPS).
- `cbrmon` — месячно, подключить существующий `cbr_monitoring_canon.py` к cron.

Особый случай — **`budget.gov.ru`**: с VPS соединение не устанавливается (проверка
20.10.2026: код 000, таймаут 15 с), то есть п. 32 перечня ДДКП закрывается только
через `minfin.gov.ru` либо через резидентный канал. Это ограничение канала, не схемы.

## 4. Схема: что добавить под РФ-ряды другой частоты

Диагноз по живой базе: регион «Российская Федерация» существует (`region_id=1`,
`level='country'`), но механизм «ряд только по РФ» объявлен и **пуст** —
`catalog.metric_region_scope` содержит 0 строк. Словарь частот — 5 кодов
(A, D, M, Q, W), причём у W `period_type='cumulative'`, что неверно (неделя —
не накопительный период). Носителя для внутридневных меток нет. Событий как
сущности нет.

### 4.1. Частоты (расширение словаря)

```sql
INSERT INTO catalog.frequency (frequency_id, freq_code, name_ru, period_type, months_per_period) VALUES
  (16, 'E', 'по событию (нерегулярная)', 'event',     0),
  (17, 'H', 'полугодовая',               'halfyear',  6),
  (18, 'I', 'внутридневная',             'intraday',  0);
UPDATE catalog.frequency SET period_type = 'week' WHERE freq_code = 'W';  -- было 'cumulative'
```

Допуски свежести в `derived.v_metric_context` дополнить: E — 40 дней (событие
происходит по календарю, «пропуск» события = дефект), H — 220, I — 3.

### 4.2. Область ряда: РФ против регионов

Задействовать существующую таблицу, не заводить новую:

```sql
-- scope: 'country' (ряд только по РФ), 'region' (только субъекты), 'all' (оба разреза)
INSERT INTO catalog.metric_region_scope (metric_id, scope, region_id, note) VALUES ...
```

Читающая сторона: в `derived.v_metric_context` добавить колонку `region_scope`,
`ops.fetch_context` — не искать региональный разрез у ряда со `scope='country'`
(сейчас пустой поиск по регионам маскируется под «данных нет»). Уникальность:
`UNIQUE (metric_id, scope, region_id)`.

### 4.3. События: заседания, аукционы, публикации

Событие — не период: у него есть дата, тип и исход, и на него ссылаются сразу
несколько рядов (решение по ставке, реакция кривой, объём предложения).

```sql
CREATE TABLE catalog.event (
  event_id      integer PRIMARY KEY,
  event_type    text NOT NULL,        -- 'sd_meeting' | 'ofz_auction' | 'budget_release' | 'data_release'
  event_date    date NOT NULL,
  title         text NOT NULL,
  source_id     integer REFERENCES catalog.source(source_id),
  payload       jsonb,                -- параметры события (выпуск ОФЗ, объём предложения)
  UNIQUE (event_type, event_date, title)
);

ALTER TABLE data.observation ADD COLUMN event_id integer REFERENCES catalog.event(event_id);
-- ряд события: frequency_id=16, period_start = period_end = event_date, event_id заполнен
```

Это же снимает разнобой «период = горизонт прогноза» у `cbr_mo_*`: у прогнозного
ряда период — горизонт, а волна опроса уходит в `release_id`, и это надо
зафиксировать в `catalog.metric.description`, а не оставлять на догадку читателя.

### 4.4. Внутридневные данные — отдельная таблица, не партиции по годам

`data.observation` партиционирована по `period_start` (месячные партиции до 2031),
`period_start` — `date`. Внутридневную метку туда положить нельзя без потери
точности, а объём несопоставим с месячными рядами.

```sql
CREATE TABLE data.observation_intraday (
  obs_id       bigint GENERATED ALWAYS AS IDENTITY,
  metric_id    integer NOT NULL REFERENCES catalog.metric(metric_id),
  region_id    integer NOT NULL DEFAULT 1,
  obs_ts       timestamptz NOT NULL,
  value        numeric,
  frequency_id integer NOT NULL DEFAULT 18,
  release_id   integer REFERENCES catalog.release(release_id),
  source_id    integer REFERENCES catalog.source(source_id),
  venue        text,            -- 'moex_tqcb', 'cbr_auction'
  sub_dimension text NOT NULL DEFAULT 'итого',
  quality_flags text[]
) PARTITION BY RANGE (obs_ts);
-- партиции — по месяцам; хранение 24 месяца, далее архив в YC Object Storage
CREATE UNIQUE INDEX ux_obs_intraday ON data.observation_intraday
  (metric_id, region_id, obs_ts, sub_dimension, release_id);
```

### 4.5. Прогнозы и распределения

`assessment_type='forecast'` уже есть в словаре значений (6 строк), но горизонт
и квантиль негде взять. Для новых рядов (макропрос, сценарные траектории):
один код метрики + `sub_dimension` вида `'квантиль: p50; горизонт: 2027Q4'`.
Переписывать существующие 53 метрики `cbr_mo_*` (12 448 строк, по метрике на
квантиль × горизонт) не предлагаю — это ревизия истории; фиксирую как
технический долг с отдельным решением.

### 4.6. Лаг публикации как первоклассный атрибут

`catalog.release.published_at` есть (пример: релиз 324 ИПЦ — `2026-09-20`,
`ingested_at 2026-10-18`), но не читается ни одним представлением. Для наукастинга
нужен явный лаг «период → публикация»:

```sql
CREATE VIEW derived.v_publication_lag AS
SELECT r.source_id, o.metric_id, r.release_id, o.period_start,
       r.published_at::date AS published_on,
       (r.published_at::date - o.period_end) AS lag_days
FROM data.observation o JOIN catalog.release r USING (release_id);
```

Без этого «дата отсечения» собирается вручную и в отчётах расходится.

### 4.7. Один реестр endpoint вместо двух

Сейчас параллельно живут `catalog.source_endpoint` (15 строк, есть `last_hash`,
`last_checked_at`, `parser_args`, `parser_pre`) и `ops.ingest_endpoint` (8 строк).
Из 8 записей `ops` четыре расходятся с `catalog` по URL для того же источника —
это не дубль, а разные адреса одного контура. Предлагаю:

- канонический реестр — `catalog.source_endpoint` (у него есть всё нужное);
- `ops.ingest_endpoint` упразднить, перенеся 8 записей с явной сверкой URL;
- `ops.ingest_queue` / `ops.ingest_run` / `ops.release_seen` оставить как журнал
  прогонов (это и есть «трасса» в смысле аудита), но наполнить: сейчас там 23 / 38 / 111
  строк, и последние прогоны — начала октября.

## 5. Порядок внедрения и приёмка

**Волна 1 (схема, без данных).** Коды частот E/H/I, правка `period_type` у W,
заполнение `metric_region_scope`, `catalog.event`, `data.observation_intraday`,
`derived.v_publication_lag`. Точка возврата: `pg_dump -Fc` схем `catalog`/`data`
плюс git-тег `pre-macro-schema-20261020`. Приёмка: `information_schema` показывает
новые объекты; существующие 6 697 780 строк не изменились (`count(*)` до/после);
`ux_observation` цел.

**Волна 2 (локальные загрузчики, порядок по цене ошибки).**
`cbr_monitoring_canon.py` → cron; `moex_intraday` → `data.observation_intraday`;
`minfin_budget` → месяц; `minfin_ofz_auctions` → события + `event_id`;
`nbki_pdn` / `bki_okb` / `riarating` → новые карточки и источники.
Приёмка каждого: повторный прогон даёт 0 строк; сверка со снимком по (период, регион,
подразрез) с нулём расхождений; запись в endpoint + cron + `ops.ingest_run`.

**Волна 3 (смысловой слой).** Тексты ЦБ: `catalog.document` + `data.document_signal`
(direction 5 классов, degree, time_ref, dissent) — по уже написанному
`queries/dkp-communication-stack-design.md`; это не ряды и в `data.observation` не идут.

**Не делать без отдельного решения:** переписывание 53 метрик макропроса под
`sub_dimension`; перенос внутридневных CSV задним числом; любые изменения в
замороженной `v2`.

## 6. Что противоречит и что требует проверки

- **Два реестра расходятся по URL** для КЭП (`50802` vs `50798`), банковской
  статистики и ключевой ставки — до объединения нельзя сказать, какой адрес живой.
- **12 448 строк макропроса лежат под `source_id = unknown`** — источник фактически
  не привязан; это дефект метаданных, а не данных.
- **ЕМИСС не обновляем с этого хоста** (403 с датацентр-IP), поэтому 1 939 038 строк
  ЕМИСС — статичный слой; безработица и зарплаты закрываются КЭП, но не ЕМИСС.
- **`budget.gov.ru` недоступен** (таймаут), `minfin.gov.ru` доступен — п. 32 перечня
  ДДКП закрывается через Минфин, а не через портал бюджета.
- **Ряды ЕМИСС живы, но с дырой по РФ.** Проверка 20.10.2026 опровергла первое
  прочтение («мёртвый ряд»): у `emiss_43062_unemp_q` 87 регионов идут до 2026-04,
  а строка Российской Федерации обрывается на 2022-10 (у `emiss_57824_wage_m` —
  регионы до 2026-06, РФ до 2022-12). То есть дефект не в источнике, а в
  федеральной строке: либо загрузчик её теряет (переименование территории в
  выгрузке), либо в самом индикаторе ЕМИСС строка РФ ведётся отдельно. Проверить
  это можно только с резидентного канала — fedstat.ru отдаёт 403 с датацентр-IP.
  До выяснения ряды **не депрекейтить**: они рабочие на региональном разрезе.
- Не проверено: есть ли у НБКИ/ОКБ API или только пресс-релизы; как часто
  РИА Рейтинг обновляет «закредитованность» — это выясняется при первом прогоне.

**Решение: канон — `catalog.source_endpoint`, `ops.ingest_endpoint` упразднить.**

### 8.3. Ряды ЕМИСС — не депрекейтить, чинить федеральную строку

**Решение пересмотрено по факту проверки 20.10.2026: `deprecated` НЕ применять.**

Первое прочтение («ряд мёртв с 2022 года») опровергнуто: дефект только в строке
Российской Федерации. У `emiss_43062_unemp_q` 87 субъектов идут до 2026-04 (последний
квартал — 87 строк), у `emiss_57824_wage_m` — до 2026-06, тогда как строка РФ
обрывается на 2022-10 и 2022-12 соответственно (62 и 72 наблюдения). Значит источник
жив, а теряется либо федеральная строка при разборе (переименование территории в
выгрузке), либо она ведётся в индикаторе отдельно и загрузчик её не берёт.

Проверить это можно только с резидентного канала: fedstat.ru отдаёт 403 с датацентр-IP,
поэтому endpoint #3 в реестре помечен неактивным. До выяснения рядами продолжаем
пользоваться в региональном разрезе и **не** переводим их в `deprecated` — иначе
пропадёт живой региональный слой. Потребность в ряде по РФ на время закрывает КЭП
(до 2026-08). Отдельно остаётся техническое противоречие каталога: 28 метрик имеют
`status='deprecated'` при `is_active=true` — это надо снять независимо от ЕМИСС.

### 8.4. Макропрос: 53 карточки оставить

**Решение: не нормализовать историю; привести метаданные и зафиксировать соглашение.**

читатель и так берёт `p50`, а квантиль читается из кода. Обязательно другое:
`source_id` → `cbr` (сейчас 51 метрика и 4 812 строк лежат под `unknown` — это дефект,
а не дизайн); `description` = «период — горизонт прогноза, волна опроса — релиз,
суффикс `_p10/_p50/_p90` — квантиль»; теги для поиска; попадание в `metric_card`.

### 8.5. Пятая развилка, найденная при проверке: видимость карточек

**Решение: чинить в волне 1a, до подключения новых загрузчиков.**

`derived.metric_card` содержит 2 505 карточек (2 478 активных) при 17 336 метриках
каталога, а `derived.v_catalog_active` построено на `core.metric_legacy` — это
**BASE TABLE, снимок**, и возвращает 1 570 карточек. Основной путь `ops.fetch_context`
читает `metric_card` + `catalog.metric`, то есть видит 2 505 метрик, а не 17 336.
Класс отказа знакомый: ряд записан, но не находится, и пустой ответ читается как
«данных нет». Поэтому приёмка каждого нового макрозагрузчика обязана включать
проверку «карточка есть в `metric_card` и находится `fetch_context`», а `v_catalog_active`
надо перевести на `catalog.metric` с контролем `count(*) WHERE metric_code IS NULL = 0`.

**Приоритет, если делать один шаг.** Сначала 8.5 и 8.2: видимость карточек и единый
реестр дают больше, чем любой новый загрузчик, потому что без них новый ряд физически
не найдётся. Потом 8.1a, затем 8.3 и 8.4 (метаданные), и только после этого 8.1b
с событиями и внутридневными рядами.

дважды: первый прогон собрал 314 712 строк, к вставке 307 368, отказов по единице 0,
метрик 1 395; число наблюдений в базе не изменилось (6 697 780 до и после) — то есть
повторный прогон идёт в конфликт ключа и даёт ноль новых строк. Идемпотентность
подтверждена не рассуждением, а счётчиком. Обёртка
`~/.hermes/profiles/macroeconomist/scripts/cbr_cbrmon_monthly.sh`, джоб
`315069e2ac03` «Мониторинг предприятий ЦБ monthly canon load», cron `0 11 20 * *`,
режим no-agent, доставка local — как у соседних джобов (inFOM, макропрос, ZCYC).

**Самопроверка датировки была ложной.** Встроенный контроль ждал значение 11.1019
в 2026-04 и получил 9.4288 — на первый взгляд ошибка загрузчика. Разбор показал
обратное: 17.10 период был сдвинут на месяц (вычитался один месяц вместо двух), ряд
переехал, и 11.1019 оказалось в 2026-05, а 9.4288 — в 2026-04. То есть врала не
датировка, а константа проверки, привязанная к «последнему периоду». Переписал
контроль на три независимых сигнала: где физически лежит контрольное значение (ожид.
2026-05-01), какой последний период (`2026-10-01`, значение −9.9912) и не ушёл ли
период в будущее. Теперь проверка не устаревает от новой волны.

**Фасеты: покрытие восстановлено, но не тем способом, каким планировалось.**
Дозаполнение упёрлось во внешний ключ — `derived.catalog_facets.metric_id` ссылался
на снимок `core.metric_legacy`, поэтому фасет физически нельзя было завести у метрик,
которых в снимке нет (первая попытка вставки упала на `metric_id=71964`). Проверил
безопасность переноса: все 2 462 существующих фасета присутствуют в `catalog.metric`,
ни одного сироты. Переключил внешний ключ на `catalog.metric` (откат —
`attic/db-snapshot-20261020-facets/rollback-fk.sql`), после чего
`scripts/rebuild_catalog_facets.py --apply` добавил 14 352 строки; фасетов стало
16 814 против 2 462, пустых `measure` и `unit_canonical` в `derived.v_catalog_active`
— ноль (было 1 926 и столько же).

Честно про качество разметки: `measure` выведен по единице и тегам (14 335 `level`,
17 `index`, темпов не нашлось — их надо размечать отдельно), `domain` переносится по
префиксу кода от уже размеченных семейств; перенеслось 15 префиксов, у 12 865 метрик
домен `other`. Это «не размечено», а не «нет домена» — писать иначе было бы выдумкой.
Существующие 2 462 строки не трогал: у них эвристика старого конвейера (например,
домен `construction` по тегу `rosstat_observations`), которую без потери качества не
воспроизвести.

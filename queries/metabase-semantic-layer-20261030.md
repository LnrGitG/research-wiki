# Семантический слой Metabase: реализация 30.10.2026

## Итог одной фразой

Семантический слой сделан на объектах-метриках (`card.type = "metric"`), а не на
мерах (`measure`): в сборке v0.64.3.5 определение меры молча теряет фильтры,
поэтому мера над витриной считает среднее по всем индикаторам сразу. Создано
17 метрик и 3 сегмента, поверх них собран дашборд id 7 «Семантический слой:
индикаторы жилья и ипотеки» из 17 карточек — в карточках SQL нет, только
ссылки на метрики.

## Почему мера не годится

- `POST /api/measure` принимает определение, но `filter` в ответе и в поведении
  отсутствует; мера считается по всей таблице `derived.v_bi_observation`.
- `PUT /api/measure/{id}` → 400, `DELETE /api/measure/{id}` → 404: объект
  неуправляем через API. Три пробные меры (`pm_a`, `pm_f`, `probe_m2`)
  удаляются только вручную в интерфейсе.
- Метрика же хранит полный одностадийный запрос: фильтры, ровно одна
  агрегация, максимум одна группировка. Этого достаточно для индикаторов
  жилищного контура.

## Принятые соглашения

1. **Запас не суммируется.** Задолженность, эскроу, площадь действующих ДДУ —
   уровни на дату: в метриках с разбивкой по месяцам они читаются по строке, а
   в региональных срезах усредняются за окно, а не складываются.
2. **Поток суммируется** (выдачи, ввод, реализация), но только внутри окна и
   с явной подписью «за 3 мес.» в названии.
3. **Индекс СМР — медиана, не среднее.** Среднее по субъектам ломается
   выбросами: Ингушетия 53 336 % в январе 2026, среднее по регионам доходило до
   714 %. Медиана сентябрь-2026 = 103,68 % при среднем 102,40 % (январь-2026:
   медиана 87,90 %).
4. **Накопительный объём работ** (`orvdsningmr`) сравнивается только с
   одноимённым месяцем прошлого года: суммировать по месяцам нельзя.
5. **ЕИСЖС-подразрезы.** `rkop_3` хранится в 432 подразрезах на регион-месяц;
   канонический агрегат — `sub_dimension = 'охват: регионы | статус: Всего'`.

## Как воспроизвести

```bash
python3 scripts/metabase_semantic_mcp.py --verify   # только прогнать запросы
python3 scripts/metabase_semantic_mcp.py --dry-run  # проверить, ничего не писать
python3 scripts/metabase_semantic_mcp.py            # создать/обновить метрики и сегменты
python3 scripts/metabase_semantic_dashboard.py      # дашборд id 7 из метрик
```

Оба скрипта идемпотентны: метрики ищутся по имени в коллекции, метрики вне
списка архивируются, карточки дашборда переиспользуются по `card_id`.

## Технические находки по API

- **MCP-сервер Metabase** (`http://<host>/api/metabase-mcp`) доступен: 21
  инструмент, включая `measure_write`, `metric_write`, `segment_write`,
  `execute_query`, `learn`. Через него созданы первые три метрики.
- Через MCP нельзя гонять объёмную работу: поток SSE отдаёт русский текст в
  битой кодировке (`Ð¡ÑÐµÐ´Ð½Ð¸Ð¹`), а длинные ответы рвутся
  (`Unterminated string`), поэтому создание переведено на REST.
- `POST /api/dataset` принимает **классическую** форму MBQL, а карточки метрик
  хранят **lib-форму** (`stages`, `filters`, `["field", opts, id]`).
  Конвертер `to_legacy()` в скрипте есть, но валидировать через него нельзя:
  фильтры искажаются (все ряды схлопываются в одинаковые числа). Надёжная
  проверка — сохранить карточку и выполнить `POST /api/card/{id}/query`.
- Карточки не добавляются на дашборд через `POST /api/dashboard/{id}/cards`
  (404): раскладка целиком отдаётся одним `PUT /api/dashboard/{id}` с массивом
  `dashcards`, где новые элементы имеют отрицательный `id`.
- Публичный дашборд отдаёт данные через
  `GET /api/public/dashboard/{uuid}/dashcard/{dashcard_id}/card/{card_id}`
  (не `.../query`; такие эндпоинты в 0.64 отсутствуют).

## Что осталось за рамками

- Метрики не поддерживают median-of-medians и расчётные величины (реальные
  ставки, PDN): для них нужны либо вью в базе, либо модели Metabase.
- `meta.series_comparability` по-прежнему пуста, поэтому о структурных разрывах
  рядов метрики не предупреждают — это отражено в описании каждой метрики
  текстом.
- Три технические меры `pm_a`, `pm_f`, `probe_m2` остаются в Measures до
  ручной чистки в UI.

## Перевод на дедуплицированную витрину (30.10.2026)

Метрики переведены с `derived.v_bi_observation` на `derived.v_bi_dedup`
(таблица Metabase id 364, поля 5546–5552). Скрипт теперь сам находит id таблицы
и полей по имени вью (`resolve_source`), поэтому id не вшиты и переживут
пересоздание витрины.

значения не сдвинулись, средние не пострадали.

Сегменты пересозданы на новой таблице (id 5, 6, 7). Прежние сегменты 1–3 висят
на старой таблице 348, а также остался пробный «сегмент-проба» — удаление
заблокировано как разрушительная операция, чистка в UI за владельцем.

### Грабли, которые встретились

- `DISTINCT ON` по широкой витрине (29 колонок, 7,8 млн строк) уронил ВМ в
  `DiskFull`: сортировка не влезла в 1,4 ГБ свободных. Узкая вью (7 колонок)
  сортирует только строки одного индикатора — 0,6–0,7 с на запрос.
- После создания вью Metabase видит таблицу с нулём полей; помогает
  `POST /api/table/{id}/sync_schema` (общий `sync_schema` базы недостаточно).
- Сегменты требуют `lib/uuid` на каждой клаузе lib-запроса; метрики — нет.
- Список сегментов нельзя собирать на этапе импорта модуля: id полей там ещё
  `None`, и в запрос уходит `null`. Собирать внутри `main()` после
  `resolve_source()`.

## Версионирование слоя в git-контенте (30.10.2026)

Слой выгружен в репозиторий контента Hermes-2 (`~/metabase-content-work`),
ветка `feature/semantic-layer`, коммит `e042162`, запушено в bare-репозиторий
`~/metabase-content.git`:

- коллекция `zhile-stroyka-i-ipoteka-research` — 38 объектов;
- карточки: **17 `card_type: metric`** и 18 `card_type: question`
  (вопросы — из дашборда-витрины, собранного ранее);
- 2 дашборда, включая «Семантический слой: индикаторы жилья и ипотеки»;
- `state/localhost_3000.json` — карта uid→id прода, без секретов.

Ограничения msync, выявленные при выгрузке:

- **Сегменты не переносятся вовсе** — в коде нет обращений к `/api/segment`.
  Три сегмента слоя существуют только на инстансе.
- Origin репозитория контента — локальный bare-репозиторий, не GitHub, поэтому
  CI-гейт (`msync validate` в Actions), описанный в README, пока не существует.
- Проверка «метрики превращаются в вопросы» оказалась ложной тревогой: списочный
  `GET /api/card/` отдаёт `type`, и в выгрузке метрики всегда были метриками
  (17 из 38). Правку msync с дозапросом карточки откатили — она добавляла 35
  лишних GET без выигрыша.

## Причина дублей: не второй писатель, а фильтр статусов (30.10.2026)

Разбор источников опроверг исходную гипотезу о «втором писателе». Уникальный
ключ `ux_observation` включает `release_id`, поэтому перезаливка не удаляет
старые строки, а помечает их статусом `superseded`. По ипотечным рядам это
видно прямо:

- релиз 138 «cbr-vfs-0420218 2026-09-21 (перенос из v2, этап 1.4)» —
  7 560 строк, статус `superseded`, периоды 2019-02…2026-07;
- релиз 153 «cbr-vfs-sync 2026-10-06 (прямой канал, ingest-watcher)» —
  7 728 строк, статус `validated`, периоды 2019-02…2026-09.

Витрина отсекала только `rejected`, а исторические версии `superseded`
включала — отсюда ровно двойные суммы. Статусы в `data.observation`:
`validated` 5 723 202, `raw` 1 940 701, `superseded` 182 022, `rejected` 35 823,
`preliminary` 352.

Исправлено в двух местах:

1. `derived.v_bi_observation` — фильтр `NOT IN ('rejected','superseded')`
   (было 7 845 179 строк, стало 7 663 355).
2. `derived.v_bi_dedup` — дедупликация по ключу с приоритетом статусов
   `validated → preliminary → raw` и последним релизом внутри статуса. Это
   закрывает и вторую категорию повторов: у рядов ЕМИСС (`emiss_57710` и др.)
   дублируются между собой строки `raw` — 434 794 строки на 403 291 ключ,
   после дедупликации 403 291 = 403 291.

Проверка после правок: выдачи ИЖК РФ январь 2019 = 174 355, задолженность
февраль 2019 = 6 667 739, сентябрь 2026 = 21 881 863, ставка август 2026 =
10,09 %, медиана ИФО СМР январь 2026 = 87,90 %, выдачи Алтая июль–август 2026 =
743. Все 17 метрик `completed`.

Публичная витрина пересобрана и опубликована с исправленными числами
(коммиты `54aeb7d` в приватном и `92f8e1f` в публичном репозитории).

Остаток: на инстансе накопились лишние сегменты (1–3 на старой таблице 348,
4 — пробный, 5–7 с устаревшими id полей, 8–10 актуальные); удаление через API
заблокировано как разрушительная операция, чистка в UI.

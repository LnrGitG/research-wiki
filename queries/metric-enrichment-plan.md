# План: ИИ-обработка и разметка показателей research_wiki

Задача: обогатить 2 438 метрик `core.metric` семантическими и статистическими
атрибутами, чтобы включить автоматический подбор спецификаций, поиск
объясняющих рядов и фильтрацию полезных рядов. Артефакты разметки — в БД
(`derived.*`), вердикты с человеческим контуром проверки.

## 1. Поля разметки (derived.metric_enrichment)

| Поле | Тип | Содержимое |
|---|---|---|
| metric_id | PK/FK | ссылка на core.metric |
| flow_stock | enum | flow (за период: выдача, сделки, ввод) / stock (на дату: остатки, действующие ДДУ, задолженность) / ratio / index / level |
| value_kind | enum | на дату (point-in-time) / за период (cumulative) / темп (yoy, mom) / среднее за период |
| frequency_native | enum | родная частота ряда (5=мес, 6=кварт, 3=год) |
| hierarchy_parent | text | metric_id вышестоящего показателя (если есть вложенность: КЭП 1.1 → 1.1.1 → …) |
| hierarchy_depth | int | уровень вложения |
| econ_group | text | экономическая группа (ипотека, эскроу, СМР, ввод, цены, ДДУ, сток, бюджет…) |
| econ_tags | jsonb | теги для поиска |
| stat_profile | jsonb | CV, AC1, сезонная амплитуда, число точек, разрывы (из metric_audit) |
| predict_power | jsonb | для каких таргетов полезен: {target_metric: {lag, rmse_gain, corr}} |
| explained_by | jsonb | от каких рядов зависит (обратная сторона predict_power) |
| stationarity | jsonb | adf_level/adf_diff/kpss + вердикт |
| transforms | jsonb | характеристики производных: diff, log, normalized (z-score), yoy — стационарность и распределение каждого |
| quality_flags | jsonb | константа, умерший, короткий, разрывы, дубли |
| ai_model | text | какая модель разметила |
| ai_confidence | numeric | уверенность модели 0-1 |
| human_reviewed | bool default false | флаг ручной проверки |
| enriched_at | timestamptz | время разметки |

## 2. Конвейер (4 шага)

### Шаг 1. Статистическая разметка (без ИИ, детерминированная)
Скрипт `scripts/enrich_stat.py`: для каждой метрики по наблюдениям:
- flow/stock — эвристика: AC1 > 0.98 и monotone → вероятный stock; yoy/темп в имени → темп;
- стационарность (ADF/KPSS level+diff) и характеристики transforms (diff, log, yoy, z-score);
- сезонная амплитуда, CV, разрывы;
- иерархия — парсинг name_ru («N.N …» для КЭП, «[подтаблица N]», «— level/yoy»)
  + parent-candidates по совпадению префикса кода и темы.
Результат: 60-70% полей заполняется без LLM. В БД со статусом `stat_only`.

### Шаг 2. LLM-разметка семантики (батчами)
Вход на метрику: name_ru, metric_code, tags, freq, первые/последние значения,
стат-профиль (CV, AC1). Задача LLM: flow_stock, value_kind, econ_group,
econ_tags, hierarchy_parent (выбор из списка кандидатов), описание.
Батч 20 метрик за вызов → 2 438 / 20 = ~122 вызова на модель.
Модели: основной проход — сильная модель; дешёвый pre-pass для
фильтрации артефактов — текущая рабочая модель.
Выход: JSON по схеме (jsonschema), при отказе схемы — ретрай с фиксом.

### Шаг 3. Predict power (вычислительный, не LLM)
Для пар «кандидат-фича → таргет» (ограничение: таргеты из среза nowcasting,
~30-50 метрик): кросс-корреляции на сетке лагов −6..+6, вклад в OOS-RMSE
простой OLS. Запись в predict_power/explained_by. Это дороже — запускается
на выбранных парах, не на всех.

### Шаг 4. Человеческий контур
HTML-дашборд «Разметка метрик» (как metric-audit): строки с полями,
фильтр по ai_confidence < 0.8, чекбоксы подтверждения. Подтверждённое
→ human_reviewed=true. Экспорт обратно в БД.

## 3. Нужна ли сильная модель (GPT/Astra)?

Да, но не для всего. Разметка семантики (flow/stock, вложенность, экономическая
группа) — задача на понимание русского экономического текста: сильная модель
даст заметно меньше ошибок на ambiguous названиях («Объём работ» vs «Остатки
на счетах»), на коротких кодах вроде y477110409, на вложенности КЭП.
Дешёвый вариант годится для: фильтрации мусора, простых тегов, префильтра
батчей. Схема затрат: ~120 батчей по 20 метрик; сильная модель — доли цента
на метрику даже в дорогом тарифе, всего порядка $1-3 на полный проход.
Модель для Astra Pro: не для tool-call пайплайнов — только батчевая разметка
через API. Итог: основной проход сильной моделью (GPT/Claude/Astra),
батчево, с валидацией схемы и confidence; ретраи и чек — текущей моделью.

## 4. Порядок реализации
1. derived.metric_enrichment таблица + jsonschema для LLM-выхода
2. scripts/enrich_stat.py — шаг 1 (стат-разметка) → отчёт в HTML как metric-audit
3. scripts/enrich_llm.py — шаг 2: батчевые вызовы, ретраи, confidence
4. predict_power — шаг 3 по мере надобности (интеграция со spec_runs!)
5. Дашборд проверки + кнопки в Telegram для спорных метрик
6. Обновление catalog: связи в вики-страницы (метрика ↔ статья/гипотеза)

## 5. Метрики качества процесса
- доля метрик с заполненным flow_stock (цель > 95%)
- доля human_reviewed (целевая ≥ 30% для nowcasting-среза)
- согласованность LLM-разметки со стат-эвристикой (шаг 1 vs шаг 2):
  расхождения > 5% — сигнал пересмотреть промпт

# Гармонизация staging → core: ключ наблюдения и рубежи
Пайплайн переноса таблиц `staging` в `core.observation_v2` по рубежам. Ключ
наблюдения:
```
(metric_id, region_id, frequency_id, period_start,
 source_id, release_id, assessment_type, sub_dimension)
Всё, что различает строки, обязано попасть в этот кортеж. Ниже — правила,
каждое из которых стоило молчаливой потери или задвоения данных.
## Рабочий порядок рубежа
1. **Разведка**: колонки, `SELECT count(DISTINCT source)`, заполненность полей
   периода (`month IS NULL` — признак, что годовые и месячные ряды лежат вместе).
2. **Симуляция ключа на staging до прогона** — Python-скрипт, `Counter` по
   кортежу ключа; потеря обязана быть 0. Ненулевая потеря означает, что найдено
   не всё различающее измерение; глушить её нумерацией строк нельзя (см. ниже).
3. **Точка возврата**: git-тег + `pg_dump -Fc -t <таблица>` по метке `localhost`
   (не `127.0.0.1` — `.pgpass` не подхватится) в бакет.
4. **Прогон** тяжёлых таблиц — на ВМ, не на слабом VDS (OOM).
5. **Сверка**: подготовлено == строк у метрик рубежа; истинные дубли по ПОЛНОМУ
   ключу (включая `release_id` и `sub_dimension`) должны быть 0.
6. Документ в `queries/`, коммит, урок в навык.
## Правило: `source` внутри staging — это первичная публикация
Колонка `source` внутри staging-таблицы означает НЕ источник вообще, а конкретный
выпуск: сборник Росстата против бюллетеня ЦБ, годовой файл против месячного.
Её место — `release_id`, а не `sub_dimension` и не игнорирование.
Проверять перед гармонизацией любой таблицы:
```sql
SELECT source, count(*) FROM staging."<таблица>" GROUP BY 1 ORDER BY 2 DESC;
Если источников больше одного и различие не вынесено — одинаковые значения
разных публикаций попадают в один ключ и **задваиваются при агрегации**. Симптом
в готовом датасете: одна метрика по одному региону и периоду выдаётся дважды с
одинаковым значением; проверка с учётом `release_id` даёт 0 истинных дублей.
```python
def ensure_release(cur, conn, source_id, label):
    cur.execute("""SELECT release_id FROM core.release
                   WHERE source_id=%s AND release_label=%s""", (source_id, label))
    r = cur.fetchone()
    if r:
        return r[0]
    cur.execute("""INSERT INTO core.release
        (source_id, release_label, published_at, status, notes)
        VALUES (%s, %s, now(), 'loaded', %s) RETURNING release_id""",
        (source_id, str(label)[:200], 'первичный источник внутри таблицы'))
    rid = cur.fetchone()[0]
    conn.commit()
    return rid
Строки с пустым `source` привязывать к первому релизу источника.
## Правило: поля, входящие в ключ, НЕ обрезать
Обрезка `substring`/срезом в Python полей, входящих в ON CONFLICT-ключ, даёт
тихую потерю: подписи различаются после предела. Пример масштаба — обрезка имён
регионов до 80 символов дала 54 потери на составных названиях вида «Всего
введено в действие жилых домов — федеральная — Всего, млн. м2 общей площади
жилых помещений».
Правило: в ключевых полях обрезки нет вовсе. Если поле нужно укоротить для
читаемости — укоротить отдельную колонку отображения, а не значение ключа.
Проверка — симуляция ключа: без обрезки потеря 0, с обрезкой ровно N.
## Правило: порядковый номер строки — только при реальной коллизии
Номер строки как универсальная защита от схлопывания засоряет `sub_dimension`
техническими хвостами (`строка 840`), которые портят легенды в датасете. Но и
убрать его целиком нельзя: бывают строки, различающиеся ТОЛЬКО значением
(в году-файле стройматериалов — пары с одной меткой и разными значениями;
сборщик утрачен, различить штатными полями невозможно).
Решение: лить во временную таблицу, затем дописывать номер только строкам с
повторяющимся ключом через оконные функции:
INSERT INTO core.observation_v2 (...)
SELECT metric_id, ...,
       CASE WHEN c = 1 THEN sub_dimension
            ELSE coalesce(sub_dimension || ' | ', '') || 'строка ' || ord END
FROM (SELECT t.*,
             count(*) OVER (PARTITION BY <ключ>) AS c,
             row_number() OVER (PARTITION BY <ключ> ORDER BY rn) AS ord
      FROM tmp_table t) z
ON CONFLICT (<ключ>) DO NOTHING;
## Правило: идемпотентность обязательна
Скрипт рубежа обязан удалять строки своего прошлого прогона, иначе повторный
запуск задваивает данные. Признак — тег рубежа у метрик:
DELETE FROM core.observation_v2 o
WHERE EXISTS (SELECT 1 FROM core.metric m
              WHERE m.metric_id = o.metric_id AND m.tags @> ARRAY['<тег рубежа>']);
Перед удалением убедиться, что тег создаёт только этот рубеж (посчитать строки).
Обход очистки — переменная окружения `SKIP_CLEAN=1` для отладки.
## Разнообразие форматов периода — проверять ДО симуляции
Формат периода неоднороден между таблицами, и каждый неучтённый вид даёт ложные
потери (несколько периодов схлопываются в один):
| Что встречается | Как выглядит | Решение |
|---|---|---|
| квартал строкой | `Q1`..`Q4` | regex `^Q(\d)`, маппинг в месяц 1/4/7/10 |
| колонка `q` вместо `quarter` | `q=1..4` | фолбэк `g('quarter') if not None else g('q')` |
| период вида `2023Q4` | годовые+квартальные в одной колонке | regex `^(\d{4})Q(\d)` ПЕРЕД разбором года |
| снапшот-дата ФНС | `20200407`, `20201123` | период = (год, квартал из месяца); полная дата → в подразрез |
| год и месяц в разных колонках | `report_year`, `report_month` | брать оба, не только год |
Квартал кодировать месяцем (1/4/7/10) — так `period_start` ложится на
квартальную сетку и хорошо фильтруется в датасете.
## Дубли против дополнений: решать по ключам, не по количеству
Таблица из остатка может быть (а) полным дублем уже перенесённого, (б)
дополнением, (в) тем и другим сразу — часть колонок дублирует, часть новая.
Решать множествами ключей, а не сравнением объёма:
keys_old = set(cur.execute("""SELECT region_id, period_start FROM core.observation_v2
    WHERE metric_id=%s AND release_id=%s""", (mid, rel_old)).fetchall())
keys_new = set(... то же для нового релиза ...)
# только-новых == 0  →  полный дубль, удалять
# только-новых  > 0  →  оставлять, это дополнение
У полного дубля число совпавших по значению пар равно числу строк. Удалять
нужно по релизу и метрике, а не по таблице целиком: из той же таблицы может
извлекаться новое (медианные цены, аренда), которого в целевой не было.
После удаления убирать осиротевшие метрики:
DELETE FROM core.metric m WHERE NOT EXISTS (
    SELECT 1 FROM core.observation_v2 o WHERE o.metric_id = m.metric_id)
  AND m.tags @> ARRAY['<тег рубежа>'];
## Диагностические грабли
- `JOIN core.release USING (release_id)` вместе с `JOIN core.source` даёт
  `AmbiguousColumn: common column name "source_id"` — писать явные `ON`.
- Коммит внутри цикла уничтожает серверный курсор — разводить соединения
  (отдельный `rconn`/`rcur` для чтения, основной `conn` для записи).
- `unit IS NULL` в SQL не группируется — строки с пустой единицей слипаются;
  либо `coalesce(unit, '')`, либо явный `count(*) FILTER`.
- Имя таблицы в `information_schema` полное (`schema__table`), не короткое.
- Словарь справочников: `SELECT source_id, source_code` + `dict()` даёт
  `{id: code}`, а нужен `{code: id}` — писать колонки в обратном порядке.
  Симптом ошибки: «нет источника <код>» на всех таблицах рубежа.
- Знак `%` внутри SQL, переданного в `cur.execute(sql, ())` с пустым кортежем,
  ломает плейсхолдеры psycopg-3 (`only '%s', '%b', '%t' are allowed, got '%'`) —
  удваивать (`%%`) либо не передавать пустой кортеж аргументов вовсе.
## Перед удалением метрик: проверить ссылки из legacy-таблиц
Удаление метрики падает с `ForeignKeyViolation`, если на неё ссылается таблица
предыдущего рубежа, не выведенная из эксплуатации. Перед чисткой метрик всегда
проверять, какие legacy-таблицы ещё живут и держат FK:
SELECT DISTINCT o.metric_id FROM core.observation o;  -- старый рубеж
Такая таблица может быть на ~99% дублем целевой (сверять по
`metric_id + region_id + period_start`) и при этом блокировать чистку. Судьба
таблицы — отдельное решение владельца; метрики, на которые она ссылается,
пропускать, а не удалять силой.
## Осиротевшие метрики после чистки
Метрика без наблюдений обычно имеет живого близнеца с тем же названием (код от
прежней попытки гармонизации) либо вытеснена новой метрикой с тем же смыслом.
Проверять по имени и по смыслу, а не только по коду. Отдельный класс — коды,

`01_01_01` (метрики панели и ДОМ.РФ) — ограничивать чистку тегом рубежа и кодами,
не начинающимися с цифры.

# Гармонизация данных research-wiki: staging → core
Данные переносятся в PostgreSQL точным слепком (схема `staging`), затем гармонизируются в целевую модель. Рубежи выполняются последовательно — каждый следующий зависит от предыдущего.
## Порядок рубежей
1. **Справочники** — `core.source`, `core.unit`, `core.frequency` (`harmonize_1_references.py`).
2. **Метрики** — `core.metric` (`harmonize_2_metrics.py`).
3. **Наблюдения** — `core.observation` (`harmonize_3a_aliases_releases.py`, `harmonize_3b_observations.py`).
Скрипты идемпотентны и поддерживают `--dry-run` — всегда сначала сухой прогон, потом запись.
## Ограничения схемы (проверять до записи)
DDL накладывает CHECK-ограничения, которые отбрасывают молча неверные значения:
- `frequency.period_type` ∈ {date, month, quarter, year, cumulative}; **для дневной и недельной частоты отдельного типа нет** — использовать `date`;
- `frequency.months_per_period` ∈ [1, 12] (ноль недопустим);
- `source.reliability` ∈ {official, primary, secondary, derived, unknown};
- `metric.metric_type` ∈ {primary, derived, nowcast_model}; `metric.status` ∈ {active, deprecated, merged};
- `observation.assessment_type` ∈ {flash, preliminary, revised, final, nowcast, forecast, estimated};
- `observation.observation_status` ∈ {raw, validated, rejected, superseded};
- `region_alias.confidence` ∈ {exact, manual, inferred, needs_review}.
Список получать заранее: `SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid='core.<таблица>'::regclass AND contype='c';`
## Генерация кодов метрик
Правило: готовый код источника, если есть (`panel.indicator_code` = `y477030001`), иначе первые буквы слов названия после транслитерации («Площадь квартир в жилых зданиях» → `pkzznns`). Минимальная длина — 3 символа: однобуквенные коды хрупки, любой новый показатель вытеснит их в суффиксную нумерацию. Коллизии разрешаются суффиксом `_2`, `_3`.
Реализация: `scripts/metric_codes.py`.
## Определение единиц измерения
В исходных данных единица часто НЕ в поле `unit`, а в скобках внутри названия. Порядок: разбор скобочного текста → смысловые правила («Количество …» → units, «Доля …» → pct) → `unknown`. Реализация: `scripts/unit_parser.py`.
## Сопоставление названий: НОРМАЛИЗУЙ ОБЕ СТОРОНЫ
Самая дорогая ошибка рубежа 3: ключ показателя нормализовался (убирались сноски «1)», лишние пробелы), а словарь метрик строился по сырому названию. Из-за рассогласования **13 103 строки** не нашли метрику — и это выглядело как «в исходных данных нет показателя», а не как баг скрипта.
Правило: если значение из источника проходит через `norm()`, то и ключи справочника обязаны строиться через `norm()`. Проверять сопоставление сравнением счётчиков «сколько уникальных имён найдено / не найдено» ДО массовой записи, и сверять эти цифры с ожидаемыми по составу справочника.
## Алиасы регионов
`data/region_aliases.csv` в репозитории — источник алиасов; загружается в `meta.region_alias` (схема: alias, region_id, source_id, confidence). Если файл пуст — восстановить из тега `backup/regions-before-cleanup-20260917`.
Нормализация перед сопоставлением: убрать сноски `\d\)$`, схлопнуть пробелы, снять NBSP, привести к нижнему регистру.
## Нерегиональные подписи → sub_dimension
В `region_name` части таблиц лежат НЕ регионы, а другие измерения: годы (`2002.0`), кварталы (`II квартал`), виды строительных работ («строительство мостов и тоннелей»). Их место — поле `sub_dimension` с регионом «Российская Федерация». Признак: имя не матчится ни в алиасах, ни в справочнике регионов и совпадает с шаблоном года/квартала/вида работ.
## Устойчивый доступ к базе (критично для долгих операций)
SSH-туннель к PostgreSQL на YC-ВМ **обязан быть systemd-юнитом**, а не фоновым `ssh -f -N`:
```ini
# ~/.config/systemd/user/pg-tunnel.service
ExecStart=/usr/bin/ssh -i %h/.ssh/id_yc -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
  -N -L 127.0.0.1:15432:localhost:5432 ubuntu@<IP>
Restart=always
Фоновый туннель умирает при перезапуске шлюза Hermes — а вместе с ним рвётся многочасовая вставка (наблюдался код 137). Долгие переносы запускать с `nohup`/в фоне **и** проверять живость туннеля перед стартом.
## Питфоллы
- **`pkill -f <шаблон>` убивает собственную оболочку**: `pgrep -f` матчит и командную строку самого вызова, где уже есть искомое слово. Фильтровать по `readlink /proc/<pid>/exe`, исключать `$$` и `$PPID`, либо обходиться без `pkill`.
- **`ON CONFLICT DO NOTHING` в `executemany`**: `cur.rowcount` показывает число реально вставленных строк, а не размер батча — это нормально, повторный прогон не создаёт дублей.
- **Транзакция в psycopg**: ошибка в одном запросе переводит соединение в состояние «aborted», все последующие запросы падают с `current transaction is aborted` — делать `rollback` или переподключаться.
- **Не брать `information_schema` через прокси `db_compat`**: прокси подставляет схему в имена после FROM/JOIN и превращает `information_schema.tables` в `staging.<db>__information_schema`. Системные имена исключены в `_qualify`, но при работе со схемой напрямую проще использовать `psycopg` без прокси.
- **Курсор нельзя переиспользовать**: после `fetchall()` он пуст; повторный `fetchall()` даёт пустой список — легко принять за «нет данных».

сразу: кириллица превращается в символы замены (`\ufffd`), и дальше имена
регионов **схлопываются по длине** — 85 регионов становятся 35, разные
субъекты сливаются в неразличимые строки, данные уходят в «категорию» под

исходниках.

— запятая с кавычками. Без автоопределения новые выпуски читаются одной
колонкой (520 колонок становятся одной).
**Коды полей — только из справочника.** `profitorg_structure.csv` даёт
соответствие `GA`/`GB`/`G1`… русским названиям (602 поля). Не хардкодить.
**Диагностика дефекта:**

# Гармонизация staging → core: ключ наблюдения и разбор дублей
Класс задач: перенос staging-таблиц в `core.observation_v2` (рубежами). Каждый
рубеж — отдельный скрипт `scripts/harmonize_N_*.py`, идемпотентный по тегу метрики.
## Порядок работы над рубежом
1. **Разведка.** Для каждой таблицы: колонки и типы, заполненность полей периода
   (`month IS NULL` = годовые и месячные ряды лежат вместе), `SELECT count(DISTINCT source)`,
   наличие колонки-кода региона.
2. **Симуляция ключа** на staging до записи (Python, `Counter` по кортежу ключа).
   Потеря обязана быть 0. Ненулевая потеря — искать потерянное измерение, а не
   глушить нумерацией строк.
3. **Точка возврата:** git-тег + `pg_dump -Fc -t core.observation_v2` в бакет.
   `pg_dump` вызывать с `-h localhost` (не `127.0.0.1`) — иначе не подхватится `.pgpass`.
4. **Прогон.** Тяжёлые таблицы — на ВМ, не на VDS (там ~1 ГБ RAM, OOM).
5. **Сверка:** подготовлено == строк у метрик рубежа; истинных дублей по ПОЛНОМУ
   ключу (включая `release_id` и `sub_dimension`) — 0.
6. Документ в `queries/`, коммит, запись в `log-tech.md`, урок в навык.
## Ключ наблюдения
`(metric_id, region_id, frequency_id, period_start, source_id, release_id, assessment_type, sub_dimension)`
Что куда относится:
| Признак | Место |
|---|---|
| Первичная публикация (`source` внутри staging) | `release_id` |
| Разрез внутри публикации (рынок, валюта, продукт, вид ряда) | `sub_dimension` |
| Состав региона («Архангельская без АО» против «с АО») | `sub_dimension` |
| Издание сборника, снапшот-дата | `release_id` / отдельная метка релиза |
| Порядковый номер строки | `sub_dimension`, ТОЛЬКО при реальной коллизии |
### Колонка `source` внутри staging = первичная публикация
Проверять ПЕРЕД гармонизацией любой таблицы:
Больше одного значения — различие обязано попасть в ключ, иначе одинаковые
значения разных публикаций схлопнутся и задвоятся при агрегации. Симптом в
датасете: одна метрика по одному региону и периоду выдаётся дважды с одинаковым
значением. Правильное место — `release_id`, не `sub_dimension`: это разные
публикации одного показателя, а не разрезы одного наблюдения.
### Поля, входящие в ON CONFLICT-ключ, нельзя обрезать
Обрезка `substring`/срезов строки в полях ключа даёт ТИХУЮ потерю: подписи
различаются после N-го символа и схлопываются. Ловилось дважды — на подписях
длиннее 70 символов и на именах регионов длиннее 80. Обрезку в ключевых полях
не применять вовсе; для читаемости заводить отдельную колонку отображения.
### Порядковый номер строки — только при реальной коллизии
Номер как универсальная защита засоряет подразрез техническими хвостами
(`строка 840`), которые портят легенды в DataLens. Но и убрать целиком нельзя:
бывают строки, различающиеся ТОЛЬКО значением, и сборщик утрачен.

### Идемпотентность обязательна
Скрипт рубежа удаляет строки своего прошлого прогона, иначе повторный запуск
задваивает данные. Признак — тег рубежа у метрик:
              WHERE m.metric_id = o.metric_id AND m.tags @> ARRAY['<тег>']);
Перед этим убедиться, что тег создаёт только этот рубеж (посчитать строки).
Обход очистки — переменной окружения для отладки (`SKIP_CLEAN=1`).
## Разнообразие форматов периода
Главный источник ложных потерь: неучтённый формат схлопывает несколько
периодов в один. Проверять ДО симуляции:
| Что встречается | Вид | Решение |
| колонка `q` вместо `quarter` | `q=1..4` | фолбэк `g('quarter') if ... is not None else g('q')` |
| период `2023Q4` | у панелей МСФО | regex `^(\d{4})Q(\d)` ПЕРЕД разбором года |
| снапшот-дата не квартальная | `20200407`, `20201123` | период = (год, квартал из месяца), полная дата → `sub_dimension` |
| год и месяц отдельно | `report_year`, `report_month` | брать оба, не только год |
Таблица из остатка может быть (а) полным дублем перенесённого, (б) дополнением,
(в) тем и другим сразу — часть колонок дублирует, часть новая. Проверять так:
У полного дубля `count(*)` совпавших по значению пар равен числу строк.
Удалять по релизу и метрике, а не по таблице целиком: из «дублирующей» таблицы
часто извлекается новое (медианные цены, аренда).
**Метрики-тёзки — не всегда дубли.** Одинаковые названия бывают у разных
первичных публикаций (один показатель в сборнике «Жилищное хозяйство» и в
«Строительстве в России»); они различаются релизами, и совпадение части значений
— пересечение периодов, не копии. Проверять `count(DISTINCT metric_id)` в группе
по имени и наличие наблюдений у ОБОИХ кодов.
## Приборка метрик после гармонизации
Осиротевшие метрики (без наблюдений) делятся на три класса, и удалять нужно не все:
1. **С живым близнецом** (то же имя, есть наблюдения у другого кода) — удалять.
2. **Вытесненные** (данные теперь под новым кодом) — удалять.
3. **Источник отсутствует** (в staging нет соответствующих строк, например нет
   строк с «темп роста») — осознанно удалять или оставлять как задел.
Суффиксы `_N` в коде метрики бывают двух видов: **артефакт повторного прогона**
(базовый код свободен → переименовать обратно) и **корректная коллизия** (базовый
код занят ДРУГИМ показателем → оставить). Скрипт чистки ограничивать метриками
с тегом рубежа и кодами, не начинающимися с цифры: шаблон `_[0-9]+$` ловит
осмысленные коды вида `01_01_01` (метрики панели и ДОМ.РФ).
## Легаси-таблица блокирует чистку
Если удаление метрики падает с `ForeignKeyViolation` на `observation_metric_id_fkey`,
рядом живёт **старая таблица наблюдений** (`core.observation` предыдущего рубежа),
не выведенная из эксплуатации. Проверять:
SELECT count(*) FROM core.observation o
WHERE NOT EXISTS (SELECT 1 FROM core.observation_v2 v
  WHERE v.metric_id=o.metric_id AND v.region_id=o.region_id AND v.period_start=o.period_start);
Уникальных строк обычно мало, и они уже есть в целевой под другими кодами.
Правило: **заменив таблицу, выводить старую явно** — иначе она копит данные,
путает запросы и блокирует чистку метрик по внешнему ключу.

## Любая разрушительная операция с БД — только через dry-run
Правило поверх всех остальных: скрипт, который что-то удаляет или переименовывает
в БД, ОБЯЗАН иметь режим сухого прогона и запускаться так сначала.
Флаг-паттерн: `APPLY=1 python3 script.py` или `--apply` (без флага — только отчёт).
Сухой прогон печатает: что будет удалено, С ЧЕМ именно (не только счётчики —
конкретные коды и имена), и сколько строк затронуто.
**Почему это не формальность.** Дважды за одну сессию сухой прогон поймал ошибку,
которая испортила бы данные молча:
1. **Шаблон чистки кодов метрик `_[0-9]+$` ловил легитимные коды** вида `01_01_01`
   (осмысленные коды панели/ДОМ.РФ) и схлопывал бы их в `01_01`. Правило:
   прежде чем чистить суффиксы, ПРОВЕРИТЬ, чем занят базовый код — если там другой
   показатель (не дубль), суффикс законен и трогать нельзя. Ограничивать чистку
   тегом рубежа и явно исключать коды, начинающиеся с цифры.
2. **Внешний ключ не учли** — удаление метрик упало на
   `ForeignKeyViolation ... referenced from table "observation"`, потому что в БД
   осталась legacy-таблица. Проверять ссылки перед удалением:
**Различать дубли и совпадения имён.** Одинаковые названия у нескольких метрик —
НЕ всегда дубли. Прежде чем чистить, сверить пары по ключам (регион + период +
значение): если ключи различаются хотя бы частично и различаются релизы — это
разные первичные публикации одного показателя, обе нужны. Удалять только тогда,
когда ключи (не имена!) полностью перекрываются.
**Точка возврата до применения.** git-тег со смысловым именем
(`backup/before-<операция>-<дата>`) + дамп затронутых таблиц в бакет
(`pg_dump -Fc -h localhost ...`). Сообщать пользователю путь восстановления —
он ожидает обратимости разрушительных операций.
## Загрузка «широких» XLSX-публикаций (Росстат/ЦБ)
Перед разбором любого XLSX, где данные лежат по сетке «годы в строках ×
месяцы/кварталы в колонках», **обязательно** прочитать
`references/wide-xlsx-row-identity.md`. Там ключ идентичности ряда (шесть
элементов) и шесть ловушек, каждая из которых тихо дробит один ряд на сотни
счётчике дублей.
Два обязательных приёма из него сразу:
- **Замер коллизий через `count(DISTINCT value)`**, а не через количество
  дублей: `dv = 1` — безобидный повтор, `dv > 1` — реальная потеря данных.
- **Правки парсера — одним патчем на функцию, а не цепочкой мелких.** При
  отладке идентичности ряда не менять кусок кода за куском: в скрипте
  циклично зависит несколько переменных (имя ряда, номер строки подписи,
  блок, имя блока), и последовательные точечные правки сбивают логику
  быстрее, чем чинят. Сначала воспроизвести конкретный случай на данных
  (`parse_sheet` + вывод триплетов для одного ряда), найти точную причину,
  затем переписать функцию целиком.
- **Не редактировать большой скрипт через `execute_code` с heredoc.** Тройные
  кавычки в тексте SQL/Python конфликтуют с обрамлением строки и ломают
  синтаксис с непонятной ошибкой. Мелкие правки — только через `patch`,
  полная перезапись — через `write_file`.
## Filter значений наблюдений
Никогда не использовать `value > 0` при выборке наблюдений: это отбрасывает
около 19% витрины, из которых ~93% — настоящие нули и отрицательные значения.
Подробно (диагностический SQL, границы применимости) —
по документации (ТЗ датасета, FAQ) — проверять grep-ом весь репозиторий.
- `references/wide-xlsx-row-identity.md` — идентичность временного ряда в «широких» XLSX: ключ из шести элементов, шесть ловушек (номер строки данных, номер колонки месяца, повтор подписи по годам, последовательные подтаблицы, год-разделитель, период накопления), диагностика коллизий по значениям, обязательная идемпотентность, разделение staging → core.

## Агентские операции на YC-ВМ research-db
Управление — через S3-бакет `agent-vm-exchange` (SSH с зарубежного VDS блокирован гео-фильтром).
**Загрузка больших файлов на ВМ.** `yc storage s3api put-object` падает с `tcsetattr: Inappropriate ioctl for device` на файлах крупнее ~100 МБ. Использовать `rclone` (remote `yc-s3` уже настроен): `rclone copyto <файл> yc-s3:agent-vm-exchange/<ключ> --s3-chunk-size 64M`. На 825 МБ ушло 3м50с (~0.3 МБ/с) — медленно, но надёжно.
**Дедупликация команд.** Агент на ВМ сравнивает md5 загруженного `_cmd/command.sh` с предыдущим и молча пропускает идентичный. Повторная отправка того же текста НЕ выполнится — добавлять уникальную метку (`echo '--- метка: $(date +%s) ---'`) или менять содержимое.
**Цикл управления:** записать `_cmd/command.sh` → ждать ~45 с (агент опрашивает каждые 20 с) → прочитать `_cmd/output.txt` и `_cmd/output.stamp` (stamp содержит rc и ts — проверять его, чтобы не принять старый вывод за новый).
**Подключение к PostgreSQL:** роль `wiki` через TCP с паролем в `/home/ubuntu/.pgpass` (права 600); `PGDSN="postgresql://wiki@localhost/research_wiki"`, `PGPASSFILE=/home/ubuntu/.pgpass`. Пароль генерируется на самой ВМ и не покидает её.
**Замечание по счётчикам объектов SQLite:** `SELECT COUNT(*) FROM sqlite_master WHERE type='table'` даёт на 1 больше реальных таблиц, если есть `sqlite_sequence` (автоинкремент служебная). Фильтровать `AND name NOT LIKE 'sqlite_%'`.
# Гармонизация staging → core.observation (research-wiki)
Рубежи: 1 (справочники), 2 (метрики), 3/3б (наблюдения Росстат + панель),
4 (ДОМ.РФ), 5 (остаток). Ключ наблюдения:
`(metric_id, region_id, frequency_id, period_start, source_id, release_id, assessment_type, sub_dimension)`.
## Правило 1 — не обрезать поля, входящие в ключ ON CONFLICT
Обрезка подписей (`subsection` до 70 симв., `unit` до 28) склеивает разные строки:
длинные подписи вида «Общая площадь жилых помещений, купленная… у граждан vs у юрлиц»
дают одинаковый префикс → строки схлопываются в одну, часть теряется молча.
Урок: любую обрезку поля, попадающего в `sub_dimension` или в ключ `ON CONFLICT`,
считать ошибкой — потеря проявляется только при сверке числа строк по группам.
**Обнаружение потери:** считается не «всего строк», а строк с заполненным подразделом;
если `count(sub_dimension non-null) < count(*)` — есть тихая потеря, искать обрезку.
Контрольная сходимость — **13/13 изданий**, и число строк равно числу строк источника;
обязательно сверять ещё и ноль дублей по полному ключу, иначе потеря маскируется дублем.
## Правило 2 — учти КАЖДУЮ колонку-измерение источника, включая `source`
Самая дорогая ошибка класса: в staging-таблице есть колонка `source` (первичная
публикация внутри одной staging-таблицы), а гармонизатор берёт `source_id` на уровне
всей таблицы — различие не выносится ни в `sub_dimension`, ни в `release_id`.
Проверка перед прогоном:
SELECT count(DISTINCT source), count(*) FROM staging."<table>";
Если источников > 1 — их надо различить в подразрезе, иначе строки с одинаковым
значением выглядят дублями и задваиваются при агрегации (`MIN(value)` по группе
не лечит семантику, только маскирует). Реальный пример: `housing_prices_quarterly`
(2 источника: сборник Росстата `info-stat-*` vs `cbr_bulletin_74`) и
`building_materials_monthly` (10 источников, 2 456 строк).
Это тот же класс, что и `unit` сплошь NULL в `domrf_indicators`: в SQL NULL не
группируется, поэтому колонка не различает строки. **Перед гармонизацией любой таблицы
проверять каждую колонку-измерение на «все NULL» и на «одно значение»** — оба случая
означают, что измерение не работает.
## Правило 3 — потеря измерений: восстанавливать по порядку строк
Когда контекст потерян (единицы/подписи съехали в колонку региона), позиция строки
восстанавливает соответствие: порядок строк в staging совпадает с порядком листа
источника. Строится `rowseq` (порядковый номер) и сопоставление идёт по нему.
Коллизия-ловушка: счётчик `rowseq` сбрасывается на каждом листе книги → строки
разных листов слипаются. Лечение — **добавить имя листа в подразрез**. Реальные цифры:
потеря 74 043 → 9 736 → 0.
## Правило 4 — «в т.ч.» не относится к основным строкам
При классификации подписей `CONT_RE` не должен матчить «в т.ч.» — иначе подчинённая
строка склеивается с основной (пример: две строки «% от строящегося жилья» 0.696 и 0.454
не различались). «в т.ч.» — признак подчинённой строки, а не продолжения основной.

## Семантика значений: что считать мусором, а что данными
Правило, действующее для ВСЕХ источников в витрине:
- `-99999999` — код Росстата «нет информации»
- `-77777777` — код Росстата «скрыто»
- вместе ~27 тыс. строк в витрине
**Фильтр `value > 0` применять нельзя.** Он отбрасывает 19% витрины, из которых
93% — легитимные значения: ~387 тыс. нулей (ноль введённых метров за месяц,
нулевая просроченная задолженность) и ~2,5 тыс. отрицательных (убыток,
Как выглядит ущерб от такого фильтра:
- метрика исчезает из выборки целиком, если все её значения неположительные
  (так пропала `obl` — уровень книги заявок, 82 строки, все отрицательные);
- у метрики занижается число наблюдений и **рвётся ряд** — у `okb` (выдачи
  ипотеки) под фильтром терялось 8 565 нулей из 25 920;
- производные оценки (баллы полезности, покрытие в каталоге) считаются по этим
  числам и тихо занижаются.
Проверка подозрительно «пустой» метрики:
Когда `value > 0` всё же уместен: логарифм, отношение, среднее геометрическое.
Но чаще нуль выпадает сам (`log(0)` → `NULL`) и отдельный фильтр не нужен.
**Плейсхолдеры концентрируются в `regions_panel.db`** (25 384 «скрыто» +
2 423 «нет информации», 143 метрики) и оттуда попадают в витрину. Аналитические
скрипты, читающие SQLite-базы напрямую, их не видят (в `rosstat_construction`,
`cbr_lending`, `fns_tochno_sectors`, `developers_ifrs`, `rosreestr_deals`
плейсхолдеров нет вообще) — но датасет DataLens читает витрину, поэтому
фильтр обязателен в ТДЗ датасета и в каждом рецепте чарта.
## Агрегация большой витрины: батчами, а не одним запросом
(2,17 млн строк) **съедают всю память** — процесс убивается OOM (exit 137).
Одиночный запрос на всю таблицу падает молча, оставляя на диске старый
Рабочий паттерн: идти **батчами по ключам** (по 25 метрик), а результат
каждого батча сразу дописывать в JSONL-файл состояния. Память ограничена
накопленного JSONL в конце, затем удалить состояние.
Признак, что вы наткнулись на это: генератор отрабатывает без вывода и с
`exit=137`, а выходной файл не обновился (сравнивать mtime с `date`).
## Гармонизация оперативных публикаций Росстата в core.observation_v2
Порядок для любого нового XLSX/CSV-издания Росстата (КЭП, «Социально-экономическое
положение», сборники):
1. **Разведка структуры** — `openpyxl.load_workbook(read_only=True, data_only=True)`,
   вывести все листы с размерами, затем заголовки первых ~20 строк 5–6 листов.
   Имена листов могут иметь хвостовые пробелы (`'1.7 '`) — сверять по `.strip()`.
2. **Зафиксировать блоки** — один лист часто = несколько рядов (уровень, yoy, mom),
   разделённых текстовыми строками в колонке 1.
3. **Проверить объём** прототипом парсера на 2–3 ключевых листах до полной загрузки.
4. **Staging** — одна таблица на лист: `staging.<источник>_<издание>__<лист>`.
5. **core.observation_v2** — источник: существующий `rosstat` (id 11), новый не заводить.
6. **Верификация** — сверка с уже имеющимися родственными рядами (годовые итоги,
   квартальные агрегаты), leak-тест, spotcheck.
**Решения, которые нужно принять заранее (иначе переделка):**
- **Блоки = отдельные метрики, не разрез.** В целевой схеме единица измерения
  единицы разные (`bln_rub` против `pct`). Схлопывание в одну метрику с разрезом
  `sub_dimension` делает единицу измерения ложью. В `sub_dimension` писать только
  маркер места (`ряд: КЭП | лист: 1.7`).
- **Версионность через `release_id`.** Каждый выпуск издания — отдельный релиз
  с `release_label` и `content_hash` файла. Оперативные ряды Росстата активно
  пересматриваются; без релиза ревизии затрут старые значения молча.
- **Идемпотентность.** Перед загрузкой проверять `release_label`; если выпуск уже
**Фильтр значений — см. `references/data-validation-cross-source.md`, раздел
«Семантика значений».** Кратко: исключать только `-99999999` и `-77777777`,
никогда `value > 0`.

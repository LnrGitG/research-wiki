# Результаты пилота (этап 3 конвейера показателей)

Связи: [[metric-working-set-review]], [[metric-pipeline-execution-plan]] (гипотеза H-A).

## Дизайн

60 метрик, эталон — золотые метки из evidence-паспортов этапа 2 (сверены с
первоисточниками: шапки и сноски КЭП, методология ЦБ, SQL-проверки).
Стратификация по temporal_type: flow 17, stock 26, index 10, average 4,
price 2, ratio 1. Сплит: 40 tuning / 20 holdout (детерминированный, каждый
третий в страте). Два условия: name_only (имя+код+частота) и evidence
(+методологическая заметка, единица, значения, период). Обе модели через
Nous: z-ai/glm-5.3 и openai/gpt-6-astra, temperature 0.1.

## Главный результат (holdout, после исправления эталона)

| Модель / условие | temporal acc | comparison_base acc | крит. ошибки | валидность |
|---|---|---|---|---|
| GLM / name_only | н/д (сбой батча) | н/д | — | 1 из 2 батчей упал (пустой ответ) |
| GLM / evidence | **1.00** | **1.00** | 0 | 3/4 батча |
| Astra / name_only | 0.85 | 1.00 | 3 (блок 01_02_*) | 4/4 |
| Astra / evidence | **1.00** | **1.00** | 0 | 4/4 |

Tuning-выборка согласуется: name_only ~0.875 у обеих моделей, evidence —
1.00 (после исправления gold-метки kvrse, см. ниже).

## Три вывода

**1. Evidence-пакет — главный фактор качества, а не модель.** Гипотеза H-A
подтверждена: точность temporal_type выросла с 0.85–0.875 до 1.00 у ОБЕИХ
моделей. Разница между моделями в evidence-условии исчезла. Систематические
ошибки name_only сосредоточены в блоке ДОМ.РФ 01_02_*/01_01_* (stock-ряды
помечались как flow: «количество домов в составе проектов» без сноски
«на дату» читается как поток) — то есть ровно там, где имя не несёт
временной семантики. Вывод для конвейера: массовая разметка БЕЗ
evidence-заметок недопустима для stock-семейств.

**2. GLM не хуже Astra по качеству, но менее надёжен по формату.** В
evidence-условии GLM дал 100% точности на holdout, но один батч из четырёх
вернул пустой ответ (у GLM 5.3 non-flash на Nous известная особенность:
reasoning_content без content). Astra стабильно валидна 4/4. Вывод:
GLM+evidence — рабочая лошадка для регулярных семейств (стоимость
практически нулевая: $0.0001 против $0.35 у Astra за прогон);
Astra — для целевых показателей, конфликтов и как контроль выборки.
Ретрай-логика с фолбэком на Astra при пустом ответе GLM закрывает
разницу в надёжности.

**3. Эталон тоже ошибается — независимая проверка обязательна.** Единственная
«ошибка» обеих моделей в evidence-условии (kvrse) оказалась ошибкой моей
gold-метки: я пометил «количество раскрытых счетов эскроу» как stock,
тогда как по методологии это поток раскрытий за месяц. Модели ответили
правильно. Исправлено в pilot_build.py и паспорте партии 2. Урок:
золотые метки нужно верифицировать по методологии источника до
использования в приёмке; расхождение «все модели против эталона» —
сигнал проверять эталон, а не модели.

## Стоимость и масштабирование

Полный прогон 4 ячеек × 60 метрик: $0.35 (Astra) + ~$0 (GLM).
Масштаб на весь корпус 1 829 preliminary: GLM+evidence ≈ $0.2–0.5,
контрольная выборка Astra 10% ≈ $3–5. В пределах бюджета конвейера.

## Решение по эскалации (для этапа массовой разметки)

1. Детерминированные правила — первыми (как в metric_registry.py).
2. GLM + evidence-заметки — однородные семейства с валидными ответами
   (с ретраем и фолбэком на Astra при пустом ответе).
3. Astra — целевые показатели nowcasting, конфликтные и needs_link случаи,
   плюс случайная 10% выборка уверенных ответов GLM.

## Ограничения

Выборка стратифицирована по типам из паспортов, но невелика (60);
нулевой holdout-результат не гарантирует нуля ошибок на корпусе
(блок 01_02_* паспортизирован группой без индивидуальных заметок —
для него evidence-заметки нужно достроить). GLM-пустые ответы —
регулярный риск, требующий ретрая в проде. Стоимость GLM из usage
($0.0001) может отражать промо-тариф Nous — перед продом сверить
биллинг подписки.

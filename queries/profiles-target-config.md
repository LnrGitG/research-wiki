# Профили под целевую конфигурацию Hermes 2.0

Записка 19.09.2026. Ответ на вопрос: какие профили создать, чтобы сетап отвечал
целевой конфигурации «AI-copilot для исследователя-экономиста» (ТЗ HERMES v2).
Дополняет `queries/hermes-v2-design-review.md` (разбор ТЗ) и `log-tech.md`
(разбор канбана) — здесь только вопрос профилей.

## Что такое профиль в Hermes (проверено)

**Профиль — не «набор навыков» и не «режим».** Это независимая инсталляция
агента: свой `config.yaml`, `.env`, `SOUL.md`, каталог навыков, память
(`MEMORY.md` / `USER.md`), история сессий (`state.db`), свои cron-джобы.
Живёт в `~/.hermes/profiles/<имя>/`, переменная `HERMES_HOME` указывает на
его корень.

Ключевое свойство, из которого всё следует: **профили — независимые острова
без живого наследования конфига**. Копирование происходит один раз при
создании (`--clone`, `--clone-all`), дальше ветки расходятся. Изменение
навыка или настройки в одном профиле не видно в другом.

Второе: **рабочий каталог и репозиторий общие**. Все профили смотрят на один
`~/research-wiki` и одну базу `research_wiki` в YC. Профиль изолирует
контекст и память агента, но не данные и не git.

## Что даёт профиль (четыре рычага)

Профиль оправдан, только если роль отличается хотя бы двумя из четырёх:

1. **Набор навыков.** Индекс навыков в системном промпте — 9 841 символ при
   92 категориях (сейчас). Профиль с ~15 релевантными навыками вместо 76
   активных экономит около 6,5 тыс. символов в каждом запросе.
2. **Модель.** У профиля своя модель в `config.yaml`. Это позволяет держать
   дорогую reasoning-модель там, где она нужна, и дешёвую — на рутине.
3. **Триггер.** Профиль вызывается иначе: cron-джоб, задача канбана
   (`--assignee <профиль>`), делегирование. Диалоговый профиль отвечает в
   Telegram.
4. **Память.** Своя `MEMORY.md` и `USER.md`. Фоновой роли профиль
   пользователя не нужен вовсе — это минус ~2,6 тыс. символов («кто такой
   пользователь» ей знать незачем).

## Ограничение по Telegram (важное)

**Один бот-токен Telegram держит ровно один профиль.** `profile create
--clone-channels` прямо отказывает, когда источник обслуживается живым
мультиплексированным gateway: два профиля на одном токене создают коллизию.

Мультиплексирование (`gateway.multiplex_profiles: true`) даёт **один
gateway на все профили** — это решает проблему памяти (не нужно по процессу
на профиль) и даёт HTTP-платформам ingress вида `/p/<профиль>/`. Но для
Telegram правило не меняется: разговорным остаётся **один** профиль.

Практический вывод: у нас один бот. Значит диалог с вами ведёт `default`, а
остальные профили — **фоновые**. Их результат попадает к вам через
`cron --deliver bot-chat[:profile]` — механизм доставки вывода фонового
профиля в канонический чат разговорного.

## Предлагаемая конфигурация: 4 профиля

Ровно по осям ТЗ (MONITORING / ANALYSIS / RESEARCH / VIEW), но без
дробления: четыре роли, а не семь, потому что часть категорий ТЗ — это
адаптеры внутри одного навыка, а не отдельная личность агента.

| Профиль | Роль по ТЗ | Триггер | Модель | Навыки | Память |
|---|---|---|---|---|---|
| `default` | VIEW, диалог | Telegram, вызов человеком | reasoning (текущая) | полный набор | USER + MEMORY |
| `monitor` | MONITORING | только cron | дешёвая / без LLM | источники, harvest, release-calendar | только MEMORY |
| `analyst` | ANALYSIS | делегирование, канбан | сильная reasoning | nowcasting, DS, hypothesis-tracker | только MEMORY |
| `librarian` | RESEARCH, knowledge | cron + вызов | средняя | wiki-ingestion, lint, frontend, translation | только MEMORY |

### default — copilot (остаётся как есть)

Диалог, синтез, Current Economic View, принятие решений. Единственный
профиль с Telegram-ботом и полным профилем пользователя. Ничего не меняем.

### monitor — контур мониторинга

Все сборщики, cron-загрузки, календарь публикаций, алерты. Модель дешёвая
или вообще не нужна: большинство проверок (свежесть данных, наличие файла,
статус релиза) — детерминированный Python. Именно здесь закрывается
проблема «7 cron-джобов запинены на glm-5.3-flash и молча пропускаются при
дрейфе модели»: в изолированном профиле можно задать `fallback_model`, не
влияя на разговорную сессию.

### analyst — расчётный контур

Эконометрика и nowcasting: `midas-nowcasting`, `duckdb-analytics`,
`jupyter-live-kernel`, `hypothesis-tracker`. Смысл отдельного профиля —
**дорогая модель там, где она реально нужна**, и изоляция тяжёлых
вычислений от разговорного контекста. Вызывается делегированием или задачей
канбана, возвращает результат в `default`.

### librarian — контур знаний

Обслуживание вики: ingestion статей, `lint_wiki`, каталог метрик, векторный
поиск, переводы. Работает по расписанию и по вызову. Модель средняя —
задачи шаблонные.

## Что даёт эта конфигурация

**Экономия промпта.** Разговорный профиль перестаёт тащить навыки
сборщиков и эконометрики; фоновые — не тащат профиль пользователя.

**Разные модели по цене задачи.** Сейчас все 7 cron-джобов и диалог сидят
на одной модели. Профили позволяют развести: мониторинг — дёшево,
анализ — дорого.

**Устойчивость cron.** Fallback задаётся на профиль, а не глобально.

**Гигиена контекста.** Тяжёлый сбор данных не засоряет диалог.

## Риски (честно)

1. **Память фрагментируется.** Четыре `MEMORY.md` вместо одного. Знания о
   сетапе, добытые в одном профиле, не видны в другом. Смягчение: то, что
   должно быть общим (конвенции, пути, инварианты), держать в `AGENTS.md`
   репозитория и в спеке, а не в памяти агента.
2. **Один git-репозиторий, параллельная запись.** Два профиля, коммитящие
   одновременно, дадут конфликт. Смягчение: коммитит только `librarian` и
   человек, остальные пишут во временные ветки/worktree, либо в БД.
3. **Обновления тяжелее.** `hermes update` снэпшотит и перезапускает все
   профили. Механизм это умеет, но время растёт.
4. **Профили расходятся.** Через полгода `monitor` будет на другой версии
   навыков, чем `default`. Это цена изоляции, а не дефект, но требует
   дисциплины: общее — в репозитории, не в профиле.
5. **Память VPS.** Сейчас 961 МБ всего, gateway 564 МБ (пик 609 МБ), swap
   отсутствует. Мультиплексирование убирает второй gateway, но каждый
   профиль держит свою `state.db` (текущая — 561 МБ) и поднимает процессы
   при cron-запуске. **Увеличение VPS обязательно** до внедрения: разумный
   минимум — 4 ГБ ОЗУ и диск от 40 ГБ.

## Порядок внедрения

1. **Увеличить VPS** (4 ГБ ОЗУ, диск 40+ ГБ, включить swap). Делать первым:
   без запаса по памяти мультиплексирование упрётся в OOM.
2. **Создать `monitor`** — самый автономный профиль, наименьший риск.
   `hermes profile create monitor --clone --no-clone-of-channels`, затем
   урезать навыки до сборщиков, задать дешёвую модель и fallback.
   Перевести на него cron-джобы загрузки.
3. **Проверить мультиплексирование.** `hermes gateway migrate --multiplex
   --dry-run` (preflight проверит коллизии токенов), затем боевой запуск.
4. **Создать `analyst`** — после того как понадобится первая тяжёлая задача;
   до этого его роль закрывает делегирование из `default`.
5. **Создать `librarian`** — когда вики-обслуживание станет регулярным.

Шаги 4 и 5 — по факту необходимости, не авансом. ТЗ требует минимально
достаточную архитектуру: три профиля (`default`, `monitor`, `librarian`)
закрывают почти всё; `analyst` имеет смысл, когда появится регулярный
расчёт с сильной моделью.

все изменения идут в **приватный главный** репозиторий, в публичный
отправляется только база знаний (данные, статьи, публикации). Относится к

## Предлагаемая схема

### Два репозитория с разными задачами

**`research-wiki-private`** (приватный, **главный**) — источник правды.
Здесь всё, включая то, что не должно быть публичным:

```
papers/ reviews/ concepts/ entities/ comparisons/   # знания (зеркалится в публичный)
annotations/ models/ templates/                      # знания (зеркалится)
data/*.csv data/catalog.yaml hypotheses.yaml         # данные (зеркалится)
docs/                                                # витрина GitHub Pages (зеркалится)
scripts/ db/                                         # ИНФРАСТРУКТУРА — только приватно
queries/                                             # рабочие записки — только приватно
raw/ (симлинк на YC)                                 # только приватно
log.md log-tech.md AGENTS.md SCHEMA.md MEMORY.md USER.md
```

**`research-wiki`** (публичный) — **витрина знаний**. Содержит только базу
знаний: `papers/`, `reviews/`, `concepts/`, `entities/`, `comparisons/`,
`annotations/`, `docs/`, `data/` (без служебных баз), плюс `index.md`,
`MOC.md`, `catalog.yaml`, `bibliography*.md`. Ничего про инфраструктуру.

### Что куда попадает — правило раздела

| Категория | Приватный | Публичный | Почему |
|---|---|---|---|
| Статьи, рецензии, концепты, сущности | да | **да** | ядро вики, ради него сайт |
| Данные CSV, каталог, гипотезы | да | **да** | исследовательский результат |
| Витрина `docs/` (Pages) | да | **да** | публикация для чтения с телефона |
| Скрипты сбора, миграции | да | нет | раскрывают источники и обходы |
| `queries/` — рабочие записки | да | нет | содержат IP, топологию, решения |
| `log.md`, `log-tech.md` | да | нет | хроника с адресами и деталями |
| `AGENTS.md`, `SCHEMA.md`, `MEMORY.md`, `USER.md` | да | нет | конвенции и профиль |
| `db/`, миграции, дампы схемы | да | нет | устройство базы |

### Техника: главный + зеркало через git subtree

**Рекомендую `git subtree`, а не `submodule`.** Причина: содержимое
публичного репозитория — это **подмножество файлов главного**, а не отдельный
проект. Submodule держал бы публичный как внешнюю зависимость с собственным
циклом коммитов, и пришлось бы вести две истории. Subtree позволяет
отправлять срез каталогов из главного одной командой.

Рабочий процесс:

```bash
# 1. Основная работа — всегда в главном (приватном)
cd ~/research-wiki-private
git add -A && git commit -m "..." && git push origin main

# 2. Публикация знаний в витрину — только явные каталоги
git subtree push --prefix=papers  public main
```

Честное ограничение: `git subtree push --prefix` работает **по одному
каталогу**. Для восьми каталогов это восемь вызовов, а `docs/` при этом
ссылается на `papers/`. Практичнее два варианта на выбор:

**Вариант А — публичный репозиторий собирается скриптом.** В приватном
лежит `scripts/publish_wiki.py`, который копирует разрешённые каталоги в
отдельный клон витрины, коммитит с сообщением, наследующим сообщение
главного коммита, и пушит. Один запуск — одна публикация. Плюс: полный
контроль над составом, можно добавить проверку «нет ли IP в публикуемом».
Минус: нужен скрипт.

**Вариант Б — subtree по каждому каталогу.** Без своего кода, но восемь
команд и риск рассинхронизации `docs/` с `papers/`.

Я за **вариант А**: он даёт точку, куда естественно встроить проверку на
утечки, а состав публичного репозитория становится явным списком в коде, а
не подразумеваемым.

### Разделение коммитов: что считать «изменением вики»

Правило простое и проверяемое: **публикуется то, что читает человек;
не публикуется то, что читает машина или обслуживает её**.

- Коммит трогает `papers/`, `reviews/`, `concepts/`, `entities/`,
  `comparisons/`, `annotations/`, `data/*.csv`, `docs/` → **публикуется**.
- Коммит трогает `scripts/`, `db/`, `queries/`, `log*.md`, `AGENTS.md`,
  `raw/` → **только приватный**.
- Смешанный коммит → публикуется только разрешённая часть; сообщение в
  витрине получает пометку `wiki: <исходное сообщение>`.

## План перехода (осторожный, с точками возврата)

**Шаг 1. Точка возврата.** Тег на текущее состояние обоих репозиториев плюс
полный бэкап `research-wiki` в бакет (архив уже 528 МБ, влезет в
`wiki-research`). Без этого не начинать.

**Шаг 2. Создать `research-wiki-private`** и залить текущее состояние целиком
— тогда приватный сразу становится главным, а публичный — производным.

**Шаг 3. Провести чистку публичного репозитория от служебного.** Убрать
`scripts/`, `db/`, `queries/`, `log*.md`, `AGENTS.md`, `SCHEMA.md`,
`MEMORY.md`, `USER.md`. Это первая публикация, где заодно закрывается утечка
IP ВМ.

**Шаг 4. Написать `scripts/publish_wiki.py`** с фильтром состава и проверкой
на IP, ключи и пути. Сухой прогон по умолчанию, применение по `APPLY=1` —
как в остальных наших скриптах.

**Шаг 5. Обновить `AGENTS.md`** правилом: рабочий репозиторий —
приватный, публикация — явным запуском, состав задан списком в скрипте.

**Шаг 6 (отдельное решение).** История публичного репозитория остаётся
528 МБ с четырьмя файлами, содержащими IP, и тяжёлыми объектами. Полная
очистка требует `git filter-repo` и перезаписи истории — операция
разрушительная для всех клонов. Без неё IP остаётся в старых коммитах
публичными. Это надо решать отдельно и осознанно.

## Что даёт схема

**Закрывается утечка топологии.** IP ВМ, имя хоста, идентификатор машины,
параметры DataLens уходят из публичного доступа в текущем состоянии. Полное
закрытие требует шага 6.

**Разделяются аудитории.** В публичном остаётся то, ради чего сайт
существует, — знания. Служебное перестаёт быть витриной.

**Приватный становится источником правды.** Сейчас публичный репозиторий
одновременно главный, что заставляет либо скрывать служебные каталоги в
`.gitignore` (и терять их из git вовсе), либо публиковать лишнее.

**Появляется точка контроля публикации.** Явный скрипт с проверкой — место,
где утечка ловится до пуша, а не после.

## Риски и что надо решить

**Двойная работа с remotes.** Привычка `git push` в публичный сломается —
два репозитория требуют дисциплины. Смягчение: алиас в конфиге и правило в
`AGENTS.md`.

**История остаётся публичной.** Пока шаг 6 не сделан, старые коммиты
публичного репозитория содержат IP и служебные файлы. Закрытие — только
перезаписью истории.

**Размер.** 528 МБ `.git` — это цена истории с PDF и БД. У приватного
репозитория она та же. Если делать шаг 6, заодно можно вычистить и тяжёлые
объекты, но это ломает все существующие клоны.

**Obsidian и мобильное чтение.** Сейчас пользователь читает вики с телефона
через Obsidian, привязанный к репозиторию. Надо проверить, к какому именно —
если к публичному, то после переноса служебного он сломается для тех
каталогов, которые уйдут в приватный.

**Проверка на утечки требует списка шаблонов.** «Нет ли IP» — проверяемо;
«нет ли ещё чего-то чувствительного» — только по списку. Первая версия
фильтра закроет известное (IP, `id_yc`, `ubuntu@`, пути `~/.hermes`),
дальше список расширяется по мере находок.

## Что предлагаю решить

1. **Идти ли по этой схеме** (приватный главный + публичная витрина знаний)
   или ограничиться переносом служебного из публичного?
2. **Шаг 6 сейчас или потом?** Перезапись истории закроет IP в старых
   коммитах, но сломает клоны и потребует времени.
3. **Как устроено мобильное чтение** — Obsidian на публичном или на
   приватном репозитории? От этого зависит, что можно убирать.

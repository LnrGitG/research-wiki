# Схема регистрации изменений: приватный главный + публичный wiki

Записка 19.09.2026 (редакция 2). Все изменения идут в **приватный главный**
репозиторий, в публичный отправляется только база знаний. Относится к
профилю AI-copilot.

Правки редакции 2 по уточнениям владельца: **IP переназначается** (вопрос
утечки снимается, история не переписывается), **Obsidian настроим позже на
публичном** (мобильное чтение не блокирует работу).

## Два репозитория

**`research-wiki-private`** (приватный, главный) — источник правды, всё:

```
papers/ reviews/ concepts/ entities/ comparisons/ annotations/   знания
data/ catalog.yaml hypotheses.yaml                               данные
docs/                                                            витрина Pages
scripts/ db/                                                     инфраструктура
queries/                                                         рабочие записки
logs: log.md log-tech.md; AGENTS.md SCHEMA.md MEMORY.md USER.md
raw/ (симлинк на YC Object Storage)
```

**`research-wiki`** (публичный) — витрина знаний. Только то, что читает
человек.

## Правило раздела

**Публикуется то, что читает человек. Не публикуется то, что читает машина
или её обслуживает.**

| Категория | Приватный | Публичный | Почему |
|---|---|---|---|
| `papers/`, `reviews/`, `concepts/`, `entities/`, `comparisons/`, `annotations/` | да | **да** | ядро вики, ради него сайт |
| `data/*.csv`, `data/catalog.yaml`, `hypotheses.yaml` | да | **да** | исследовательский результат |
| `docs/` (витрина Pages) | да | **да**, после чистки | публикация для чтения с телефона |
| `scripts/`, `db/` | да | нет | раскрывают источники, обходы, схему БД |
| `queries/` | да | нет | рабочие записки: топология, решения, параметры |
| `log.md`, `log-tech.md` | да | нет | хроника с адресами и деталями |
| `AGENTS.md`, `SCHEMA.md`, `MEMORY.md`, `USER.md` | да | нет | конвенции и профиль |
| `raw/` | да (симлинк) | нет | тяжёлые исходники, уже вне git |

### Проверка разделения на чистоту

Сверка `wikilinks` показала: **из знаний в служебные каталоги ссылок нет
ни одной** — `papers/` (475 файлов), `reviews/`, `concepts/`, `entities/`,
`comparisons/`, `annotations/`, `data/` все чисты. Обратных ссылок (из
служебного в знания) 164, но они не мешают: приватный видит всё.

Значит разделение пройдёт **без разрыва связей** — редкий случай, когда
структура уже готова. Единственное, что требует внимания, — витрина `docs/`.

### Витрина требует отдельной чистки

`docs/` публикуется на Pages и потому идёт в публичный репозиторий. Но
проверка нашла в ней служебное:

- `docs/faq-database.html` — **IP рабочей ВМ** `89.169.168.214` в таблице
  параметров подключения;
- `docs/help.md` — упоминания `~/.hermes`, команды `hermes backup`;
- `docs/hermes-agent-guide.html` — пути `~/.hermes/scripts/`,
  `~/.hermes/pending/skills/*.json`, `~/.pgpass`.

Часть файлов витрины **генерируется скриптами** из `scripts/`
(`search-index.json`, `vector-embeddings.json`, `data-summary.json`,
`metrics-catalog.json`). То есть витрина — производная от служебного кода,
но публикуется в публичный.

**Решение:** либо в `docs/` остаются только страницы для чтения знаний, а
служебные (FAQ по базе, справочник по Hermes) переезжают в приватный;
либо из публикуемых страниц вычищаются адреса. Первое чище: страница про
устройство БД не относится к базе знаний о жилищном рынке.

## Техника публикации

**`git subtree` не подходит в лоб:** он пушит по одному каталогу, а нужных
каталогов восемь, и `docs/` зависит от `papers/`. Восемь команд на каждую
публикацию дадут рассинхронизацию. **`submodule` тоже не подходит:**
публичный — не отдельный проект, а подмножество файлов главного; submodule
заставил бы вести две истории.

**Рекомендую скрипт `scripts/publish_wiki.py`** в приватном репозитории:

1. берёт явный список каталогов и файлов (состав публичного — список в коде,
   а не подразумеваемое);
2. копирует в клон витрины, исключая служебное;
3. **прогоняет фильтр** на IP, `id_yc`, `ubuntu@`, `~/.hermes`, `~/.pgpass`,
   имена хостов;
4. коммитит с сообщением, наследующим сообщение главного коммита
   (пометка `wiki: ...`);
5. пушит.

Сухой прогон по умолчанию, применение по `APPLY=1` — как в остальных наших
скриптах. Фильтр — то место, где утечка ловится до пуша, поэтому он не
опция, а обязательный шаг.

## План

**Шаг 1. Точка возврата.** Тег на текущее состояние, полный бэкап
`research-wiki` в бакет `wiki-research` (528 МБ влезет). Без этого не
начинать.

**Шаг 2. Создать `research-wiki-private`,** залить текущее состояние целиком
— приватный сразу становится главным, публичный — производным.

**Шаг 3. Вычистить витрину `docs/`.** Убрать служебные страницы (FAQ по БД,
справочник по Hermes) в приватный; из оставшихся убрать адреса. Проверить
генерируемые файлы на IP.

**Шаг 4. Первая публикация.** Убрать из публичного `scripts/`, `db/`,
`queries/`, журналы, `AGENTS.md`, `SCHEMA.md`, `MEMORY.md`, `USER.md`.
Проверка: в публичном не остаётся ни одного упоминания инфраструктуры.

**Шаг 5. `scripts/publish_wiki.py`** с фильтром. Проверить сухим прогоном
на текущем состоянии.

**Шаг 6. Правило в `AGENTS.md`:** рабочий репозиторий — приватный;
публикация — явным запуском; состав задан списком в скрипте.

**Шаг 7. Obsidian на публичном** — когда понадобится мобильное чтение.
Планируется позже, поэтому сейчас ничего не блокирует.

## Что даёт схема

**Разделяются аудитории.** В публичном остаётся то, ради чего сайт
существует, — знания о жилищном рынке. Служебное перестаёт быть витриной.

**Приватный становится источником правды.** Сейчас публичный одновременно
главный, что заставляет либо прятать служебные каталоги в `.gitignore` (и
терять их из git вовсе), либо публиковать лишнее.

**Появляется контроль публикации.** Явный список состава плюс фильтр — место,
где утечка ловится до пуша.

**Снимается вопрос истории.** Раз IP будет переназначен, старые коммиты
теряют ценность для злоумышленника, и перезапись истории (`git filter-repo`,
ломающая клоны) не нужна. Это существенно упрощает переход: остаётся только
новое состояние.

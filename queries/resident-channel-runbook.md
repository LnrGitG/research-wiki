# Резидентный канал с ноутбука: регламент (30.10.2026)

## Зачем

Часть источников закрыта для датацентр-IP: `api.hh.ru` отдаёт **403** и с VPS,
и с ВМ YC; `fedstat.ru` (ЕМИСС) — тоже. Это не ошибка доступа и не вопрос
заголовков: проверено с браузерным User-Agent, результат тот же. Сверка таких
рядов возможна только через канал с резидентным адресом — ноутбук владельца
(Уфанет, Уфа), у которого нет публичного IP.

Отсюда схема: прокси слушает 127.0.0.1 **на ноутбуке**, а SSH-соединение с
ноутбука **на VPS** пробрасывает этот порт назад (`ssh -R`). На VPS прокси
виден как `127.0.0.1:18080`; снаружи его нет: обратный проброс без
`GatewayPorts` слушает только loopback, да и на VPS `GatewayPorts
clientspecified`, поэтому публично порт не поднимается.

## Запуск (две стороны)

**На ноутбуке** (WSL или любой Linux/macOS с `python3`), одна команда:

```bash
ssh lnr@45.157.117.125 'cat ~/research-wiki-private/scripts/resident_channel.sh' | bash
```

Скрипт сам забирает прокси с VPS по SSH, печатает внешний адрес, поднимает
локальный прокси и держит обратный туннель. Останавливается `Ctrl-C` — туннель
и прокси снимаются вместе.

**Перед запуском выключить VPN.** Если внешний адрес окажется датацентровым,
скрипт предупредит: `api.hh.ru` через VPN-выход тоже ответит 403, и вся
конструкция теряет смысл. Ожидаемый адрес — Уфанет (Уфа), не 45.157.117.125,
не 89.169.*, не 153.51.*.

**На VPS** (проверка):

```bash
scripts/resident_check.sh 18080
```

Скрипт сравнивает внешний IP напрямую и через канал, затем прогоняет четыре
источника в двух режимах и печатает вердикт. Коды возврата: 0 — всё штатно,
2 — канал есть, но выход закрыт (забыли выключить VPN), 3 — канал не поднят.

## Как этим пользоваться в коде

Прокси стандартный HTTP CONNECT, поэтому достаточно переменных окружения:

```bash
export HTTPS_PROXY=http://127.0.0.1:18080
export HTTP_PROXY=http://127.0.0.1:18080
python3 scripts/<загрузчик>.py
```

Токен не обязателен: порт доступен только с loopback. Если понадобится
`GatewayPorts` (публикация), прокси запускается с `--token <TOKEN>`, а запросы
идут с `-U <TOKEN>:` (проверка `Proxy-Authorization`, сравнение постоянного
времени). Allowlist хостов в прокси ограничен источниками, которые нужны:
`api.hh.ru`, `fedstat.ru`, `rosstat.gov.ru`, дом.рф, `roschart.ru`, `cbr.ru`,
`ipinfo.io`. Всё остальное — 403, чтобы канал не стал открытым релеем.

## Проверено и не проверено

Механизм проверен на VPS в режиме «прокси есть, выход датацентровый»: канал
поднимается, внешний IP определяется, `api.hh.ru` даёт 403 через канал,
вердикт — «канал есть, но выход тоже закрыт», код возврата 2. Отдельно
проверено, что прокси отвечает `407` без токена и `403` на хост вне allowlist,
а `cbr.ru` через него отдаёт 200.

**Не проверено:** реальный резидентный выход — для этого нужен запуск на
ноутбуке с выключенным VPN. Критерий приёмки: `api.hh.ru` через канал отдаёт
200 и в ответе есть `items`, а внешний IP отличается от адреса VPS.

## Ограничения и правила

- Канал **разовый, по требованию**, не 24/7: ноутбук рабочий, корпоративные
  политики могут ограничивать установку ПО и видимость SSH. Ничего не
  устанавливаем: только `python3` и `ssh`, которые уже есть в WSL.
- Прокси не пишет на диск и не логирует тела запросов — только строку «кто
  куда» в stderr.
- Пока канал поднят, трафик заблокированных источников идёт через домашний
  адрес; крупные выгрузки через него не гоняем — только точечные проверки и
  небольшие выгрузки (hh, ЕМИСС-файлы), тяжёлое берём из зеркала nsEDC.
- Туннель не переживает сон ноутбука: `ServerAliveInterval=30` роняет его
  через ~90 секунд простоя — это нормально, канал поднимается заново одной
  командой.

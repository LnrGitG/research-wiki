# Пользовательский путь: поиск по тексту всех PDF/md с переходом в документ

Разбор по запросу: нужен поиск по всему тексту статей с навигацией из
результатов прямо в документ — «как поиск Яндекса».

## Диагноз текущего состояния

Проверка показала конкретную проблему. Сейчас в `docs/search-index.json`
633 записи, поиск идёт по полям `title` + `abstract`. Но:

- **`abstract` в 515 из 629 случаев короче 100 символов** — это не аннотация,
  а первая строка markdown (часто сам заголовок). Пример: запись с заголовком
  «source_path: Workpapers/...» имеет в abstract просто «# **Housing market
  responses to the mortgage interest deduction**».
- **Покрытие текста: 0.1%.** В индекс попало 0.05 МБ из 36.1 МБ полных текстов.

То есть сейчас ищется не по тексту статей, а по их заголовкам. Найти работу
по фразе из середины статьи невозможно.

Плюс уже есть рабочие компоненты: `viewer.html` открывает документ по ссылке
`?p=путь/к/файлу.md` и рендерит markdown через `marked`. Механизм перехода
в документ существует — не хватает только качественного поиска, который бы
в него вёл.

## Ключевая цифра, определяющая решение

Замер по 709 файлам (32.3 МБ, 3.35 млн слов, 90 549 уникальных терминов):

| Компонент | Размер |
|---|---|
| Словарь (90 549 терминов) | 0.9 МБ |
| Постинги (746 247 пар термин-документ) | 2.2 МБ |
| **Инвертированный индекс целиком** | **3.1 МБ** |
| Со сжатием (brotli ~25%) | **0.8 МБ** |

**Индекс полного текста умещается в 0.8 МБ** — меньше, чем половина текущего
`search-index.json` (0.28 МБ) вместе со всеми остальными JSON на странице.
Это значит: полнотекстовый поиск можно сделать **целиком в браузере**, без
сервера, без базы, без внешних API. Как раз то, что нужно GitHub Pages.

## Пользовательский путь (как у Яндекса)

### Экран 1 — поисковая строка

Пользователь открывает страницу поиска и видит одно поле. Начинает печатать.

**Что происходит под капотом:** по мере ввода (с задержкой 150–200 мс, чтобы
не искать на каждой букве) запрос идёт в локальный индекс. Поиск — логика
AND по словам с учётом морфологии: «эластичность предложения жилья» находит
«эластичности предложения жилья», «эластичность предложения жилищного».

**Почему нужна морфология:** русский язык флективный, без стемминга поиск
по «эластичность» не найдёт «эластичности». Вариант — Snowball-стеммер для
русского (~5 КБ JS) или усечение до 6 символов с проверкой. Стеммер лучше.

### Экран 2 — результаты со сниппетами

Выдача — список карточек, каждая содержит:

- **Заголовок документа** (из frontmatter или первой строки).
- **Тип и метаданные**: статья / перевод / записка; год, автор, теги.
- **Сниппет** — 2–3 фрагмента по 150–200 символов вокруг найденных слов,
  с подсветкой совпадений. Именно то, что делает Яндекс: видно **контекст**,
  а не только факт совпадения.
- **Релевантность**: ранжирование по TF-IDF или BM25 — редкие слова весят
  больше, что отсеивает мусорные совпадения по частым терминам.

Для этого индекс хранит не только «термин → документы», но и позиции слов
(или хотя бы смещения), чтобы построить сниппет. Позиции увеличат индекс
с 3.1 МБ до примерно 6–8 МБ, со сжатием ~2 МБ. Приемлемо.

**Альтернатива без позиций:** хранить сами тексты (32 МБ — многовато для
мобильного) или подгружать нужный файл при клике и строить сниппет на месте.
Второе экономнее: клик по результату → fetch файла → найти совпадения →
показать. Тогда индекс остаётся 0.8 МБ, а текст грузится по требованию.

### Экран 3 — переход в документ на нужном месте

Пользователь кликает результат. Открывается `viewer.html` с документом —
и **прокручивает к первому совпадению с подсветкой**. Это ключевая деталь
«как у Яндекса»: не просто открыть документ, а показать место.

Реализация: ссылка вида `viewer.html?p=papers/foo.md#:~:text=искомая%20фраза`.
Современные браузеры поддерживают **Text Fragments** (`#:~:text=`): при
открытии документа браузер сам находит фразу, прокручивает к ней и подсвечивает
жёлтым. Ничего программировать не нужно — механизм встроен в браузер.

Для браузеров без поддержки — fallback: `viewer.html` получает параметр
`?q=фраза`, после рендеринга ищет её в тексте и программно прокручивает.

### Экран 4 — навигация внутри документа

В `viewer.html` добавить:
- **оглавление** из заголовков markdown (h1–h3) — боковая панель;
- **поиск внутри документа** (Ctrl+F работает и так, но свой поиск может
  подсвечивать все совпадения сразу);
- **хлебные крошки**: тип → категория → документ.

## Что уже готово и что нужно доделать

| Компонент | Статус |
|---|---|
| `viewer.html` с рендерингом markdown | **работает** |
| Переход по ссылке `?p=файл` | **работает** |
| Страница поиска | **есть**, но ищет только по заголовкам |
| Полнотекстовый индекс | **нужно построить** (0.8 МБ) |
| Морфология (стеммер) | **нужно добавить** |
| Сниппеты с подсветкой | **нужно добавить** |
| Прокрутка к совпадению | **нужно добавить** (Text Fragments) |

## Три варианта реализации

### Вариант А — клиентский индекс (рекомендую)

Индекс строится скриптом `scripts/build_search_index.py`: читает все md,
токенизирует со стеммингом, строит постинги, пишет `docs/search-index-full.json`
(сжатый brotli). Страница поиска грузит его и ищет в памяти.

**Плюсы:** нулевая инфраструктура, работает на GitHub Pages, скорость — доли
секунды (3 МБ в памяти), офлайн, ничего не ломается при недоступности YC.
**Минусы:** индекс надо пересобирать при изменении страниц (это делает cron
или commit-hook); 2 МБ на первый запрос с телефона (кэшируется).

### Вариант Б — серверный поиск на YC-ВМ

Yandex Cloud даёт полнотекстовый поиск в PostgreSQL (GIN-индекс + русский
словарь `russian`), а pgvector — семантический. Эндпоинт на FastAPI, страница
ищет через API.

**Плюсы:** морфология и ранжирование из коробки, гибридный поиск (текст+вектор),
не надо пересобирать статику, работает для любых объёмов.
**Минусы:** нужен работающий сервер и публичный HTTPS-эндпоинт; зависимость от
доступности ВМ; вопросы безопасности (публичный API поиска).

### Вариант В — гибрид

Статический клиентский поиск для основной работы (быстро, всегда доступно)
плюс серверный семантический по кнопке «умный поиск». Первый — вариант А,
второй появляется позже, когда накопятся чанки с эмбеддингами.

**Это, по-моему, правильный путь**: начать с А (закрывает 90% потребности
за один вечер), а В добавить, когда заработает векторный слой.

## Сравнение с «поиском Яндекса»

Что делает Яндекс и что реально нужно здесь:

| Возможность Яндекса | Нужно ли | Как |
|---|---|---|
| Поиск по всем словам (AND) | да | инвертированный индекс |
| Морфология | **да** | Snowball-стеммер для русского |
| Подсветка совпадений | да | сниппеты с позициями |
| Ранжирование | да | BM25/TF-IDF |
| Переход к нужному месту | **да** | Text Fragments |
| Исправление опечаток | опционально | редакционное расстояние по словарю |
| Синонимы | опционально | словарь, вручную |
| Персонализация, антиспам | нет | не наш случай |

Главное отличие: Яндекс ищет по всему интернету, здесь — по 709 документам.
Поэтому сложную инфраструктуру не нужно: всё умещается в браузер.

## Порядок работ

1. **Построить полнотекстовый индекс** со стеммингом (0.8–2 МБ) — скрипт.
2. **Переделать `search.html`**: строка + результаты со сниппетами.
3. **Связать с `viewer.html`** через Text Fragments — прокрутка к совпадению.
4. **Обновить индекс в cron** при изменениях в вики.
5. Позже — семантический поиск по эмбеддингам (когда будут чанки).

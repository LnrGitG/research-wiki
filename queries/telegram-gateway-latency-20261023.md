# Скорость ответов через шлюз Telegram: где тратится время

Техническая записка: измерение времени ответа агента в Telegram-канале и
разложение этого времени по компонентам. Данные — штатные логи шлюза
(`~/.hermes/logs/gateway.log`, `agent.log*`) за период, покрытый детальными
записями о вызовах модели.

## Метод

Шлюз на каждый ход пишет строку вида
`response ready: platform=telegram chat=… time=…s api_calls=N response=…`
— это полное время хода от входящего сообщения до готового ответа [[1]].
Длительность отдельных обращений к модели пишет агент
(`agent.conversation_loop: API call #k … latency=…s`), длительность
инструментов — исполнитель (`agent.tool_executor: tool X completed (…s)`) [[2]].
Время хода раскладывается как `wall = LLM + инструменты + прочее`, где
«прочее» — сборка контекста, память, доставка в Telegram, повторы и ожидания.

Оговорка о покрытии: строки `response ready` в `gateway.log` есть с 15.07.2026
(1712 ходов), но детальные вызовы модели в `agent.log*` доступны только с
26.09.2026 (ротация: 3 файла по 5 МБ). Разложение построено на 276 telegram-ходах
за 26.09–21.10.2026. Привязка инструментов к ходу — по идентификатору сессии;
в окне хода на 1,8 вызова в среднем приходится «чужой» вызов соседней сессии,
то есть погрешность есть.

## Результат

Полное время всех 276 ходов — 41,96 ч. Доли:

| Компонент | Часы | Доля |
|---|---|---|
| Обращения к модели (LLM) | 15,27 | 36,4 % |
| Инструменты на машине (терминал, код, файлы) | 15,58 | 37,1 % |
| clarify — ожидание ответа человека | 4,23 | 10,1 % |
| Прочее (контекст, доставка, повторы) | 6,88 | 16,4 % |

Средний ход — 547 с, медианный — 177 с. На подвыборке со стопроцентной
сходимостью (146 ходов): медиана 73 с, из них LLM 51 с, инструменты 13 с,
прочее 5 с — то есть в типичном ходе около 70 % времени занимает модель.

Время концентрируется в тяжёлых ходах: ходы дороже 30 вызовов — это 21 %
хода, но 62 % всего времени; ходы на 1–2 вызова — 28 % ходов, но 6 % времени.
Ускорять одиночный вызов малоэффективно, основная масса времени — длинные
агентные цепочки.

## Латентность модели

Текущая модель `deepseek/deepseek-v4.1-flash-1017`: медиана 4,8 с, среднее
7,2 с на вызов, 84 ток/с генерации, попадание в кэш 98 %. Предыдущая
`deepseek-v4.1-flash` — 9,1 с / 16,3 с и 65 ток/с. Фолбэки медленнее по
генерации: `glm-5.3-flash` 3,6 с / 49 ток/с, `glm-5.2` 6,2 с / 49 ток/с,
`openai/gpt-oss-120b` 3,0 с / 50 ток/с [[3]].

Регрессия на 1466 вызовах текущей модели: `latency ≈ 1,71 с + 0,0088 · out_tokens`
(r = 0,60; ~114 ток/с на марже). То есть время вызова почти линейно по числу
сгенерированных токенов, а фиксированная часть (префилл + очередь) всего ~1,7 с.
Длинный контекст (медиана 127 тыс. токенов на вызов, попадание в кэш 99 %)
почти не влияет на латентность. Оценка по всем вызовам: генерация — около 74 %
времени модели, префилл/очередь — 26 %.

## Инструменты

Суммарное время по инструментам (telegram-ходы с 26.09): терминал 796,8 мин
(2797 вызовов, в среднем 17,09 с) — главный источник машинного времени;
`execute_code` 93,8 мин (805 вызовов, 6,99 с); `process_manage` 21,3 мин;
`patch` 8,9 мин; `write_file` 6,9 мин. Отдельно `clarify` — 253,9 мин на
14 вызовов (в среднем 1088 с): это не машинное время, а ожидание ответа
владельца внутри хода.

## Сеть и устойчивость шлюза

`gateway.log` содержит 4227 предупреждающих строк; основные — недоступность
IPv4-адресов API Telegram (149.154.166.110 и 149.154.167.220) и неудача
dual-stack маршрута. 21.10.2026 — инцидент: 245 событий переподключения и
2245 строк сбоя отправки за сутки, шлюз перезапускался 5 раз за день
(`gateway-starts.log`, всего 40 запусков). Отдельно 241 ответ 429 (лимиты
провайдера) и 47 случаев `credential pool: no available entries` — переход
на фолбэк-модели и рост латентности. Всплески «прочего» (до 1370 с в одном
ходе) приходятся на окна сетевых сбоев Telegram.

## Конфигурация, значимая для скорости

`agent.reasoning_effort: low` (быстрее), `display.streaming: true`,
`display.tool_progress: all` (каждое обращение к инструменту даёт сообщение
в Telegram — это сетевые round-trip'ы, входящие в «прочее»),
`compression.threshold: 0.2` при окне 1 048 576 — сжатие начинается около
200 тыс. токенов, а типичный контекст 127 тыс., поэтому сжатие почти не
срабатывает. `prompt_caching.cache_ttl: 5m` в конфиге, но по замерам кэш
держится и после паузы свыше 900 с (попадание 96–99 %), то есть фактический
TTL у провайдера больше.

## Проверяемые гипотезы

1. Время ответа модели пропорционально числу сгенерированных токенов
   (подтверждено регрессией: 0,0088 с/токен, r = 0,60). Проверка: снизить
   многословность промежуточных вызовов и перемерить.
2. Значимая часть «прочего» — доставка промежуточных сообщений при
   `tool_progress: all` и сетевые повторы Telegram. Проверка: тот же ход при
   `tool_progress: off` и на здоровом канале.
3. Доля тяжёлых ходов (свыше 30 вызовов) устойчива ~20 % и даёт ~60 % времени;
   ускорение достижимо декомпозицией задач (делегирование, очередь), а не
   ускорением отдельного вызова.
4. Ответы 429 коррелируют с переходом на ollama-cloud-фолбэк и ростом
   латентности вызова.

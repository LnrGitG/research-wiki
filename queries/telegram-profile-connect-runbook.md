## 3. Процедура-первоисточник

Отчёт в репозитории: `~/research-wiki-private/db_docs/hermes-agent-setup-guide.md`.

> «2. Telegram-шлюз: токен от @BotFather + свой tg-user-id (список
> allowed) + home channel.» — строка 52.

> «3. `hermes gateway install --system --run-as-user <user>` →
> `hermes gateway start --system` (systemd service).» — строка 53.

Там же грабля под номером 6 сводной таблицы: Telegram-токен может
обслуживать только одного слушателя; при двойном запуске — `409 Conflict`
и обрыв сообщений, поэтому старый сервис останавливают перед новым.

Уточнение по нашей инфраструктуре: в гайде описан системный вариант
(`--system`), а у нас все шлюзы — **пользовательские** юниты в
`~/.config/systemd/user/`. Поэтому для наших профилей команда установки
идёт **без** `--system`: `hermes gateway install` ставит пользовательский
сервис, `--system` потребовал бы root и создал бы юнит в другом месте.

## 5. Порядок работ: что делает владелец, что делает агент

Шаг 1 (владелец). Создать в @BotFather нового бота и получить токен.
Токен вписывается **только** в файл `.env` соответствующего профиля,
в строку `TELEGRAM_BOT_TOKEN=`, и нигде больше: ни в переписку, ни в
репозиторий, ни в конфиг. Для двух профилей нужны два разных бота.

Шаг 2 (агент, после токена). Убедиться, что канал не занят вторым
слушателем, затем установить и запустить шлюз:

```bash
hermes --profile personal gateway status
hermes --profile personal gateway install --start-on-login
```

`--start-on-login` включает автозапуск пользовательского сервиса при входе.
Если автозапуск не нужен, установить без флага и запускать вручную.

Шаг 3 (агент). Проверить, что шлюз поднялся:

```bash
hermes --profile personal gateway status
systemctl --user status hermes-gateway-personal.service
```

Шаг 4 (владелец, из чата). Открыть диалог с новым ботом и отправить
команду `/sethome` — она назначает текущий чат домашним каналом
(home channel), то есть адресом доставки для cron-задач и фоновых
профилей. Это встроенный gateway-командный путь, отдельный ключ
`telegram.home_channel` руками править не нужно.

Шаг 5 (агент, при необходимости). Ограничить круг чатов, где бот
отвечает в группах:

```bash
hermes --profile personal config set telegram.allowed_chats "[430232790]"
```

Шаг 6 (для профиля `legal`) — повторить шаги 1–5 с подстановкой
`legal` вместо `personal`.

## 6. Точка возврата

Откат установки шлюза (выполнять только если сервис падает, например
из-за `409 Conflict` — значит токен уже слушает другой процесс):

```bash
systemctl --user disable --now hermes-gateway-personal.service
rm ~/.config/systemd/user/hermes-gateway-personal.service
systemctl --user daemon-reload
```

Данные профиля при этом не затрагиваются: откат удаляет только юнит и
останавливает процесс. Строку `TELEGRAM_BOT_TOKEN=` в `.env` можно
очистить или оставить пустой — пустое значение шлюз не поднимет.

## 7. Осталось за владельцем

1. Создать двух ботов в @BotFather (по одному на профиль).
2. Вписать токены в `~/.hermes/profiles/personal/.env` и
   `~/.hermes/profiles/legal/.env`.
3. После запуска отправить `/sethome` в диалоге с каждым ботом.
4. Дать команду на установку и запуск шлюзов (шаги 2, 3, 6).

## 8. Что исправлено против первой редакции ранбука

Первая редакция подготовлена делегатом и содержала три ошибки, снятые
при проверке:

- глобальный флаг профиля стоял **после** подкоманды
  (`hermes gateway status --profile personal`); правильная форма —
  `hermes --profile personal gateway status` (проверено запуском,
  отвечает корректно);
- в шаблоне юнита `ExecStart` вызывал `hermes gateway start --profile …`,
  то есть сервис запускал сам себя через systemd; правильно — `gateway run`
  (сверено с рабочим юнитом `macroeconomist`);
- предлагался системный вариант установки (`--system --run-as-user lnr`)
  с путём юнита `/etc/systemd/user/…`; у нас все шлюзы пользовательские,
  поэтому установка идёт без `--system`.

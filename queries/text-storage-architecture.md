# Где хранить тексты: статьи, публикации, рефераты

Разбор вопроса после замечания, что текущая схема БД описывает только
метаданные документов, но не сами тексты.

## Что есть сейчас

**В репозитории** — 721 markdown-файл, 41.8 МБ текста:

| Каталог | Файлов | Объём | Природа |
|---|---|---|---|
| `papers/` | 587 | 36.1 МБ | **производное** — извлечено из PDF, регенерируемо |
| `papers/ru_papers/` | 162 | 4.2 МБ | производное — перевод (стоит денег, но восстановимо) |
| `queries/` | 62 | 1.0 МБ | **первичный** — авторские записки |
| `concepts/` | 17 | 0.2 МБ | первичный — авторские синтезы |
| `reviews/` | 11 | 0.3 МБ | первичный |
| `annotations/` | 16 | 0.1 МБ | первичный |
| `entities/`, `comparisons/`, `news/` | 5 | <0.1 МБ | первичный |

**Итого: 36.1 МБ производного и 5.7 МБ первичного текста.** Разделение
принципиально: производное можно пересоздать из исходников, первичное — нет.

**В схеме БД** — `core.document` описывает только метаданные: `doc_code`,
`title_ru`, `doc_type`, `file_id`, `url`, `sha256`, `published_at`. Тела текста
нет нигде. `core.file_registry` хранит путь к файлу в объектном хранилище.
Таблицы для чанков и эмбеддингов отсутствуют, хотя pgvector установлен.

## Принцип: где что живёт

Три слоя, и их важно не смешивать.

**1. Тело текста — в git-репозитории, не в базе.**
Markdown-страницы вики и есть первичный артефакт: они редактируются
(Obsidian, git-версионирование), читаются как файлы, линкуются
`[[wikilinks]]`. Класть их в БД означало бы дублировать источник правды и
терять diff-историю. Git даёт версионирование бесплатно.

**2. Метаданные и связи — в PostgreSQL (`core.document`).**
Одна строка на документ: код, заголовок, тип, DOI/URL, хеш. Сюда же — связи
с показателями (`metric_id`), регионами, источниками, гипотезами через
`core.note`. Это позволяет отвечать на вопросы, которые по файлам не
отвечаются: «в каких работах упоминается эластичность предложения по
Московской области», «какие гипотезы опираются на этот источник».

**3. Чанки и эмбеддинги — в PostgreSQL с pgvector.**
Для семантического поиска нужны вектора. Текст дробится на чанки
(по разделам/абзацам), каждый получает эмбеддинг, и поиск идёт по
векторному сходству. Здесь же хранится смещение чанка в исходном файле —
чтобы вернуть не «где-то в документе», а точное место.

**4. Исходники (PDF, XLSX) — в объектном хранилище YC.**
272 PDF на 458 МБ в `raw/papers`. Хеш и путь — в `core.file_registry`.

## Каких таблиц не хватает

Схему нужно дополнить тремя таблицами (в `core` или отдельной схеме `text`).

### `core.document` — расширить

Текущие колонки метаданные; добавить связь со страницей вики и признак природы:

- `source_path text` — путь в git-репозитории (`papers/foo.md`) — связь файла
  с метаданными
- `content_sha256 text` — хеш содержимого (для отслеживания изменений)
- `doc_nature text` — `primary` (авторский текст) | `derived` (извлечённый/перевод)
- `language text` — `ru` | `en`
- `page_count int`, `char_count int` — объём
- `is_in_git bool` — подтверждение, что тело в репозитории

Назначение `doc_nature` — отделять то, что можно пересоздать, от того, что
нельзя. При потере репозитория производные тексты восстановимы из PDF,
первичные — нет, и это влияет на приоритет бэкапов.

### `core.document_chunk` — новая

- `chunk_id bigint PK`
- `document_id bigint FK → core.document`
- `chunk_no int` — порядковый номер
- `heading text` — заголовок раздела, если есть
- `body text` — сам текст чанка
- `char_start int`, `char_end int` — смещение в документе (для точной ссылки)
- `token_count int`
- `created_at timestamptz`

Уникальность: `(document_id, chunk_no)`.

Почему чанки в базе, а не только в файлах: вектор требует фиксированного
текстового фрагмента. Хранить их в БД дешевле, чем пересчитывать при каждом
поиске, и позволяет делать гибридный запрос (текстовый + векторный) одним
SQL.

### `core.document_embedding` — новая (pgvector)

- `embedding_id bigint PK`
- `chunk_id bigint FK → core.document_chunk`
- `model_code text` — какая модель считала (для смены модели без пересчёта всей базы)
- `embedding vector(N)` — сам вектор
- `created_at timestamptz`

Уникальность: `(chunk_id, model_code)` — позволяет держать несколько вариантов
эмбеддингов одного чанка (при смене модели или сравнении).

Индекс: `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)` — HNSW
быстрее ivfflat при умеренных объёмах, а у нас 721 документ.

### Связь документа со страницами вики

Страницы вики (`concepts/`, `queries/`) — это тоже документы, но особого рода:
они **ссылаются** на другие документы через `[[wikilinks]]`. Полезны две вещи:

- `doc_type` уже включает `wiki_page` — подходит для авторских страниц;
- для графа связей — либо парсить `[[wikilinks]]` в отдельную
  `core.document_link (from_doc_id, to_doc_id, link_type)`, либо оставить
  в вики, поскольку Obsidian граф строит сам.

Рекомендую начать без таблицы связей: `[[wikilinks]]` уже работают в Obsidian
и GitHub Pages, дублировать их в БД стоит только если понадобится SQL-запросы
по графу цитирований (а у тебя для этого есть `docs/bibliography.json`).

## Как это работает на практике

**Сценарий 1: обзор литературы по теме.** Запрос «эластичность предложения
жилья в России» → векторный поиск по `document_embedding` → топ-10 чанков из
разных документов → вернуть с точными ссылками (документ + смещение) →
`core.note` связывает находки с гипотезой H-002.

**Сценарий 2: сверка источников.** «Покажи все документы, где ввод жилья за
2026 отличается от Росстата» → `core.note` с `metric_id='housing_input'` →
список документов с датами и ссылками.

**Сценарий 3: библиография с проверкой.** 898 записей из `docs/bibliography.json`
→ `core.document` с DOI → Search API проверяет доступность ссылок (30,5 ₽/1000
отложенных запросов) → помечает битые.

## Оценка объёма

Тексты 41.8 МБ ≈ 15.1 млн токенов.

- **Чанки:** при среднем размере 1000 токенов — ~15 100 чанков.
- **Эмбеддинги:** 15 100 × 384 измерения × 4 байта (float32) ≈ **23 МБ**.
- С 1536-мерными (более сильная модель) — ~93 МБ.
- **Векторизация** через AI Studio (0,0101 ₽/1000 токенов): **~153 ₽** разово.

Всё это умещается в существующий PostgreSQL на 60 ГБ диска с большим запасом.

## Приоритет бэкапов

Разделение `doc_nature` даёт понятную политику:

- **первичные тексты (5.7 МБ)** — только в git, бэкап обязателен (уже есть);
- **производные (36.1 МБ)** — регенерируемы из PDF в `raw/`, бэкап второстепенен;
- **PDF-исходники (458 МБ)** — в объектном хранилище, версионирование включено;
- **чанки и эмбеддинги** — пересчитываются из текстов, бэкапить не нужно.

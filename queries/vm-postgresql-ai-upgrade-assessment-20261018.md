# Оценка целесообразности установки на ВМ «PostgreSQL 9.18 с AI-native возможностями»

**Дата:** 18.10.2026. **Постановка:** владелец поставил вопрос об установке на ВМ
research-db-2 нового релиза «PostgreSQL 9.18» с AI-native возможностями.
**Вывод:** релиза 9.18 не существует; «AI-native» в PostgreSQL реализуется не ядром,
а расширением pgvector, которое обновляется без смены мажорной версии сервера.
Установка нового мажорного релиза сейчас нецелесообразна; полезное действие —
обновление pgvector 0.6.0 → 0.8.7 и настройка памяти.

## 1. Проверка постановки

PostgreSQL нумеровал минорные версии как 9.x до 2016 года; линия 9 завершилась
релизом 9.6 (29.09.2016), поддержка прекращена 11.11.2021. Начиная с 10 (2017)
номер мажорной версии — одно число. Версии 9.18 не существовало ни в одной ветке.
Возможные прочтения запроса: (а) «PostgreSQL 18» — текущий стабильный релиз,
последний минор 18.6 от 11.08.2026; (б) «PostgreSQL 19» — 15.10.2026 вышел RC 1,
генеральная доступность запланирована на 19.11.2026.

«AI-native» в ядре PostgreSQL нет ни в 17, ни в 18, ни в 19: векторный тип, индексы
HNSW/IVFFlat и гибридный поиск живут в расширении pgvector. В PG 19 релиз-ноты
перечисляют REPACK (CONCURRENTLY), pg_plan_advice / pg_stash_advice, автоскейлинг
числа I/O-воркеров, включение логической репликации без рестарта, WAIT для
read-your-writes на стендбае, параллельный autovacuum — ничего относящегося к AI.
Пометка «AI-ready» у PostgreSQL 18 в материалах вендоров — маркетинг расширений.

## 2. Фактическое состояние ВМ (замер 18.10.2026)

- PostgreSQL 16.15 (`16.15-0ubuntu0.24.04.1`), Ubuntu 24.04.5 LTS, 4 vCPU, 7,8 ГиБ RAM, swap 0.
- Диск `/dev/vda1`: 9,1 ГБ, занято 6,7 ГБ, свободно 2,4 ГБ (74 %).
- БД `research_wiki` — 3608 МБ; таблицы 2085 МБ + индексы 1441 МБ; 311 пользовательских
  таблиц в 11 схемах; `data.observation_v2` — 6 481 177 строк; `core.fns_firms_year` —
  3 716 169 строки (607 МБ).
- `derived.metric_card`: 2505 карточек, 2498 с вектором `vector(256)`; индекс
  `metric_card_embedding_idx` — ivfflat, `lists=100`, cosine.
- Расширения: `pg_stat_statements 1.10`, `pg_trgm 1.6`, `vector 0.6.0` (пакет
  `postgresql-16-pgvector 0.6.0-1` из Ubuntu noble/universe); PostGIS нет.
- Параметры: `shared_buffers 128MB`, `work_mem 4MB`, `max_parallel_workers 8`, `jit on`.
- Репозиторий PGDG не подключён: в `/etc/apt/sources.list.d/` только `ubuntu.sources`,
  в apt доступен лишь `postgresql-16` (16.2 в базовом срезе, 16.15 в noble-updates).

## 3. Почему мажорный апгрейд сейчас нецелесообразен

1. **Диск.** Свободно 2,4 ГБ при БД 3,6 ГБ. Классический `pg_upgrade` держит два
   кластера одновременно (≈ +4 ГБ с WAL) — не помещается. `pg_upgrade --link`
   теоретически проходит по месту, но он линкует файлы данных на месте: откат к 16
   после такого шага возможен только восстановлением из дампа.
2. **Единственная копия.** Дамп от 07.10.2026 не содержит схем staging/public/v2;
   контура Hermes на ВМ нет (порт 8642 не слушается), то есть после сбоя проверить
   данные и поднять пайплайн автоматикой нечем.
3. **Пакетирование.** PG 18/19 в Ubuntu 24.04 нет; требуется добавление PGDG,
   то есть смена базы обновлений на хосте, где живёт единственная копия канона.
4. **Потребители.** DataLens (внешний доступ по TLS с собственным УЦ, дашборд
   паспорта региона), три read-only роли, SSH-тоннель на 15432, `ops.fetch_context`
   и замороженная схема v2 — смена мажора требует приёмочного прогона по всем.
5. **Срочности нет.** PG 16 поддерживается до ноября 2028; 16.15 — актуальный минор.
   PG 19 на 18.10.2026 — RC, ставить RC в единственный исследовательский контур нельзя.

## 4. Что даёт выигрыш дешевле смены мажора

- **pgvector 0.6.0 (29.01.2024) → 0.8.7 (01.10.2026).** Даёт `halfvec` (2-байтные
  компоненты, вдвое меньше индекс и больше ёмкость размерности), iterative index
  scans (планировщик не теряет recall при фильтре), улучшенную оценку стоимости при
  фильтрации, ускоренные HNSW-вставки; 0.8.7 закрывает переполнение буфера при
  построении IVFFlat. Механика: `ALTER EXTENSION vector UPDATE` + пересоздание
  индекса в обслуживаемое окно, сервер не перезапускается, мажор не меняется.
  Цена — минуты простоя на перестройку индекса; выгода — прямо в векторном поиске.
- **Индексация.** `lists=100` при 2498 векторах завышен (эвристика ~rows/1000 при
  малом объёме, √rows ≈ 50); для фильтрованного поиска по `themes` IVFFlat с
  probe по умолчанию даёт просадку recall — HNSW на halfvec устойчивее.
- **Память.** `shared_buffers 128MB` и `work_mem 4MB` — дефолты; при 7,8 ГиБ RAM и
  БД 3,6 ГБ разумны 1–2 ГБ и 16–32 МБ. Это влияет на планы сильнее, чем версия ядра.

## 5. Условия, при которых апгрейд к 18/19 оправдан

Апгрейд к PG 18.6 (или 19 после выхода 19.1, ориентировочно февраль 2027) имеет смысл,
если одновременно выполнено: (а) диск расширен хотя бы до 20 ГБ либо есть отдельный
том под staging-кластер; (б) снят полный дамп с проверкой восстановления, включая
схемы, отсутствующие в дампе 07.10; (в) на ВМ восстановлен агентский контур для
приёмочных прогонов; (г) есть окно на приёмку `ops.fetch_context`, DataLens и трёх
ролей. Практический интерес из новых версий — REPACK (CONCURRENTLY) при жёстком
диске, автоскейлинг I/O-воркеров и приоритизация autovacuum; для аналитики на
6,5 млн строк без параллельных пользователей выигрыш скромный.

## 6. Проверяемые ожидания (для проверки после обновления pgvector)

1. Перевод вектора в `halfvec(256)` с HNSW уменьшит размер индексного файла
   `metric_card_embedding_idx` примерно вдвое (замер до/после через `pg_relation_size`).
2. Iterative index scan повысит recall топ-10 при фильтре по `themes` до уровня
   точного перебора (замер: пересечение с `ORDER BY` без индекса на 200 запросах).
3. `shared_buffers` 1–2 ГБ снизит число чтений с диска на типовых `fetch_context`
   (замер по `pg_stat_statements` до/после).

# Wordstat: диагностика ряда и предложение по расширению поисковых индексов (28.09.2026)

## 1. Диагностика: ряд обрывался из-за захардкоженной даты в сборщике, а не из-за лага API

**Исправление первой версии этого разбора.** Первоначально я объяснил обрыв на 24.08.2026 лагом
публикации Wordstat. Это было неверно, и ошибка вскрылась при перепроверке по вопросу владельца.
В сборщике `scripts/wordstat_construction_collect.py` конец диапазона был вписан числом —
`dynamics(ph, 'PERIOD_WEEKLY', '2018-01-01', '2026-08-30')`. Скрипт физически не запрашивал более
поздние недели, поэтому ряд и не мог продвинуться дальше недели 24.08.

**Как измерено.** У недельной гранулярности `toDate` обязан быть воскресеньем, иначе API отвечает
HTTP 400 — мои первые пробные запросы с датами 31.08, 07.09, 14.09, 21.09 были отклонены именно по
этой причине (дни недели — понедельники), а я неверно истолковал отказы как подверждение лага.
Корректный замер по воскресеньям:

| Диапазон запроса | Точек | Последняя точка |
|---|---|---|
| 03.08 … 30.08 | 4 | 24.08 |
| 03.08 … 06.09 | 5 | 31.08 |
| 03.08 … 20.09 | 7 | 14.09 |
| 03.08 … 27.09 | 7 | 14.09 |
| 01.01.2018 … 27.09 | 455 | 14.09 |

То есть Wordstat отдаёт недельные данные по неделю, начинающуюся **14.09.2026** — лаг составляет
около двух недель, а не четырёх недель. Месячная гранулярность отдаёт август (сентябрь ещё не
опубликован), её лаг действительно около месяца.

**Что сделано.** Конец диапазона в сборщике вычисляется от текущей даты (последнее воскресенье),
захардкоженная дата убрана. Ряд пересобран: **455 недель, 9 100 строк, 20 фраз**, последняя точка
14.09.2026. Возвращённые три недели меняют картину: по широкой фразе «строительство» значения
24.08 — 810 279, 31.08 — 825 541, 07.09 — 866 539, 14.09 — 912 576, то есть после августовского
спада интерес растёт, а не падает. Прежний вывод о «падении на 21,6 % за две недели» опирался на
обрезанный ряд и снят.

**Урок для скриптов сбора.** Диапазон запроса нельзя оставлять константой: любой сборщик, у которого
даты вписаны числом, тихо перестаёт приносить новые данные, а внешне выглядит работающим — джоб
отчитывается «успешно, добавлено 0 недель». Плюс `toDate` у недельной гранулярности обязан попадать
на воскресенье, а отказ API (HTTP 400) нельзя трактовать как признак отсутствия данных.

**Побочная находка про омонимию.** Проверка связанных запросов показала, что часть очевидных фраз
для индексов непригодна в исходном виде: у фразы «работа строителем» в топе преобладают запросы про
магазин «Строитель» и режим его работы (из 44 571 запроса в месяц смысловой сигнал — меньшая часть),
а «построить дом» заметно загрязнена развлекательными запросами («дом который построил Джек» 38 469,
«как построить дом в майнкрафте» 34 171 против «сколько стоит построить дом» 27 538). Вывод для
методики: любую фразу перед включением в индекс нужно просматривать через `topRequests` и
отбрасывать те, где доля посторонних смыслов велика.

## 3. Предложение: восемь групп индексов под наши задачи

Объём указан по `topRequests` (число запросов в месяц по РФ, выгрузка
`data/wordstat_toplevel_20260927.json`) — это позволяет оценить, будет ли ряд достаточно
устойчивым, чтобы не утонуть в шуме.

|---|---|

## 3а. Дневная гранулярность как слой свежести (предложение владельца, проверено)

Идея — собирать последнее окно с дневной гранулярностью, чтобы точка была свежее. Проверка
подтвердила её полностью, с двумя оговорками по механике API:

| Гранулярность | Последняя доступная точка | Лаг | Глубина истории |
|---|---|---|---|
| дневная | 24.09.2026 | ~4 дня | только ~60 дней назад (запрос от 15.07 и раньше отклоняется) |
| недельная | неделя от 14.09.2026 | ~2 недели | с 2018 года |
| месячная | август 2026 | ~1 месяц | с 2018 года |

То есть дневной слой даёт выигрыш примерно в десять дней свежести относительно недельного и
является единственным способом увидеть первую половину сентября прямо сейчас.

**Сшивка проверяется арифметикой.** Сумма дневных значений за неделю совпадает с недельной точкой
API: для фразы «строительство» неделя 07–13.09 — 866 857 против 866 539 (+0,04 %), неделя
14–20.09 — 912 873 против 912 576 (+0,03 %). Поэтому дневные недели можно добавлять к недельному
ряду там, где недельного значения ещё нет. Автоматическая сверка по всем фразам за всё окно даёт
среднее расхождение 3,08 % и максимум 3,86 % — это отдельный вопрос: расхождение почти наверняка
сосредоточено в фразах с малыми абсолютными числами, где дневные значения у Wordstat огрублены;
на крупных фразах оно в пределах сотых долей процента. Проверку по фразам нужно довести отдельно.

**Выравнивание недель проверено.** Дневные суммы считались для семи окон с разным сдвигом начала
недели: лучшее совпадение с недельным API даёт понедельник (среднее расхождение +7,84 % у «подряд на
строительство», +2,98 % у «аренда крана», +0,07 % у «строительство»), любые сдвиги на 1–6 дней дают
и большее смещение, и втрое больший разброс. Значит, недельный ряд в Wordstat действительно
понедельничный.

**Расхождение дневных и недельных сумм систематическое и зависит от объёма фразы.** Дневные суммы
выше недельных значений, причём тем сильнее, чем меньше фраза: «строительство» (миллионы запросов) —
+0,07 %, «аренда крана» — +3,0 %, «подряд на строительство» (сотни запросов) — +7,8 %; на четырёх
неделях подряд знак и величина устойчивы. Онлайн-объяснение «недельные значения округлены» не
подтвердилось: недельные числа не кратны ни 10, ни 100. Наиболее правдоподобная версия — к недельным
агрегатам Wordstat применяет более сильную фильтрацию или дедупликацию при малых объёмах, но
документального подтверждения у меня нет, поэтому выдавать её за объяснение не буду.

**Что из этого следует практически.** Сшивать напрямую нельзя: уровень ряда дёрнулся бы на стыке.
В сборщике считается медианный множитель «недельное/дневное» по полным неделям перекрытия отдельно
для каждой фразы, и недели из дневного слоя добавляются уже с поправкой: у «подряд на строительство»
множитель 0,9277, у «смета на строительство» 0,9364, у «строительный подрядчик» 0,9446. Множитель и
признак неполной недели пишутся в `data/wordstat_weekly_provenance.json`.

**Как это устроено в сборщике.** `scripts/wordstat_construction_collect.py` собирает оба разреза:
недельный (весь ряд, 9 100 точек) и дневной (последнее окно, начало подбирается автоматически).
Дневные значения суммируются в недели понедельник–воскресенье и добавляются только для отсутствующих
недель; неполные недели помечаются. Дневной файл сохраняется сразу после сбора, чтобы сбой на
следующем шаге не стоил данных, а недельный — только по успешным фразам: неуспешные строки берутся
из прежнего файла. Текущее состояние: **9 120 недельных строк, последняя полная неделя 14.09,
добавлена неполная неделя 21.09 (четыре дня), последняя дневная точка 24.09.**

**Лимиты API.** Кроме часового лимита есть узкий минутный: при паузе 2 секунды сбор упал на HTTP 429
уже на восьмой фразе. Пауза увеличена до 8 секунд, на 429 — ожидание 75 секунд и повтор. Отдельно
проверено, что начало диапазона у недельной гранулярности тоже надо выравнивать: дата `2018-01-03`
(среда) давала отказ по всем фразам, верная — понедельник `2018-01-01`.

## 4. Стоимость и регламент обновления

Один вызов API отдаёт весь диапазон по фразе, поэтому цена расширения — число фраз плюс число
региональных пар, а не число периодов. Лимит — 100 запросов в час.

| Что | Вызовов | Когда |
|---|---|---|
| базовый набор сейчас (20 фраз, недельная) | 20 | месяц, 7-го числа |
| дневной слой свежести (20 фраз, последнее окно) | 20 | месяц, 7-го числа |
| расширение A–H (~55 фраз, недельная) | 55 | месяц, 7-го числа |
| те же фразы в месячной гранулярности (месяц как контроль к недельной) | 55 | месяц, 7-го числа |
| региональный разрез (4 фразы × 20 регионов) | 80 | месяц, 7-го числа |
| итого | ~230 | 3 запуска по лимиту 100/час, пауза 8 с между вызовами |

Практический вывод: расширенный сбор укладывается в три последовательных прохода с паузой между
ними, то есть в один вечер; держать 210 запросов в одном прогоне нельзя — упрёмся в лимит и получим
HTTP 429.

## 5. Что нужно поправить в пайплайне

1. **Фразы вынести в реестр** (`data/wordstat_phrases.csv`: фраза, группа, смысловая проверка,
   дата включения) вместо списка внутри скрипта — тогда расширение не требует правки кода.
2. **Добавить месячную гранулярность как контроль:** недельная отдаёт данные по неделю от 14.09
   (лаг около двух недель), месячная — по август (лаг около месяца); для nowcasting первична недельная,
   месячная нужна для сопоставления с официальными месячными рядами и для снятия сезонности.
3. **Каждую новую фразу прогонять через `topRequests`** и фиксировать в реестре долю посторонних
   смыслов; это уже готовый шаг, выгрузка сохранена.
4. **Пересобрать композит после расширения** — веса по MIDAS/Алмону, а не уровневая регрессия;
   текущий ориентир r = 0,644 (n = 18) служит базой для сравнения.
5. **Развести каденсы:** сбор — раз в месяц (лаг API иной смысл не имеет), пересборка композита —
   по поступлении, отчёт по индексам — в факт-блок.
